# What duplicate rules are worth

v0.6 measured the staged funnel with one implicit pool over everything
([then](../2026.07/2026.07.30-duplicate-cost.md)). v0.7 makes the pool
configurable, so the question becomes what the configuration buys.

## How

```bash
just bench-dup ~/Downloads
just bench-dup ~/Projects
DT_DUP_ROOT=~/Projects/misc just bench-dup ~/Projects
```

`core/src/duplicates.rs::diagnostics::over_a_real_tree`, release build, macOS on
Apple Silicon, APFS, warm cache. The built-in duplicate rule is in force unless
`DT_DUP_ROOT` names one part's root instead.

## The measurement

| Tree | Pool | Eligible | Contested | Read | Search | Groups |
|---|---|---|---|---|---|---|
| `~/Downloads` | built-in | 1,397 / 33.7 GiB | 539 (39%) | 3.1 GiB | 1.0 s | 247 |
| `~/Projects` | built-in | 15,879 / 87.1 GiB | 14,215 (90%) | 49.8 GiB | 13.6 s | 1,003 |
| `~/Projects` | rooted at `~/Projects/misc` | 109 / 537 MiB | 41 (38%) | 125 MiB | **0.38 s** | 7 |

**A rooted pool is the difference between a coffee and a keystroke.** Narrowing
the same tree from everything to one subdirectory cuts the search 36× in time
and 400× in bytes read. That is not a micro-optimisation of the pipeline; it is
the pipeline being told where to look, which no amount of hashing cleverness can
substitute for.

**The `.git` exclusion is not free, and pays for itself twice.** Against v0.6's
run of the same tree, eligible files fell from 16,850 to 15,879 and groups from
1,585 to 1,003. Those 582 groups were mostly a repository's own storage pairing
with the working tree — LFS objects, which git keeps verbatim. Every one of them
was noise at best: neither side of such a pair may be removed.

**The adversarial case is unchanged and still worth knowing.** A project tree has
90% of its eligible files sharing a size with something, so the size bucket
narrows almost nothing and the search reads half of what it is pointed at. The
answer is a rule, not a faster hash.

## What this says about the default

The shipped rule searches everywhere. On a home directory that is the honest
default — a user who has not said where to look should not have the tool guess —
but the numbers above are the argument for saying so. One `root` under
`duplicate-rules:` turns a search that reads fifty gigabytes into one that reads
a hundred and twenty-five megabytes.

`--explain` names the pools and their sizes precisely so that this decision is
visible before the run rather than inferred from how long it took.

## What is not measured here

- **Cold cache.** Only the incidentally-cold rows of the v0.6 note stand for it;
  the disk gave ~850 MiB/s there, and that is still the figure to plan by.
- **The cost of the rules themselves.** Pool membership is one glob-set query per
  eligible file, on the same automaton the clean rules use, whose budget was
  measured at 201 ns per node in v0.3. It disappears beside a single read.
- **Windows and Linux.** The pipeline has no platform split of its own.
