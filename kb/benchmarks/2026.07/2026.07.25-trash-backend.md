# Smoke test: the trash backend

Task 1 of the [v0.2 spec](../../specs/2026.07/2026.07.25-disk-tools-v0.2-detectors-cleanup.md)
exists to answer one question before anything is built on it: **is the `trash`
crate usable here?** The [concept](../../concepts/2026.07/2026.07.14-disk-tools.md)
recorded a downstream report of a macOS build issue and said to check first.

**Answer: yes.** The issue does not reproduce, deletions are recoverable, and the
cost on a large tree is negligible — for a reason that shapes Task 7.

Reproduce with `just smoke-trash`.

## Environment

| | |
|---|---|
| Machine | Mac16,5 — 16 cores, 64 GB RAM |
| OS | macOS 26.5.2, APFS |
| Crate | `trash` 5.2.6 (2026-05-03, 2.3M downloads, MIT) |
| Toolchain | stable; crate MSRV is **1.85.0**, identical to ours |

## The build question

`cargo build -p disk-tools-core` succeeded in **3.4 s** from a cold fetch. The
reported problem was with the old `cocoa`/`objc` stack; 5.x builds on `objc2`.

Dependencies actually pulled on macOS — four crates, none heavy:

```
trash v5.2.6
├── log v0.4.33
├── objc2 v0.6.4
│   └── objc2-encode v4.1.0
├── objc2-foundation v0.3.2
│   └── bitflags v2.13.0
└── percent-encoding v2.3.2
```

Linux adds `libc`, `once_cell`, `scopeguard`, `urlencoding`, `chrono`; Windows adds
`windows` 0.56. **No dbus, no portal** — headless CI needs nothing extra.

## Results

| Case | Result |
|------|--------|
| Single file | Trashed; original path gone |
| Non-existent path | `Err(TrashFailure)` carrying path and reason — no panic |

### Trashing 10,000 files, one call on the directory

`just smoke-trash` runs in CI on all three platforms, so these are measured, not
assumed:

| Platform | Time | Backend |
|----------|------|---------|
| Linux (ubuntu-latest) | **443 µs** | freedesktop — a rename into `~/.local/share/Trash` |
| macOS (this machine / CI) | **198 ms / 140 ms** | Finder via `osascript` |
| Windows (windows-latest) | **3.1 s** | `IFileOperation` → Recycle Bin |

**A four-order-of-magnitude spread, and it settles Task 7's progress question.**

On Linux and macOS the directory moves as one item — the cost is a rename, and
10,000 files cost what one costs. Progress there would be decoration.

On Windows it is **3.1 seconds**, which is per-file work however the call is
phrased. That is squarely in the range where a user assumes the tool has hung. So
progress reporting is **required, not optional** — and since the backend never
reports per-file completion, the granularity available is per *candidate*. A
cleanup run removing several large trees can show which candidate it is on; it
cannot show a percentage within one.

The concept's warning about huge trees was right, just not where expected: not on
macOS, where it was raised, but on Windows.

**Not measured:** a candidate on a **different volume**, which cannot be renamed
and must be copied. That is where even Linux would hurt. Worth measuring during
Task 7, on an external disk.

## Recoverability — and the limits of verifying it

macOS offers two backends, and `trash::delete` uses the crate's default:

| | Finder (**default**) | NsFileManager |
|---|---|---|
| "Put Back" in the context menu | ✓ | ✗ |
| Speed | slower | faster |
| Extra permissions | may prompt | none |

The default is the right one for this project: **"Put Back" is the recoverability
the whole safety model promises.** Do not switch to `NsFileManager` for speed —
198 ms is not a problem worth trading recovery for.

**Confirmed by hand**, because it cannot be confirmed any other way on macOS:

- `~/.Trash` is unreadable from the test process — `Operation not permitted`, macOS
  TCC. Full Disk Access would be needed, which a test must not require.
- `trash::os_limited::list()` is documented as Windows/Linux only, and the macOS
  backend has no `list` at all, so it does not even compile there.

So an automated test on macOS can assert only that **the original path is gone** —
which would also be true of an unrecoverable delete. The gap was closed by opening
Finder and checking: the trashed items are present and offer "Put Back".

That limitation is worth remembering: **on macOS, no test can prove the safety
promise.** It rests on the crate's documented behaviour plus this one manual check.

## An upstream bug worth knowing about

`trash` 5.2.6's Windows delete path calls
`CoCreateInstance(&FileOperation, None, CLSCTX_ALL).unwrap()`
(`src/windows.rs:42`) — while the *same call* in its `purge_all` and `restore_all`
paths (lines 186, 224) correctly uses `?`. So on Windows, a COM initialisation
failure **panics** rather than returning an error, and no wrapper on our side can
convert a panic into a `TrashFailure`.

That matters here more than it would elsewhere: the whole point of returning
failures as data is that one bad candidate must not abort a cleanup run mid-way,
leaving the user unsure what was removed. A panic does exactly that.

It is unlikely in a normal desktop session and plausible in a service, session-0
process, or restrictive sandbox. Mitigation: `just smoke-trash` now runs in CI on
all three platforms, so if a runner is COM-hostile it turns up as a red build
instead of a user's aborted run. Worth reporting upstream.

**It did not fire on `windows-latest`** — the first CI run with the smoke test was
green — so a normal GitHub runner initialises COM fine. That is evidence the path
is rare, not evidence it is safe.

## Risks carried into Task 7

- **The Finder method drives `osascript`.** It may prompt for Automation permission
  on a fresh machine, and it needs Finder running — an SSH or headless session may
  behave differently. Untested here.
- **Cross-volume candidates** are a copy, not a rename; the timings above say
  nothing about them.
- **Headless Linux works.** The freedesktop backend needs no desktop session, no
  dbus and no portal — `ubuntu-latest` trashed successfully with nothing installed.
  The "skips loudly when there is no backend" path therefore stayed unexercised on
  every platform: all three have one.
- **MSRV is exactly ours.** `trash` requires 1.85.0 and so do we. A future bump in
  the crate breaks the `msrv` CI job immediately — that job is the early warning,
  and it should not be relaxed.
