# What the cleanup engine costs

v0.2 added four rules on top of the scan, three of which are pure functions over
the built tree and cost nothing worth measuring. The fourth shells out to `git`.

This note exists because nobody had measured that, and the number turned out to
matter: it is not a rounding error on top of the scan, it is **the** cost of a
dry run.

## Environment

| | |
|---|---|
| Machine | Mac16,5 — 16 cores, 64 GB RAM |
| OS | macOS 26.5.2, APFS |
| Build | `just release` |
| Tool | `hyperfine -N --warmup 3 --runs 10 --output=null` |

## The fixture

50 directories, each a separate `git init` with a `Cargo.toml`, a `src/main.rs`
and a `target/debug/artifact.bin` of 200 KiB. 14 MB in total — deliberately tiny,
so that what is being measured is the guard and not the walk. Every repository is
dirty (nothing is committed), so every one of the 50 `rust-target` candidates
reaches the guard and is excluded by it.

## Results

| Command | Time | |
|---------|------|---|
| `disk-tools <path>` | **14.7 ms** ± 0.2 | the scan alone |
| `disk-tools clean <path> --allow-dirty` | **14.7 ms** ± 0.3 | guard disabled |
| `disk-tools clean <path>` | **1.178 s** ± 0.183 | guard enabled |
| `disk-tools clean <path> --safe` | **2.083 s** ± 0.036 | *before* the fix below |

Three things follow.

**The guard costs ~23 ms per repository**, and everything else is noise beside
it. A dry run over 50 repositories is **80×** a plain scan of the same tree.
That is one process spawn plus a `git status --porcelain` per repository — the
price D6 accepted to avoid a libgit2 or `gix` dependency for one boolean.

**`--allow-dirty` is genuinely free.** It short-circuits before the filesystem is
touched rather than computing the answer and ignoring it — 14.7 ms against
14.7 ms says so exactly.

**Memoisation is doing its job.** The 50 candidates sit in 50 distinct
repositories, so this is the worst case: one `git status` each. Candidates
sharing a repository — a Cargo workspace, most commonly — collapse to one call.

## What measuring it found

`--safe` was **the slowest of the three modes**, at nearly twice a plain `clean`.
It is also the mode worth recommending, being the one that only offers
regenerable output.

The cause was not the filter. It was that the report wants to say "N more
candidates need confirmation", and the count was obtained by planning a **second
time** without the flag and subtracting — a full extra pass of the guard, which
is to say a doubling of the only expensive thing in the operation.

`CleanPlan` now carries `filtered_out`, counted by the pass that already runs:

| | before | after |
|---|---|---|
| `clean --safe` | 2.083 s | **1.140 s** |

That also removed a correctness hazard rather than only a slow one. Task 6's
review had found the subtraction of two independently-measured plan lengths could
wrap on `usize` — the guard re-reads the world on each call, so the unfiltered
plan can come back *shorter* — and announce eighteen quintillion hidden
candidates in a release build. With one plan there is nothing to subtract.

## What is not measured

- **A large real tree.** `~/Projects` here is 159 GB across 174 repositories; a
  full `clean` over it was not timed. Extrapolating from 23 ms per repository
  gives roughly 4 seconds of guard on top of the walk, but the walk itself
  dominates at that size and the two have not been measured together.
- **Windows and Linux.** Process spawn is more expensive on Windows, so the
  per-repository figure is likely worse there; nothing confirms that.
- **A repository with a large working tree.** `git status` cost grows with the
  number of tracked files, and every repository in this fixture has three.
  `core.fsmonitor` would change the picture again.

## If it ever needs to be faster

The obvious move is to run the guard across repositories in parallel — the calls
are independent and the memo is already keyed by repository. Nothing needs it
today: at 23 ms per repository, a tree has to hold hundreds of Rust projects
before the guard rivals the walk it follows.
