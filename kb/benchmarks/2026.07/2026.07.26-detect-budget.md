# What detection costs, and the budget a rule engine inherits

v0.3 replaces the four hardcoded safe-list categories with declarative rules read
from a config file. Before agreeing to that, one number was missing: what the
hardcoded matcher costs today. `phase_split` timed the walk, the dedup and the
aggregation — **detection was not in it**, so the rewrite had no baseline to be
compared against.

This note establishes one.

## Environment

| | |
|---|---|
| Machine | Mac16,5 — 16 cores, 64 GB RAM |
| OS | macOS 26.5.2, APFS |
| Build | `--release` |
| Tool | `just bench-phases ~/Projects` |
| Tree | `~/Projects` — 171 GB, **2 339 316 entries**, 26 211 hardlink groups |

## Results

```
  walk           12.1s   86.4%
  dedup        382.4ms    2.7%
  aggregate       1.2s    8.4%
  detect       347.0ms    2.5%   104 candidates
  detect*      667.5ms          every node visited, nothing claimed
  total          14.0s
```

**Detection is 2.5% of a scan.** The walk is 86% and nothing else comes close.
That alone settles whether detection is "the hot path": it is not.

**But 347 ms is not a per-node cost.** `detect` never descends into a match — a
claimed `node_modules` is one candidate, not 40 000 — so the pass skips whole
subtrees and visits far fewer than 2.34M nodes. Only 104 candidates came back,
but the subtrees behind them are exactly the dense ones.

`detect*` is the same pass with `CategorySet::none()`: nothing claims anything,
the DFS reaches every node, and the name checks still run. **667 ms over
2 339 316 nodes — 285 ns per node.**

## Why the upper bound is the number that matters

285 ns per node is the budget a declarative rule engine has to hit, and the
comparison has to be made against the *unclaimed* figure rather than the 347 ms,
because a config with narrower rules claims less and therefore visits more. The
worst case for the rule engine is precisely a config that matches nothing — which
is also the config a user gets after disabling categories they do not want.

Against a 12.1 s walk, even a rule engine three times slower than today's matcher
adds 1.3 s, or 9% of a scan. That is the honest ceiling on how bad this can get.

## What the current matcher spends it on

`claim()` calls `user_dirs.cache_roots()` on **every node** (`core/src/detect.rs:228`),
and that function allocates a `Vec` and performs two or three `PathBuf::join`s per
call. On this tree that is roughly seven million allocations, in code shipped
since v0.2 and never measured.

The rule model removes them: roots resolve once when the rules are compiled.
Some of the 285 ns is therefore budget the rewrite gets back before it spends
anything.

## What the rule engine must do to stay inside it

- **One `GlobSet` across all rules**, not one per rule. `GlobSet::matches()`
  returns the indices of the patterns that matched; mapping pattern index to rule
  index and taking the lowest *is* "list order is precedence". One match call per
  node instead of one per rule.
- **One `globset::Candidate` per node.** It precomputes the basename and the
  lowercased form once; that is what it exists for, and rebuilding it per pattern
  would pay the cost N times.
- **Prefix-prune by rule root at directory level.** A subtree under no rule's
  root is skipped whole — one comparison per directory rather than a match per
  file. A config whose rules all sit under `~/Projects/github` should make a scan
  of `~` almost free to detect over.
- **Cheap predicates after the glob, not before.** `requires-sibling` and
  `older-than` rarely eliminate anything, so running them first would cost more
  than it saves.

## What the rule engine actually cost

Task 1 landed and the same measurement was repeated on the same tree.

| | hardcoded (v0.2) | rules (v0.3) | |
|---|---|---|---|
| `detect` | 347.0 ms | **196.3 ms** | −43% |
| `detect*` (nothing claimed) | 667.5 ms | **472.4 ms** | −29% |
| per node | 285 ns | **201 ns** | |
| candidates on `~/Projects` | 104 | **104** | unchanged |

The budget was "no more than 2×", and it came in at **0.71×** — the declarative
engine is *faster* than the `match` it replaced. Two reasons, in order of size:

**The per-node allocation is gone.** `claim()` called `cache_roots()` on every
node, building a `Vec` and two or three `PathBuf`s each time. Roots now resolve
once, when the rules are compiled.

**One automaton beats a chain of comparisons.** Five rules' patterns compile into
a single `GlobSet`; a `Candidate` computes the basename once and every pattern
reuses it. v0.2 did `same_path` against each cache root, then three string
comparisons, then an extension check.

Identical candidate counts on a 171 GB tree of 174 repositories is the strongest
available evidence that the rewrite changed no behaviour. The upper-bound figure
is now produced by an age rule with an impossible threshold rather than by
disabling categories, since there are no categories left to disable.

## What is not measured

- **Windows and Linux.** Path handling differs — `Candidate` lowercases on
  Windows where the match is case-insensitive — and neither was timed.
- **A config with many rules.** Five built-ins were measured. A user with fifty
  rules pays more in `GlobSet` construction (once) and, if the single-set design
  is not followed, per node.
