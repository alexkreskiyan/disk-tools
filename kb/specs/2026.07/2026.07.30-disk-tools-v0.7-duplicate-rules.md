# Feature Spec: disk-tools v0.7 — rules made of parts

## 1. Overview

v0.6 made duplicates findable and left **where** they are looked for
unconfigurable. Fixing that turned out to need a change one level down, in what a
rule *is*.

Today a rule is a root plus three independent lists — `includes`, `excludes`,
`requires-sibling` — and its meaning is their cross product. The pairing between
a pattern and the marker that justifies it is lost, and `requires-sibling` is
matched **all**, so this cannot be said at all:

> claim `bin/` when a `*.csproj` sits beside it, **or** when a `*.fsproj` does

v0.7 makes a rule a **name, a consequence, and a list of parts**, each part a
self-contained statement about what qualifies:

```yaml
clean-rules:
  - name: dotnet-output
    tier: purge
    parts:
      - root: "~/"
        includes: ["**/bin/", "**/obj/"]
        requires: ["*.csproj"]
      - root: "~/"
        includes: ["**/bin/", "**/obj/"]
        requires: ["*.fsproj"]
```

The same shape carries duplicates, and there the parts mean something subtly
different — which is the interesting half:

| | a part contributes |
|---|---|
| **clean rule** | matchers. Anything satisfying **any** part is claimed, independently |
| **duplicate rule** | a population. Everything satisfying any part is **pooled**, and duplicates are searched *within that pool* |

So adding a part to a clean rule adds candidates; adding a part to a duplicate
rule can **create groups that did not exist**, because two populations can now
pair. One word, two consequences, and the second is worth a comment in the
template.

The sharp edge this started from — git LFS stores its objects verbatim, so every
tracked file pairs with its own object under `.git/lfs/objects/` — is then an
ordinary `excludes` in the built-in duplicate rule, and no longer needs a clean
rule that would also offer `.git` for deletion. (Verified before this spec: such
a rule prunes the search *and* lists `2.0M git-internals confirm …/repo/.git`.)

- **Concept:** [2026.07.14-disk-tools.md](../../concepts/2026.07/2026.07.14-disk-tools.md)
- **Predecessor:** [v0.6 — duplicates](2026.07.30-disk-tools-v0.6-duplicates.md)
- The configuration became YAML before this spec was written; `[[rules]]` is
  `rules:` today and becomes `clean-rules:` here.

## 2. Approach

### Architecture

```
config.yml
  ├── clean-rules:     ─► Rules      ─► detect ──► plan ──────────────┐
  │      name/tier/enabled + parts        │                            ├─► CleanPlan ─► apply
  │                                       └── prunes ──┐               │
  └── duplicate-rules: ─► DupRules ───────────────────┴─► duplicates ─►┘
         name/tier/keep/keep-in + parts        one pool per rule
```

### Design Decisions

| Decision | Chosen | Rationale | Alternatives |
|---|---|---|---|
| A rule is parts | `name` + consequence + `parts: [...]`, **always**, with no flat form | Two spellings of one thing tax everything else: every example, every error message and every future field has to answer "and in the flat form?". Two lines per rule is the cheaper side of that trade, and people copy what `config init` writes | Flat rule as sugar for one part |
| What a part holds | Everything that decides *whether an object qualifies*: `root`, `includes`, `excludes`, `requires`, `requires-clean-repo`, `older-than`, `min-size` | If a part is a self-contained statement, a predicate left outside it makes the part unreadable on its own. It also makes "old `bin/`, but any `obj/`" expressible, and "`target/` only in dirty repos here, in any repo there" | Thresholds and the git guard on the rule, one set for all its parts |
| What the rule holds | `name`, `tier`, `enabled`; duplicate rules add `keep` and `keep-in` | Identity and consequence. A tier on a part would make the part a rule, and the rule would stop being the unit the report groups by | `tier` per part |
| `includes` / `excludes` | Arrays in a part | The pairing that matters is *between* parts, not inside one; two patterns under one condition should not have to be two parts. A bare string is still accepted, as today | One `include` per part |
| `requires-sibling` → `requires` | Renamed, an array, matched **all**, and now **paths relative to the directory holding the match** | `Cargo.toml` is the depth-0 case of `src/main.rs`, so nothing existing changes meaning and `requires: ["src/main.rs"]` becomes sayable. No filesystem: `detect` walks down from the parent through the tree it already has, one lookup per component, and a glob inside a component matches among that directory's children | Sibling names only |
| `..` in any pattern field | **Refused at parse time**, in `includes`, `excludes` and `requires` alike | It is the only way a pattern can leave its root, and every way it can do so is a mistake: an `includes` that escapes compiles to a glob no absolute path matches — silently disabling the part — and a `requires` that escapes cannot be checked statically at all, since the match's depth under the root is unknown until it is found. Refusing ascent makes "a pattern never leaves its root" a property proved once, at startup, rather than a case handled per match | Allow, and treat leaving the root as a failed predicate |
| Where rules are validated | Entirely at parse time, for **every** verb, before anything is walked | The rules decide what may be deleted. A structural mistake found halfway through a removal is a mistake found too late, and one found only by a rule quietly matching nothing is not found at all | Validate lazily, per match |
| Duplicates: pooling | Everything a rule's parts match is **one pool**; groups form only inside a pool | The keeper policy and the tier are then never ambiguous — a group cannot span two rules, so there is nothing to resolve. It replaces the open question v0.7 opened with | Group across rules, resolve by list order |
| Pool membership | **Exclusive: the first rule, in list order, whose parts match a file takes it** | Overlapping pools are not an ambiguity, they are a corrupt plan: one pool names a file its keeper while another lists it for removal, and both end up in the same merged plan. Exclusivity makes "no intersections needed" true rather than merely intended, and reuses the precedence list order already carries | Membership in every matching pool |
| The cost of exclusivity | Accepted, and made visible: the report states how many pools were searched and how big each was | A photo in `~/Photos` and its copy in `~/Downloads` are in different pools if they are in different rules, and will never be compared. That is expressible — one rule, two parts — but the failure of *not* expressing it is silent, and silence is what the count is for | Leave it unsaid |
| Two lists | `clean-rules:` and `duplicate-rules:` | `includes` names *what will be deleted* in one and *what will be compared* in the other. One list would make a reader check a `kind` field before they could read the row below | One list with `kind:` |
| The rename | `rules:` → `clean-rules:`, old spelling is a **hard error** | An unfamiliar key is a warning here, so silence would mean the user's rules stop applying while `clean` runs on the built-ins | Accept both |
| `tier` on a duplicate rule | `trash` and `confirm`; **`purge` refused** | For a clean rule `purge` means "one command regenerates this". A duplicate's content is regenerated by nothing — the other copy is the only thing making removal safe. `--purge` the flag still applies: typed by hand, like `--yes` | All three |
| `requires-clean-repo` on a duplicate part | Refused | The guard asks whether build output regenerates identically from committed source. It says nothing about a photograph | Accept and ignore |
| `--dup` with no PATH | Walks the roots of every part of every enabled duplicate rule | The v0.6 special case disappears; this is the sentence `preview` with no path already speaks | Keep requiring a PATH |
| `Candidate.rule` | The rule's own name; `DUPLICATE_RULE` and the reserved name go | The two kinds never appear in one plan, so a name shared across the lists cannot be ambiguous | Keep the fixed string |
| Sharing the matcher | One compiled `Parts` matcher, used by both rule kinds; the kinds differ only in what they carry beside it | The matching question is now literally the same object, which is what the parts model bought. The kinds diverge in consequence, not in matching | A matcher per kind |

### Components

**New:**
- `core/src/parts.rs` — `Part`, and the compiled `Parts` matcher both kinds use
- `core/src/dup_rules.rs` — `DuplicateRule`, pools, and exclusive membership

**Modified:**

- `core/src/detect.rs`, `core/src/clean.rs` — a claim comes from a part

## 3. Tasks

### Task 1: parts in the core

- **Goal:** A rule is a name, a consequence and a list of parts, and everything that decided a match moves into the part.
- **Acceptance Criteria:**
  - [ ] Given a rule with two parts, when a node satisfies either, then it is claimed, once, with the rule's tier
  - [ ] Given a node satisfying no part, when detection runs, then the rule does not claim it
  - [ ] Given two parts with different `requires`, when a node has the marker of the second only, then it is claimed — the case the old cross-product could not express
  - [ ] Given a part with `requires: ["*.csproj", "*.sln"]`, when only one of them sits beside the node, then the part does not hold: every pattern must find something of its own
  - [ ] Given `requires: ["src/main.rs"]`, when a match's directory holds `src/main.rs`, then the part holds — and `Cargo.toml` still means the file beside the match, which is the same rule at depth 0
  - [ ] Given `requires: ["src/*.rs"]`, when that directory holds any `.rs`, then the part holds: a glob matches among the children of the directory it names
  - [ ] Given a `requires` path that leads outside the scanned tree — a match at the tree's own root — then the part does not hold, as it does today for a root with no siblings
  - [ ] Given a part with its own `older-than` / `min-size` / `requires-clean-repo`, when detection runs, then it constrains that part and no other
  - [ ] Given parts with different roots, when `scan_roots` is asked, then it returns the roots of all of them, still dropping any nested in another
  - [ ] Given a part whose root cannot be resolved, when the rules are compiled, then that **part** matches nothing while the rule's other parts stand
  - [ ] Given a disabled rule, when the rules are compiled, then none of its parts match anything
  - [ ] Given the built-in rules expressed as parts, when they are compiled, then they claim exactly what they claimed before
- **Tests first (TDD):** the existing `rules.rs` and `detect.rs` suites, re-expressed; the third and fifth criteria are new capability and need new fixtures.
- **Key files:** `core/src/parts.rs`, `core/src/rules.rs`, `core/src/detect.rs`, `core/src/clean.rs`
- **Dependencies:** None
- **Status:** Done

#### Implementation Notes
One `GlobSet` across every pattern of every part of every rule, with the pattern
index mapping to `(rule, part)` rather than to `rule`. `Rules::state` — what the
browser colours by — answers from the part that matched, so `in scope` and
`included` keep meaning what they mean.

**`Facts` changes shape.** `any_sibling` is a predicate over sibling *names*,
which cannot answer `src/main.rs`; the parent's node goes in instead, and the
descent walks its children. That is a change to a public core type, and it is the
one place where "the core reads no filesystem" has to be re-proved: every lookup
still comes from the `ScanTree`, so a `requires` path leading outside the scanned
tree is unanswerable and reads as *no*, exactly as an absent sibling does today.

### Task 2: the config, renamed and reshaped

- **Goal:** `clean-rules:` with parts parses; the old spellings are refused by name.
- **Acceptance Criteria:**
  - [ ] Given `clean-rules:` with `parts:`, when parsed, then the rules compile
  - [ ] Given `rules:`, when parsed, then it is an error naming `clean-rules`
  - [ ] Given a rule with no `parts`, when parsed, then it is an error saying that a rule is a list of parts, and showing one
  - [ ] Given a rule carrying `root` or `includes` of its own, when parsed, then it is an error pointing at the part they belong in
  - [ ] Given `requires-sibling`, when parsed, then it is an error naming `requires` — an alias would outlive the rename
  - [ ] Given `..` anywhere in an `includes`, `excludes` or `requires` pattern, when parsed, then it is refused with one message: a pattern may not leave the root of its part
  - [ ] Given any rule error at all, when any verb runs, then the program stops before a single directory is walked
  - [ ] Given `includes: "**/x/"`, when parsed, then a bare string is still one-element list
  - [ ] Given `config init`, when it writes, then the template is in the new shape and parses back to the built-in rules
- **Key files:** `cli/src/config/mod.rs`
- **Dependencies:** Requires Task 1
- **Status:** Done

### Task 3: the browser refuses to work on rules it cannot read

- **Goal:** `R` over a broken config blocks the browser rather than leaving it painted in stale colours.
- **Acceptance Criteria:**
  - [ ] Given a config that no longer parses, when `R` re-reads it, then the browser enters a blocked state showing the error in full — not a one-line notice at the foot of a screen still painted in the previous rules' colours
  - [ ] Given the blocked state, when any key but `R` or `q` is pressed, then nothing happens: every colour, every `clean` column and every legend row on that screen is a claim about rules the tool no longer has
  - [ ] Given the blocked state, when `R` re-reads a config that parses, then the browser resumes with the new rules in force and the sizes recomputed against them
  - [ ] Given the blocked state, when `q` is pressed, then the terminal is given back as always
  - [ ] Given a config broken at startup, when `ui` is asked to open, then it never opens — the existing behaviour, unchanged, since the rules are unknown before the first frame
- **Tests first (TDD):** the blocked state is a value on `App`, so both the key handling and the drawing are testable without a terminal, as everything else in the browser is.
- **Key files:** `cli/src/ui/app.rs`, `cli/src/ui/mod.rs`
- **Dependencies:** Requires Task 2
- **Status:** Done

#### Implementation Notes
This reverses a v0.4 decision: a bad file used to leave the working rules in
place with a notice, so that a typo would not turn every colour off. That was
right when the alternative was an empty screen; it is wrong now that the notice
is one dim line under a screenful of colours the file no longer justifies. The
new rule is the same one the CLI already follows — rules that cannot be read
stop the work — and blocking keeps the two verbs saying the same thing about the
same file.

### Task 4: duplicate rules and their pools

- **Goal:** `duplicate-rules:` decides what is compared with what.
- **Acceptance Criteria:**
  - [ ] Given a duplicate rule with two parts, when the pass runs, then files from both are compared **with each other** — one pool
  - [ ] Given two duplicate rules whose parts both match a file, when the pass runs, then the **first** rule takes it and the second never sees it
  - [ ] Given a file matched by no duplicate rule, when the pass runs, then it is not compared
  - [ ] Given a rule with `excludes: ["**/.git/"]`, when the pass runs, then nothing under any `.git` is compared and the directory is not descended into
  - [ ] Given a rule's `keep` and `keep-in`, when a group forms in its pool, then that rule's policy chooses the keeper
  - [ ] Given `tier: purge` on a duplicate rule, when the config parses, then it is refused with the reason
  - [ ] Given `requires-clean-repo` in a duplicate part, when the config parses, then it is refused with the reason
  - [ ] Given an absent `duplicate-rules:`, when a `--dup` run resolves, then the built-in applies: everything, less `**/.git/`
  - [ ] Given `duplicate-rules: []`, when a `--dup` run resolves, then nothing is compared — a different statement from absence
  - [ ] Given a clean rule claiming a subtree, when the pass runs, then nothing inside it is compared, whatever the duplicate rules say
- **Key files:** `core/src/dup_rules.rs`, `core/src/duplicates.rs`, `cli/src/config/mod.rs`
- **Dependencies:** Requires Tasks 1, 2
- **Status:** Done

### Task 5: the flags become overrides

- **Goal:** `--dup` runs on the rules; the flags override what a rule said, in the one place precedence lives.
- **Acceptance Criteria:**
  - [ ] Given `--dup` and no PATH, when the args resolve, then the roots of every part of every enabled duplicate rule are walked
  - [ ] Given `--keep` / `--keep-in`, when the args resolve, then they win over every rule's own
  - [ ] Given `--min-size`, when the args resolve, then it applies alongside each part's, and the larger decides
  - [ ] Given no `--dup`, when the args resolve, then the duplicate rules compile but are never consulted
  - [ ] Given both verbs, when their flags are compared, then the sets are still identical

## 4. Boundaries

### In Scope
- Parts as the rule model, for both kinds
- Two lists, the rename, and refusing the old spellings loudly
- Pools, exclusive membership, per-rule keeper policy
- `--explain`

### Out of Scope
- **Editing rules from the TUI** — removed with the move to YAML; the browser
  reads rules and colours by them, and `R` re-reads the file
- **Automatic migration of a user's file** — the errors name the new spellings
- **Ascending paths.** `requires` descends; `..` is refused everywhere. Adding it
  would need an ancestor stack in `detect` and a per-match bounds check that no
  amount of parsing could replace
- Duplicate directories, reflinking, similar-file detection

### Protected Elements (DO NOT CHANGE)
- The never-touch denylist, and that no rule or flag reaches it
- `apply` taking no removal mode
- `#![deny(unsafe_code)]` and its four exemptions
- The core reading no clock, no environment and no config
- `std::path::absolute`, never `canonicalize`
- Identical flag sets on `preview` and `clean`
- Clean rules pruning the duplicate search

See `CLAUDE.md`. The rule engine is `core/src/rules.rs`; the config layer is

**TDD workflow:** a failing test per acceptance criterion first.

| Task | What to Test | Type |

| 2 | The new shape parses; all three old spellings refuse by name | Unit |

Path literals are platform-shaped — `/x` is drive-relative on Windows, and a path
written into a **config literal** has the same problem: build it with `rooted()`
and put it in a YAML single-quoted string. CI caught exactly that in v0.6.

## 7. Open Questions

None. The one that was here — what `requires` matches against — is settled:
**paths relative to the directory holding the match**, descending only. What the
field means is still stated where a user meets it (the template, `--explain`),
because the name does not say it; what is refused is `..`, and that refusal is
what makes "a pattern never leaves its root" checkable once, at startup.

## 8. Implementation Reference

### 8.1 Data Structures

```rust
// core/src/parts.rs

/// One self-contained statement about what qualifies.
pub struct Part {
    /// `None` is the file's `"*"`: wherever the scan goes.
    pub root: Option<String>,
    pub includes: Vec<String>,
    pub excludes: Vec<String>,
    /// Paths **relative to the directory holding the match**, each of which must
    /// find something of its own. `Cargo.toml` is the depth-0 case; `src/main.rs`
    /// descends. `..` is refused at parse time, so a pattern can never leave the
    /// part's root and nothing here needs checking again at match time.
    pub requires: Vec<String>,
    pub requires_clean_repo: bool,
    pub older_than: Option<Duration>,
    pub min_size: u64,
}

/// Every part of every rule, compiled into one automaton.
pub struct Parts { /* pattern index → (rule, part) */ }

// core/src/rules.rs
pub struct Rule {
    pub name: String,
    pub tier: Tier,
    pub enabled: bool,
    pub parts: Vec<Part>,
}

// core/src/dup_rules.rs
pub struct DuplicateRule {
    pub name: String,
    pub tier: Tier,          // Trash or Confirm; Purge refused by the config layer
    pub enabled: bool,
    pub keep: Option<Keep>,
    pub keep_in: Vec<PathBuf>,
    pub parts: Vec<Part>,    // one pool, whatever any of them matches
}

pub struct DuplicateRules { /* … */ }

impl DuplicateRules {
    /// The pool this file belongs to: the **first** rule, in list order, whose
    /// parts match it. Exclusive, so no file is in two pools and no plan can
    /// both keep and remove it.
    pub fn pool(&self, path: &Path, facts: &Facts<'_>) -> Option<&DuplicateRule>;
    pub fn prunes(&self, dir: &Path) -> bool;
    pub fn scan_roots(&self) -> Vec<PathBuf>;
}
```

### 8.2 Algorithms

#### 8.2.1 A claim, from parts

**Used by:** Task 1

At each node, the rules are tried in list order; within a rule its parts are
tried in order; the first part whose root contains the node, whose `includes`
match, whose `excludes` do not, and whose predicates hold claims it, with the
**rule's** tier. A match is still never descended into.

#### 8.2.2 Pools

**Used by:** Task 3

1. A clean rule claims this subtree → skip it whole. Unchanged, and it wins.
2. `DuplicateRules::prunes(dir)` → skip the subtree.
3. For each file, `pool(path, facts)` → the first rule whose parts match. None →
   not compared.
4. Groups form **within a pool only**. The pool's rule supplies `keep`,
   `keep_in` and `tier`; each part supplies the `min_size` that let its files in.

**Edge cases:**
- A file matched by a later rule only: ordinary, it joins that pool.
- Two parts of one rule matching the same file: one pool, one membership.
- A pool with fewer than two files: no group, and its size is still reported.

### 8.3 Validation Rules

| Rule | Condition | Behavior | Task |
|---|---|---|---|
| Renamed list | `rules:` present | Error naming `clean-rules` | 2 |
| Parts required | a rule with no `parts` | Error, with an example | 2 |
| Nothing outside a part | `root` / `includes` on the rule | Error naming the part they belong in | 2 |
| Renamed field | `requires-sibling` | Error naming `requires` | 2 |
| No standing purge | `tier: purge` on a duplicate rule | Error: nothing regenerates a duplicate | 3 |
| Wrong predicate | `requires-clean-repo` in a duplicate part | Error naming why it cannot apply | 3 |
| Empty vs absent | `duplicate-rules: []` | No comparison at all; absence keeps the built-in | 3 |
