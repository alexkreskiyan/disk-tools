# Feature Spec: disk-tools v0.7 — duplicate rules, and saying what will happen

## 1. Overview

v0.6 made duplicates findable. It left **where** they are looked for
unconfigurable: `--dup <PATH>` searches everything under the path except what a
clean rule claims, and the only lever a user has is `--min-size`.

That gap has a sharp edge. Git LFS stores objects **verbatim**, so every
LFS-tracked file pairs with its own object under `.git/lfs/objects/` — the report
offers to delete one side of a pair where neither side may go. Excluding it today
means writing a clean rule for `**/.git/`, which prunes the duplicate search
**and makes `.git` a removal candidate**. Verified: with such a rule
`preview -d 1` lists `2.0M git-internals confirm …/repo/.git`.

So v0.7 gives duplicates their own rules, on the same terms as cleaning:

```toml
[[duplicate-rules]]
name     = "everywhere"
root     = "*"
includes = ["**"]
excludes = ["**/.git/"]   # LFS keeps its objects verbatim
```

Two consequences ride along. `[[rules]]` is renamed **`[[clean-rules]]`**, since
a file with two rule lists cannot have one of them called "rules". And `--explain`
answers, before anything is walked, the question a file with two rule lists makes
much easier to get wrong: *what is about to happen, and under which rules*.

- **Predecessor:** [v0.6 — duplicates](2026.07.30-disk-tools-v0.6-duplicates.md)

## 2. Approach

### Architecture

```
config.toml
  ├── [[clean-rules]] ──► Rules ─────────► detect ──► plan ─────────┐
  │                          │                                       ├─► CleanPlan ─► apply
  │                          └── prunes ──┐                          │
  └── [[duplicate-rules]] ─► DupRules ────┴─► duplicates ──► plan_duplicates
                                 │
                                 └── per area: keep, keep-in, min-size, tier
```

Both rule kinds still act on a `--dup` run, and they act differently on purpose:

| | says |
|---|---|
| a **clean** rule | *this whole directory may go* — so never look for single files inside it |
| a **duplicate** rule | *files here may be compared with each other*, and what to do with the copies |

### Design Decisions

| Decision | Chosen | Rationale | Alternatives |
|---|---|---|---|
| Two lists | `[[clean-rules]]` and `[[duplicate-rules]]` | `includes` means *what will be deleted* in one and *what will be compared* in the other. One list would make a reader check `kind` before they could read the row below it — the same defect that made `duplicate` a reserved name in v0.6 | One `[[rules]]` list with `kind = "junk" \| "duplicates"` |
| The rename | `[[rules]]` → `[[clean-rules]]`, and the old spelling is a **hard error** naming the new one | An unknown table is a *warning* here, so leaving it would mean a user's edited rules are silently ignored while `clean` runs on the built-ins. That is worse than refusing to start. Same call as `tier = "auto"`: an alias lives for ever, an error costs one edit — and the tool is unpublished | Accept both; warn and continue |
| `tier` on a duplicate rule | `trash` and `confirm` only; **`purge` is refused** | For a clean rule `purge` means "one command regenerates this". A duplicate's content is regenerated by *nothing* — the only thing making its removal safe is the other copy, and if the keeper was chosen wrongly there is no way back. `trash` keeps one | All three, for schema symmetry; no `tier` at all |
| `--purge` the flag | Still applies under `--dup` | Typed by hand at the moment of running, like `--yes`. A standing instruction in a file is the thing being refused, not the deliberate act | Refuse it too |
| `requires-clean-repo` | Not a field on a duplicate rule; present is an error | The guard asks whether build output would regenerate identically from committed source. That says nothing about a photograph | Accept and ignore it |
| `keep` / `keep-in` | Per duplicate rule, overridden by the flags | "In `~/Photos` keep the oldest; in the exports keep whatever is in the library" is the request that made the flag exist. It is a property of an area | Global only, as in v0.6 |
| Exclusion | Plain `excludes` on a rule, no new field | `excludes` already means "matched by `includes`, but not this". A `.git` exclusion is then an ordinary rule, and the **built-in default is one** — visible in `config init`, editable, and not hardcoded | A separate `[duplicates] excludes` list; a hardcoded skip |
| Absent `[[duplicate-rules]]` | Leaves the built-in in force | Exactly as for clean rules. The alternative turns the feature off for everyone who upgrades | Empty means "search everything" |
| `--dup` with no PATH | Walks the roots of the duplicate rules | The special case v0.6 needed disappears: with rules that have roots, this is the same sentence `preview` with no path already speaks. The "no rule names a directory" message is already written | Keep requiring a PATH |
| `Candidate.rule` for a duplicate | The **duplicate rule's own name**, and `duplicate` stops being reserved | The two kinds never appear in one plan, so a name shared across the two lists cannot be ambiguous. The v0.6 reservation existed because there was no rule to name | Keep the fixed string |
| Sharing the matcher | Duplicate rules get their own compiled type, sharing the **helpers** (glob compilation, `strip_dir_marker`, `resolve_root`) rather than the `Rules` container | The predicate sets have already diverged and will diverge further. Making `Rules` generic over both would put type noise through a 1,776-line tested engine to save ~100 lines of compilation. The risk — two matchers drifting on glob semantics — is bought off by one shared test asserting identical answers | Generic `Rules<R: Matchable>`; one `Rule` type with unused fields |
| The TUI | Writes `[[clean-rules]]` only; duplicate rules are edited by hand | The browser is a *directory* browser: it colours rows by what a rule says about that path, which is the clean question. Editing an area's `keep` policy from a file listing has no obvious gesture | Teach the editor both lists |

### Components

**New:**
- `core/src/dup_rules.rs` — `DuplicateRule` / `DuplicateRules`, compiled and applied
- `cli/src/explain.rs` — what a command is about to do, as text

**Modified:**
- `core/src/rules.rs` — helpers made shareable; nothing about clean rules changes
- `core/src/duplicates.rs` — participation decided by the rules, not by the walk
- `core/src/clean.rs` — `Candidate.rule` carries the duplicate rule's name; `DUPLICATE_RULE` goes
- `cli/src/config/mod.rs` — the rename, the second list, the built-in, the template
- `cli/src/config/write.rs` — writes `[[clean-rules]]`
- `cli/src/args.rs` — `--explain`; `--dup` with no path; `--keep` / `--keep-in` become overrides

## 3. Tasks

### Task 1: the rename

- **Goal:** `[[clean-rules]]` is the name, and a file still using `[[rules]]` stops the program with a message naming the replacement.
- **Acceptance Criteria:**
  - [ ] Given a config with `[[clean-rules]]`, when it is parsed, then the rules are read exactly as `[[rules]]` used to be
  - [ ] Given a config with `[[rules]]`, when it is parsed, then it is an **error** naming `clean-rules` — not a warning, and not an unknown key
  - [ ] Given a config with both, when it is parsed, then it is the same error: guessing which one is meant is not on
  - [ ] Given the browser writing a rule to a file with no rule list, when it writes, then it writes `[[clean-rules]]` and the built-ins with it
  - [ ] Given `config init`, when it writes, then the template uses the new name and parses back to the built-in rules
- **Tests first (TDD):** the existing config tests renamed, plus the three refusal cases.
- **Key files:** `cli/src/config/mod.rs`, `cli/src/config/write.rs`, `README.md`, `CLAUDE.md`
- **Dependencies:** None
- **Status:** Pending

#### Implementation Notes
`serde_ignored` reports an unfamiliar table as a warning, so the refusal cannot
be left to the schema: `FileConfig` needs a `rules: Option<toml::Value>` field
whose presence is checked and rejected by hand, the way `tier = "auto"` is.

### Task 2: duplicate rules in the core

- **Goal:** `DuplicateRule` / `DuplicateRules`, and a `duplicates()` that asks them what may be compared.
- **Acceptance Criteria:**
  - [ ] Given a rule rooted at `~/Photos`, when the pass runs over a wider tree, then only files under that root are compared
  - [ ] Given `includes = ["**/*.jpg"]`, when the pass runs, then a `.mov` of the same size is not compared with anything
  - [ ] Given `excludes = ["**/.git/"]`, when the pass runs, then nothing under any `.git` is compared **and the directory is not descended into**
  - [ ] Given two rules whose roots overlap, when a file matches both, then the **first in list order** decides — its `keep`, its `min-size`, its `tier`
  - [ ] Given a file no rule matches, when the pass runs, then it is not compared
  - [ ] Given a rule with `min-size`, when the pass runs, then a file below it is never opened, and the flag's value still applies where it is larger
  - [ ] Given a rule with `older-than`, when the pass runs, then only files untouched for that long are compared
  - [ ] Given a rule with `keep = "newest-modified"`, when a group is formed from files it matched, then that rule's policy chooses the keeper
  - [ ] Given a disabled rule, or one whose root cannot be resolved, when the rules are compiled, then it matches nothing — never everything
  - [ ] Given the same tree and rules twice, when the pass runs, then the groups and their keepers are byte-identical
  - [ ] Given a clean rule claiming a subtree, when the pass runs, then nothing inside it is compared, whatever the duplicate rules say
- **Tests first (TDD):** temp trees for the matching cases; the drift guard is a test that compiles one pattern set into both matchers and asserts they answer identically over a fixture of paths.
- **Key files:** `core/src/dup_rules.rs`, `core/src/duplicates.rs`, `core/src/rules.rs`, `core/src/lib.rs`
- **Dependencies:** None (parallel to Task 1)
- **Status:** Pending

#### Implementation Notes
- A group may hold files matched by **different** rules — two copies of one photo,
  one inside `~/Photos` and one outside. The keeper policy is taken from the rule
  that matched the **keeper candidate set**, resolved as: the first rule, in list
  order, that matched any member. Stated in the report (Task 5).
- `min_size` is now per rule *and* a flag. The larger wins, as with clean rules;
  which of the two dropped a file is counted apart, so the report can name the
  right remedy.

### Task 3: the second list in the config

- **Goal:** `[[duplicate-rules]]` parses, validates and defaults, and `config init` explains it.
- **Acceptance Criteria:**
  - [ ] Given a `[[duplicate-rules]]` entry, when it is parsed, then `root`, `includes`, `excludes`, `requires-sibling`, `older-than`, `min-size`, `keep`, `keep-in`, `tier` and `enabled` are read
  - [ ] Given `tier = "purge"` on one, when it is parsed, then it is an error saying why: a duplicate's content is regenerated by nothing, so there is no way back from a wrong keeper
  - [ ] Given `requires-clean-repo` on one, when it is parsed, then it is an error naming the reason rather than a warning
  - [ ] Given an absent `[[duplicate-rules]]`, when a `--dup` run resolves, then the built-in applies: everything, less `**/.git/`
  - [ ] Given an empty `[[duplicate-rules]] = []`, when a `--dup` run resolves, then nothing is compared — a different statement from absence, as for clean rules
  - [ ] Given `config init`, when it writes, then the file carries the built-in duplicate rule with the comment explaining LFS, and parses back to it
  - [ ] Given a duplicate rule sharing a name with a clean rule, when it is parsed, then it is accepted — the two never appear in one plan
- **Tests first (TDD):** string-literal configs through `parse`, as every other config test.
- **Key files:** `cli/src/config/mod.rs`
- **Dependencies:** Requires Tasks 1, 2
- **Status:** Pending

### Task 4: the flags become overrides

- **Goal:** `--dup` runs on the rules; the flags override what a rule said, in the one place precedence is expressed.
- **Acceptance Criteria:**
  - [ ] Given `--dup` and no PATH, when the args resolve, then the roots of the enabled duplicate rules are walked, and the existing "no rule names a directory" message covers the empty case
  - [ ] Given `--keep` with rules that carry their own, when the args resolve, then the flag wins for every rule
  - [ ] Given `--keep-in`, when the args resolve, then it wins over every rule's own list
  - [ ] Given `--min-size`, when the args resolve, then it applies alongside each rule's, and the larger decides
  - [ ] Given no `--dup`, when the args resolve, then the duplicate rules are compiled but never consulted
  - [ ] Given both verbs, when their flags are compared, then the sets are still identical
- **Key files:** `cli/src/args.rs`, `cli/src/main.rs`
- **Dependencies:** Requires Task 3
- **Status:** Pending

### Task 5: the report names the rule

- **Goal:** A duplicate group says which rule governed it, and the keeper line stays as informative as v0.6 made it.
- **Acceptance Criteria:**
  - [ ] Given a plan from duplicate rules, when it renders at `-d 0`, then each group shows the rule that governed it

  - [ ] Given `--json`, when it renders, then each group carries its rule's name

### Task 6: `--explain`

- **Goal:** A global flag that states what the command is about to do, and does nothing else.
- **Acceptance Criteria:**
  - [ ] Given `--explain` on any verb, when it runs, then it prints and **exits 0 without scanning, reading or removing anything**
  - [ ] Given `--explain`, when it prints, then it names: the config file actually read (or that none was found), the mode (rules or duplicates), the roots that would be walked and where they came from, the rules in force **and the ones dropped, with the reason**, every floor and threshold with the source of each value (flag, file, or default), and — for `clean` — where each tier sends things and whether confirmation would stop the run
  - [ ] Given a value that came from the file, when it prints, then it says so; given one from a flag, likewise. A user reading this must be able to find the line to change
  - [ ] Given `--explain --json`, when it runs, then the same facts as a document
  - [ ] Given `--explain` and a config that does not parse, when it runs, then it reports the config error as usual and exits 2 — explaining cannot be a way to skip validation
- **Tests first (TDD):** the text is built from a value, so it renders into a buffer like every other report.
- **Key files:** `cli/src/explain.rs`, `cli/src/args.rs`, `cli/src/main.rs`, `cli/tests/cli.rs`
- **Dependencies:** Requires Task 4 (it explains the resolved mode, so the resolution has to be final)

## 4. Boundaries

### In Scope
- A second rule list, with its own schema, defaults and validation
- The rename, and refusing the old name loudly
- Per-area keeper policy, floors and tier
- `--explain`

### Out of Scope
- **Editing duplicate rules from the TUI.** The browser writes `[[clean-rules]]`;
  it colours *paths* by what a rule says about them, and an area's keeper policy
  has no gesture in a file listing.
- **Migrating a user's file automatically.** The error names the new spelling;
  the edit is one word.
- **Duplicate directories**, reflinking instead of removing, similar-file
  detection — all still out, as in v0.6.

### Protected Elements (DO NOT CHANGE)
- The never-touch denylist, and that no rule or flag reaches it
- `apply` taking no removal mode
- `#![deny(unsafe_code)]` and its four exemptions
- The core reading no clock, no environment and no config
- `std::path::absolute`, never `canonicalize`
- Identical flag sets on `preview` and `clean`
- Clean rules pruning the duplicate search — a directory that goes whole is not
  a place to remove single files from, whatever the duplicate rules say

### Constraints
- MSRV 1.88, edition 2024, three platforms
- A config that cannot be understood stops the program before anything is walked

## 5. Codebase Context

See `CLAUDE.md`. The rule engine is `core/src/rules.rs` (compiled `GlobSet`, list
order is precedence, an unresolvable rule matches nothing); the config layer is
`cli/src/config/`, which owns every question about the file's schema, because the
core reads no config.

### Build & Test Commands
- Build: `just build` · Test: `just test` · Gate: `just verify`

## 6. Testing Strategy

**TDD workflow:** a failing test per acceptance criterion first.

### Per-Task Testing
| Task | What to Test | Test Type |
|---|---|---|
| 1 | The new name reads; the old name refuses; the writer emits the new one | Unit |
| 2 | Matching, scoping, exclusion, precedence, per-rule policy, determinism; the two matchers agree | Unit |
| 3 | Parsing, both refusals, both defaults, the template round-trip | Unit |
| 4 | Resolution tables: roots from rules, every flag overriding every rule field | Unit |
| 5 | Rendering into a buffer, and the JSON shape | Unit |
| 6 | The text, the document, and that nothing is scanned | Unit + integration |
| 7 | `just verify` on three platforms | CI |

### Test Patterns
- `tempfile::tempdir()` fixtures; hardlink fixtures degrade with a printed reason
- Path literals are platform-shaped — `/x` is drive-relative on Windows, and a
  path written into a **config literal** has the same problem: build it with
  `rooted()` and put it in a TOML literal string. CI caught exactly that in v0.6.

## 7. Open Questions

- [ ] When a group's members were matched by different rules, the spec takes the
      first rule in list order that matched any member. The alternative — refuse
      to group across rules — is stricter and may be what a user rooting a rule
      at `~/Photos` expects. Decide before Task 2 lands.

## 8. Implementation Reference

### 8.1 Data Structures

```rust
// core/src/dup_rules.rs

/// Where duplicates may be looked for, and what to do with the copies.
pub struct DuplicateRule {
    pub name: String,
    /// `None` is the file's `"*"`: wherever the search goes.
    pub root: Option<String>,
    pub includes: Vec<String>,
    pub excludes: Vec<String>,
    pub requires_sibling: Vec<String>,
    pub older_than: Option<Duration>,
    /// Below this a file here is never opened.
    pub min_size: u64,
    /// `Trash` or `Confirm`. `Purge` is unrepresentable by validation, not by
    /// the type — the type is shared, and the config layer refuses it by name.
    pub tier: Tier,
    pub keep: Option<Keep>,
    pub keep_in: Vec<PathBuf>,
    pub enabled: bool,
}

pub struct DuplicateRules { /* one GlobSet, pattern index → rule index */ }

impl DuplicateRules {
    pub fn new(rules: Vec<DuplicateRule>, dirs: &UserDirs) -> Result<Self, RuleError>;
    /// The first rule, in list order, that claims this file for comparison.
    pub fn governing(&self, path: &Path, facts: &Facts<'_>) -> Option<&DuplicateRule>;
    /// Can anything under this directory be compared? Prunes the walk.
    pub fn prunes(&self, dir: &Path) -> bool;
    pub fn scan_roots(&self) -> Vec<PathBuf>;
}

pub fn builtin_duplicate_rules() -> Vec<DuplicateRule>;  // everything, less **/.git/
```

### 8.2 Algorithms

#### 8.2.1 Participation

**Used by:** Task 2

1. A clean rule claims this subtree → skip it whole. Unchanged, and it wins.
2. `DuplicateRules::prunes(dir)` → skip the subtree; nothing under it can match.
3. For each file: `governing(path, facts)` → the first rule whose root contains
   it, whose `includes` match, whose `excludes` do not, and whose predicates hold.
   No rule → not compared.
4. That rule supplies `min_size` (against the flag's, larger wins), and later
   `keep` / `keep_in` / `tier` for any group it governs.

#### 8.2.2 The rename's refusal

**Used by:** Task 1

`FileConfig` gains `rules: Option<toml::Value>`. Present → `ConfigError::Invalid`
naming `clean-rules`. Checked **before** anything else is validated, so a stale
file gets the one message that matters rather than a complaint about a key inside
a table that no longer exists.

### 8.3 Validation Rules

| Rule | Condition | Behavior | Task |
|---|---|---|---|
| Renamed list | `[[rules]]` present | Error naming `clean-rules` | 1 |
| No standing purge | `tier = "purge"` on a duplicate rule | Error: nothing regenerates a duplicate | 3 |
| Wrong field | `requires-clean-repo` on a duplicate rule | Error naming why it cannot apply | 3 |
| Names | A duplicate rule named like a clean rule | Accepted | 3 |
| Empty vs absent | `[[duplicate-rules]] = []` | No comparison at all; absence keeps the built-in | 3 |
