# Feature Spec: disk-tools v0.4 — the TUI

## 1. Overview

`disk-tools ui <PATH>` opens a terminal file manager over the same core — closer
to `mc` than to `ncdu`. One directory on screen at a time, every entry coloured by
its standing against the configured rules, and directory sizes computed only when
asked for.

The point of the screen is the **rules**. A user browsing their disk sees which
paths `clean` would touch, which are merely in scope, and which are excluded —
and can turn what they are looking at into a rule without leaving the program.

- **Concept:** [2026.07.14-disk-tools.md](../../concepts/2026.07/2026.07.14-disk-tools.md) §6, as amended 2026-07-26
- **Predecessor:** [v0.3 configuration and declarative rules](2026.07.26-disk-tools-v0.3-config-rules.md)

The concept's original §6 assumed the TUI browsed a tree `scan` had already
built. On a real target that is 2.3 million nodes, 1.4 GB and fourteen seconds
before a key can be pressed. The amendment replaces it with lazy, per-directory
work; this spec implements the amendment.

## 2. Approach

### Architecture

```
  disk-tools ui <PATH>
          │
          ▼
  ┌──────────────────────────────────────────────┐
  │ cli/src/ui/                                  │
  │   app.rs      state: cwd, cursor, sort, sizes│
  │   term.rs     alternate screen; panic hook   │
  │   listing.rs  read_dir -> Vec<Entry>         │
  │   measure.rs  thread per directory + channel │
  │   paint.rs    colours, bar, legend           │
  │   edit.rs     dialog -> toml_edit -> config  │
  └───────┬──────────────────────────┬───────────┘
          │                          │
          ▼                          ▼
  ┌───────────────────┐    ┌─────────────────────┐
  │ core::measure()   │    │ Rules::state(path)  │
  │ cancellable walk, │    │ untracked | inscope │
  │ running total     │    │ included  | excluded│
  └───────────────────┘    └─────────────────────┘
```

`scan()`, `plan()` and `apply()` are untouched. The TUI does its own listing and
asks the core two new questions.

### Design Decisions

| # | Decision | Chosen | Rationale | Alternatives |
|---|----------|--------|-----------|--------------|
| T1 | Where the TUI lives | A `ui` module in `cli`, always built | One binary, one build. The user chose this over a feature flag | `[features] ui`, mirroring the core's `trash` |
| T2 | Sizing | New `core::measure()` — a cancellable walk returning a running total | `scan()` builds a whole tree (1.4 GB on `~/Projects`) when the answer wanted is one number, and cannot be abandoned half-way | Reuse `scan()` on the subdirectory |
| T3 | Listing | The TUI reads directories itself | It needs `created()`, which `ScanNode` does not carry — and adding it would change the `--json` wire shape for a field only the TUI wants | Extend `ScanNode` with `created` |
| T4 | Rule states | **Four**, not three | "Under a root, matched by no `includes`" is the common case: `root = "~"` puts the whole home in scope while `includes` matches `.cache/`. Folding it into either neighbour misreports most of the screen | Three, per the first reading |
| T5 | Percent of parent | Denominator is the sum of the siblings **computed so far** | With lazy totals there is no parent figure to divide by. Bars settle as counting proceeds, which is honest about what is known | Show no bar until everything is computed |
| T6 | Writing the config | `toml_edit` | Rewriting through `toml` discards comments, and the comments are what `config init` exists to produce | Serialize and rewrite |
| T7 | MSRV | Rises 1.85 → **1.88** | `ratatui` 0.30 requires 1.86+, 0.30.2 requires 1.88. Staying would mean `ratatui` 0.29, a major version behind | Pin `ratatui` 0.29 (MSRV 1.74) |
| T8 | Creation time | Sorting by it **degrades to name** where the platform has none, and says so | `Metadata::created()` returns `Unsupported` on Linux filesystems without `statx` birth times. A silently different order is worse than a stated fallback | Hide the sort order on such platforms |
| T9 | Deletion from the TUI | **Out of scope** | Marking writes a *rule*; removal stays with `clean`, which has the denylist, the git guard, the tiers and the dry run. Duplicating that decision surface in a UI is where it would diverge | Mark-and-trash, as the original §6 sketched |
| T10 | Keys | Mnemonic letters, one per sort order rather than a cycle | A cycle makes "sort by size" a variable number of presses depending on where you are. Vim's `hjkl` and the arrows both work | `mc`'s F-keys with a hint line |
| T11 | The rule dialog | A **full editor** — `root`, `includes`, `excludes`, `min-size`, `older-than`, `tier`, `enabled` | The user's choice. A dialog limited to appending an include would send them to a text editor for everything else, which defeats the point of editing from the browser | Append to `includes` only; append to `includes` or `excludes` |
| T12 | `ui` with no path | Opens the **working directory** | The rule against defaulting to the CWD exists so that nothing huge is *scanned* by accident. Opening a browser costs one `read_dir`, so the reason does not carry. `scan` and `clean` are unchanged | Required, as `scan` demands |

## 3. Tasks

### Task 1: The terminal opens, and closes whatever happens

- **Goal:** `disk-tools ui <PATH>` enters an alternate screen, quits on `q`, and
  **cannot leave the terminal broken**.
- **Acceptance Criteria:**
  - [x] Given `ui <PATH>`, when `q` is pressed, then the terminal is restored and
        the exit code is 0
  - [x] Given a panic inside the draw loop, when the process ends, then the
        alternate screen has been left and echo restored
  - [x] Given a path that does not exist, when `ui` starts, then it is a usage
        error **before** the alternate screen is entered
  - [x] Given no path at all, when `ui` starts, then it opens the working
        directory (T12) — unlike `scan`, which still demands one
  - [x] Given stdout is not a terminal, when `ui` starts, then it refuses with a
        message rather than writing escape sequences into a pipe
- **Tests first (TDD):** terminal restoration driven through the guard type, not
  a real terminal; a `#[should_panic]` test asserting the guard's `Drop` ran;
  integration tests for the two refusals, which need no terminal at all.
- **Key files:** `Cargo.toml`, `.github/workflows/ci.yml`, `cli/Cargo.toml`,
  `cli/src/ui/term.rs`, `cli/src/args.rs`, `cli/src/main.rs`, `cli/tests/cli.rs`
- **Dependencies:** None
- **Status:** Done
- **Handoff:** [2026.07.26-disk-tools-v0.4-tui-task-1.md](../../handoffs/2026.07/2026.07.26-disk-tools-v0.4-tui-task-1.md)

#### Implementation Notes
Restoration belongs to a guard whose `Drop` leaves the screen, **plus** a panic
hook — `Drop` does not run on abort, and a hook alone loses the ordinary path.
This is the task's substance: a user whose terminal is left without echo has to
type `reset` blind.

MSRV rises to 1.88 here, so the CI job pinned to 1.85 moves with it.

- **Goal:** One directory on screen, navigable, in any of four orders.
- **Acceptance Criteria:**

### Task 3: Lazy directory sizing

- **Goal:** A directory's total is computed when asked for, restartable, and
  visible as it grows.
- **Acceptance Criteria:**
  - [x] Given a directory with no size yet, when sizing is requested, then the
        row shows a rising figure beside a spinner
  - [x] Given a walk in progress, when the user navigates away, then it **runs to
        completion** and its answer is cached — revised during Task 3, see below
  - [x] Given a walk of a directory, then walks of anything inside it are not
        started separately: the outer walk reports each subtree as it finishes
  - [x] Given some siblings sized, then each bar and percentage is against the sum
        of the sized ones (T5)
  - [x] Given sizing in progress, when the TUI exits, then no thread outlives the
        process
  - [x] Given `core::measure` and a cancel flag set part-way, then it returns
        having stopped, and the partial figure is not presented as final
- **Tests first (TDD):** `measure` against a temp tree, with cancellation driven
  from the test; the percent-of-sized arithmetic as a pure function.
- **Revised during implementation.** The criterion as written was "a size in
  progress **stops** when restarted". Tested on a real home directory that is
  wrong twice over: navigating away threw the work out, so coming back
  recomputed it from nothing; and the walk of `~` and the separate walks of
  `~/Projects`'s children were the same tree measured twice. Cancellation is now
  only what the user asks for (`r`) and what exit requires. What made
  cancel-on-navigate seem necessary — stale answers landing on the wrong rows —
  is solved by keying results on the absolute path instead.
- **Key files:** `core/src/measure.rs`, `cli/src/ui/measure.rs`,
  `cli/src/ui/layout.rs`
- **Dependencies:** Requires Task 2
- **Status:** Done
- **Handoff:** [2026.07.27-disk-tools-v0.4-tui-task-3.md](../../handoffs/2026.07/2026.07.27-disk-tools-v0.4-tui-task-3.md)

### Task 4: Rule states on screen

- **Goal:** Every entry is coloured by what the configured rules say about it.
- **Acceptance Criteria:**
  - [x] Given a path under no rule's root, then its state is `untracked`

### Task 5: The rule editor

- **Goal:** `a` on an entry opens a form over a whole rule — new, or an existing

- **Acceptance Criteria:**

## 4. Boundaries

### In Scope
- `disk-tools ui <PATH>`: navigation, sorting, lazy sizing, rule colouring
- Writing and reloading `config.toml` from the TUI

### Out of Scope
- **Deletion from the TUI** (T9) — marking writes a rule; removal stays with
  `clean`
- Mouse support, search, `mc`'s two panels, file operations (copy, move, rename)
- A published binary — distribution is still deferred

### Protected Elements (DO NOT CHANGE)
- `scan()`, `plan()`, `apply()` and the whole cleanup pipeline
- The denylist, in code and unreachable from any file or flag
- `ScanNode` and the `--json` wire shape (T3 exists to avoid touching them)
- `scan <PATH>` and `clean [PATH]` behaviour and output
- `#![deny(unsafe_code)]` in the core

### Constraints
- MSRV **1.88** after Task 1; the pinned CI job moves with it
- The core still reads no config, no clock and no environment
- The terminal must be restored on every exit path, panic included
- No test may require a real terminal: CI has none

## 6. Testing Strategy

**TDD workflow:** one failing test per acceptance criterion, then the simplest
code that passes.

**CI has no terminal.** Every criterion above is therefore expressed over a value
rather than a screen: sorting is a function on a `Vec<Entry>`, rule state is a
function on a path, the percent arithmetic is a function on two numbers, and the
config edit is a function from TOML text to TOML text.

Layout is checked too, through `ratatui::backend::TestBackend` — a fake terminal
of a fixed size whose buffer can be read back (added in Task 2). A real
pseudo-terminal is *not* an option: `script` reports a size of 0×0, so nothing
renders at all.

### Per-Task Testing
| Task | What to Test | Test Type |
|------|--------------|-----------|
| 1 | Terminal restoration via the guard's `Drop` and the panic hook; the two pre-terminal refusals | Unit + integration |
| 2 | Listing over temp directories; sorting as a pure function; the birth-time fallback | Unit |
| 3 | `measure` against a temp tree including cancellation; percent-of-sized arithmetic | Unit |
| 4 | `Rules::state` over hand-built rule lists, no filesystem | Unit |
| 5 | The form's state and validation, reusing `config.rs`'s | Unit |
| 6 | The edit as TOML-in/TOML-out, asserting comments survive | Unit |
| 7 | — | Manual review |

### Test Patterns
- Hand-built values over filesystems wherever the logic allows
  (`core/src/detect.rs` `fn file`, `fn dir`, `fn tree`)
- Temp directories via `tempfile`, never a fixed path
- Anything that really deletes is `#[ignore]`d — nothing here should

## 8. Implementation Reference

### 8.1 Data Structures

#### `Entry` — one row on screen

| Field | Type | Notes |
|-------|------|-------|
| `name` | `OsString` | As the listing gave it |
| `is_dir` | `bool` | |
| `size` | `Option<u64>` | Known immediately for a file; `None` for a directory until measured |
| `modified` | `Option<SystemTime>` | |
| `created` | `Option<SystemTime>` | `None` where the platform has no birth time (T8) |
| `state` | `RuleState` | Recomputed when the config reloads |

#### `RuleState`

| Variant | Meaning |
|---------|---------|
| `Untracked` | Under no rule's `root` |
| `InScope` | Under a `root`, matched by no `includes` |
| `Included` | Matched by a rule's `includes` |
| `Excluded` | Under a `root`, matched by a rule's `excludes` |

### 8.2 Algorithms

#### 8.2.1 `core::measure`

**Used by:** Task 3

```
measure(root, cancel: &AtomicBool, progress: impl Fn(u64)) -> Measured
```

1. Walk as `scan` does, in parallel, but accumulate a total instead of building
   nodes.
2. Check `cancel` at each directory boundary — per entry would cost an atomic
   load per file for no better responsiveness.
3. Report the running total through `progress` at each directory boundary.
4. Return `Measured { total, complete: bool }`. **`complete` is not decoration**:
   a cancelled total is a lower bound, and presenting it as a size would be the
   screen lying about what is known.

**Edge cases:**
- Unreadable subdirectory: skipped, as `scan` does, and counted so the caller can
  say the figure is partial.
- Cancelled before any directory finishes: total 0, `complete: false`.

#### 8.2.2 Percent of the siblings computed so far

**Used by:** Task 3

1. Sum the `size` of every sibling that has one.
2. If that sum is 0, draw no bar — dividing by nothing produces either a panic or
   a lie.
3. Otherwise each sized entry's bar is `size / sum`.

Bars therefore move as more siblings are measured. That is intended: the
alternative is showing nothing until everything is known, on a screen whose whole
point is being usable before then.

#### 8.2.3 `Rules::state`

**Used by:** Task 4

1. If the path is under no resolved root → `Untracked`.
2. If any rule's `excludes` matches → `Excluded`.
3. If any rule's `includes` matches → `Included`.
4. Otherwise → `InScope`.

Excludes are tested before includes so that a path matching both reads as
excluded — the narrower statement, and the one a user wrote to override the other.

### 8.4 Keys

| Key | Does |
|-----|------|
| `↑` `↓` / `j` `k` | Move the cursor |
| `Enter` / `l` | Enter the directory under the cursor |
| `←` / `h` / `Backspace` | Up one level |
| `n` | Sort by name |
| `s` | Sort by size |
| `c` | Sort by creation time |
| `m` | Sort by modification time |
| *(the active order again)* | Reverse it |
| `Space` | Measure, or re-measure, the directory under the cursor |
| `a` | Open the rule editor for the entry under the cursor |
| `r` | Re-read the config file |
| `?` | Help |
| `q` | Quit |

One key per order rather than a cycle: with a cycle, "sort by size" costs a
different number of presses depending on where you already were, which is the
kind of thing that stops being learnable.

### 8.3 Validation Rules

| Rule | Condition | Behaviour | Task |
|------|-----------|-----------|------|
| Path | `ui <PATH>` does not exist | Usage error, before the alternate screen | 1 |
| Terminal | stdout is not a tty | Refuse with a message | 1 |
| Birth time | Platform reports none | Sort falls back to name, stated on screen | 2 |
| Cancellation | Flag set mid-measure | Return a lower bound flagged incomplete | 3 |
| Config write | File has comments | They survive (`toml_edit`) | 5 |
| Config reload | File is now invalid | Message; the loaded rules stay in effect | 5 |
