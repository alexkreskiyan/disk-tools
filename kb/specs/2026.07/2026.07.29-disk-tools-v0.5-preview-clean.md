# Feature Spec: disk-tools v0.5 — preview and clean

## 1. Overview

`clean` means two things today. Without `--apply` it shows; with it, it removes.
One word for both is why the flag exists, and the flag is why the word is
ambiguous. v0.5 splits them:

- **`preview`** — what would be removed. Removes nothing, refuses nothing.
- **`clean`** — removes it. To the OS trash, immediately, no `--apply`.

The two take an **identical** flag set, because the way preview is used is to
retype the same line with a different verb.

Around that split, three smaller things:

- The report **unfolds by depth** (`-d`) rather than being capped by count
  (`-n`, which goes). Level 0 is one line per rule, 1 is one line per candidate.
- **Where a candidate goes becomes part of the rule.** `node_modules` and
  `target/` are regenerable by a command; putting 20 GB of them in the trash
  frees nothing until the trash is emptied. A third tier says so, and the three
  are renamed to answer one question — *what does `clean` do with this*:
  `purge` · `trash` · `confirm`.
- `--allow-dirty` goes: `requires-clean-repo` is already per-rule, which is the
  right granularity and the right place.

- **Concept:** [2026.07.14-disk-tools.md](../../concepts/2026.07/2026.07.14-disk-tools.md) §4
- **Predecessor:** [v0.4 the TUI](2026.07.26-disk-tools-v0.4-tui.md)

The roadmap listed v0.5 as the duplicate detector. This takes the number;
duplicates become v0.6. Nothing in that ordering was a dependency — duplicates
are blocked by the cleanup engine, which has shipped, and this reworks the
surface that would present them.

## 2. Approach

### Architecture

```
  disk-tools preview [PATH]          disk-tools clean [PATH]
            │                                  │
            └──────────────┬───────────────────┘
                           │  identical flags, one CleanArgs
                           ▼
                    Args::resolve
                           │
                           ▼
              Mode::Clean { intent, .. }
                           │
                    scan() per root
                           │
                           ▼
              plan(&tree, &CleanOptions)  ─── decides, per candidate,
                           │                  *where it goes*
              ┌────────────┴────────────┐
              │                         │
    Intent::Preview            Intent::Removing
              │                         │
              ▼                         ▼
      render::clean            confirm-tier gate
      (nothing happens)                 │
                                        ▼
                                  apply(&plan)
                              trash batch + purge batch
```

Everything the plan will do is **in the plan**. `apply` no longer takes a
`Removal`; it reads one off each candidate. That is what lets `preview` print
exactly what `clean` does, rather than a description of it maintained separately.

### Design Decisions

| # | Decision | Chosen | Rationale | Alternatives |
|---|----------|--------|-----------|--------------|
| P1 | Preview vs clean | **Two verbs**, identical flags | A flag that decides whether a command is destructive is a flag that gets forgotten in both directions. The verb is the intent | Keep `--apply`; add `--dry-run` |
| P2 | `clean` with no flags | **Removes**, to the trash | The verb says so. The guard that mattered — refusing while confirm-tier remains — is kept; the ceremonial one goes | Prompt when stdin is a tty |
| P3 | The confirm-tier refusal | **Stays**, exit 1 | It is a property of the *plan*, not of the arguments, so clap could never have enforced it. It is also the only remaining thing between a typo and losing something that does not regenerate | Drop it with `--apply` |
| P4 | Where a candidate goes | A **third tier**, not a separate `purge` key | `purge` is only ever wanted where `trash` already is — "so cheap it needs no confirmation" and "so cheap it needs no undo" are the same claim. As two fields, `purge = true` on a `confirm` rule is a representable state that has to be rejected at load time. As one field it cannot be written | `Rule.purge: bool` validated against `tier`; a `Removal` field per rule |
| P4a | The three names | `purge` · `trash` · `confirm` | All three answer **one** question — what `clean` does with this — and "nothing, until you say `--yes`" is an answer of the same kind as the other two. The previous set could not be read that way: `purge` named a destination while `auto` named a ceremony, so the contrast between them resolved on no axis at all | `purge`/`auto`/`confirm`; `none`/`auto`/`confirm` |
| P4b | `Removal` | **Deleted** | It is now a second name for `Tier`: `Removal::Purge` is `Tier::Purge`, `Removal::Trash` is the other two. `apply` already stopped taking one. Keeping a derived name beside its source is what "a colour and a candidate are decided by the same code" exists to prevent | Keep it, derived from `Tier` at the point of removal |
| P4c | `tier = "auto"` | A **config error** naming `trash` | An alias lives for ever. An error costs one edit and stops `clean` from starting on a file the user has not finished reading — which is the safe direction | Accept as a deprecated alias |
| P5 | `--purge` the flag | Overrides every candidate's tier | Flag beats file, as everywhere. A `--purge` that quietly trashed half the plan would be a flag that lies about its own name | Honour per-rule tiers even under the flag |
| P6 | `--allow-dirty` | **Removed**, no replacement key | `requires-clean-repo` is already per rule, which is finer and lives with the rule it guards. A global "off" would be a coarser duplicate — and putting it in the file was rejected before, because a guard disabled invisibly is worse than one disabled per run | Move it into `[clean]` |
| P7 | `--older-than` | **Kept**, on both verbs | It changes *which question is asked*, not how the answer is shown, and it is asked with three different values in a row. Moving it to the file means editing a file to vary a number | Rule-only, as `--allow-dirty` |
| P8 | `-n` on preview/clean | **Removed** | `-d 0` gives the overview it was providing, and does it by grouping rather than truncating. A truncated list of what was deleted hides its own tail | Keep, capping candidates |
| P9 | `-n` on `scan` | **Kept** | It limits *breadth*; `-d` limits depth. On a wide directory neither substitutes for the other, and "top 20" is what a size report is opened for | Remove for symmetry |
| P10 | `-d` numbering | 0 = per rule, 1 = per candidate, 2+ = inside a candidate | Level 0 has to *be* something, or the default does nothing. Grouping by rule is also the answer to "which of my rules is doing this" | 0 = per candidate (today's output), 1+ = inside |
| P11 | `--sort` | Display only; the plan keeps its path order | `CleanPlan.candidates` is path-sorted so two runs over one tree are comparable. Sorting the plan itself would trade that away for a report concern | Sort the plan |
| P12 | `--sort size` ties | Broken by path | Size is not unique — a hundred empty `obj/` share one. Without the tiebreak the same disk state prints in a different order each run | Leave ties to the sort's stability |
| P13 | `--json` | Ignores `-d` and `--sort`, emits the whole plan | A machine-readable output silently shortened by a display flag is the worst kind of shortened | Honour `-d` |
| P14 | `--yes` on `preview` | Accepted, and a no-op but for one line | Preview exists so the same line can be retyped with another verb. A flag set that differs breaks the copy exactly when the user has decided to act | Reject it as meaningless |
| P15 | `--yes` name | Unchanged | `--confirm` reads as "ask me", the opposite of what it does — the worst property a destructive flag can have. `-y` is universal | `--confirm`, `--include-confirm` |
| P16 | Migration | None beyond a hidden `--apply` that errors with guidance | The tool is unpublished; the only scripts are this repository's own. The hazard — a script that said `clean <path>` meaning "show me" — cannot be caught by a flag, since the danger is in its *absence* | Rename the verb so old lines fail loudly |

### Components

**New:**
- `preview` verb; `Intent::{Preview, Removing}` replacing `{DryRun, AboutToApply}`
- `Tier::Purge`, and `Candidate.tier` deciding removal on its own
- `cli/src/render/clean.rs` — depth levels 0/1/2+, `--sort`
- `cli/src/render/json.rs` — a plan encoder beside the tree encoder

**Modified:**
- `core/src/rules.rs` — `Tier::{Purge, Trash, Confirm}`; `Auto` renamed to `Trash`
- `core/src/clean.rs` — `CleanOptions` gains `purge_all`, loses `allow_dirty`
- `core/src/trash.rs` — `apply(&plan, progress)`; `CleanOutcome` splits
- `cli/src/args.rs` — the verb split and the flag set
- `cli/src/main.rs` — dispatch, exit codes
- `cli/src/config/` — the three tier names, `allow-dirty` warned as unknown

**Removed:**
- `--apply`, `--allow-dirty`, `-n` on the cleanup verbs
- `Removal` — subsumed by `Tier` (P4b)

## 3. Tasks

### Task 1: Two verbs, one flag set

- **Goal:** `preview` and `clean` exist, take identical flags, and mean
  different things. `--apply` and `--allow-dirty` are gone.
- **Acceptance Criteria:**
  - [ ] Given `preview <PATH>`, when it runs, then the plan is printed and
        **nothing on disk changes**, whatever flags were passed
  - [ ] Given `clean <PATH>` with a plan of auto-tier candidates only, when it
        runs, then they are removed to the trash without any further flag
  - [ ] Given `clean <PATH>` with a confirm-tier candidate in the plan, when it
        runs without `--safe` or `--yes`, then **nothing is removed**, the reason
        names both remedies, and the exit code is **1**
  - [ ] Given the same with `--yes`, when it runs, then everything is removed
  - [ ] Given the same with `--safe`, when it runs, then the confirm-tier
        candidates are absent from the plan and the rest is removed
  - [ ] Given `clean --apply`, when it is parsed, then it is a usage error whose
        message names `preview` and says `clean` now removes
  - [ ] Given `--allow-dirty` on either verb, when it is parsed, then it is an
        unknown flag
  - [ ] Given `preview --yes`, when it runs, then it is accepted and the report
        omits the "clean will refuse" note
  - [ ] Given `--older-than 90d` on either verb, when it runs, then the `old`
        rule is appended last, as before
- **Tests first (TDD):** integration tests over a temp tree for each exit path;
  a `#[ignore]`d smoke test for the one that really removes; `args` unit tests
  that both verbs resolve to the same `CleanOptions` from the same flags.
- **Key files:** `cli/src/args.rs`, `cli/src/main.rs`, `cli/src/render/clean.rs`,
  `core/src/clean.rs`, `cli/tests/cli.rs`
- **Dependencies:** None
- **Status:** Pending

#### Implementation Notes

`Intent` already exists in `render/clean.rs` and already models the difference;
it is renamed and promoted rather than invented. `Mode::Clean` gains
`intent: Intent` and loses `apply: bool` and `removal: Removal`.

The refusal is the substance of this task. It reads the **plan**, not the
arguments — `clap` cannot express "refuse while the plan holds a confirm-tier
candidate", and that is why this check survives the flag that used to accompany
it.

Exit 1 rather than a code of its own: the command did not do what was asked, and
a tool with no published exit-code contract should not start one for a case a
script can already read from stderr.

### Task 2: The report unfolds by depth

- **Goal:** `-d, --depth <N>` with 0 as the default, and `--sort <name|size>`.
- **Acceptance Criteria:**
  - [ ] Given a plan spanning two rules, when the report is printed with no
        `-d`, then there is **one line per rule** carrying its candidate count,
        its total, and where those candidates are going
  - [ ] Given `-d 1`, when the report is printed, then there is one line per
        candidate, as today
  - [ ] Given `--sort size`, when the report is printed at any depth, then rows
        descend by size, and two rows of equal size are ordered by path
  - [ ] Given no `--sort`, when the report is printed, then rows are ordered by
        name
  - [ ] Given any `--sort` or `-d`, when the plan is inspected, then
        `CleanPlan.candidates` is still ordered by path
  - [ ] Given an empty plan, when the report is printed at any depth, then it
        says so in one line rather than printing an empty grouping
- **Tests first (TDD):** the renderer is a pure function of a `CleanPlan`, so
  every level is a unit test over a hand-built plan; one property test that the
  totals at level 0 equal the sum of the rows at level 1.
- **Key files:** `cli/src/render/clean.rs`, `cli/src/args.rs`
- **Dependencies:** Requires Task 1
- **Status:** Pending

#### Implementation Notes

Level 0's row needs the rule name, which `Candidate.rule` already carries, and a
per-rule total, which is a fold. Nothing new is read from disk.

`--sort` is a display concern and must not touch the plan: `CleanPlan.candidates`
is documented as path-sorted "so two runs over one tree produce identical plans",
and that is worth more than saving a `sort` in the renderer.

The size tiebreak is not pedantry. A `pycache` rule over a large tree produces
hundreds of candidates of identical size, and without it the same disk state
prints in a different order every run, which makes two reports impossible to
diff.

### Task 3: Where a candidate goes is part of the rule

- **Goal:** three tiers, a per-candidate destination, and an outcome that
  reports the two halves separately.
- **Acceptance Criteria:**
  - [ ] Given `tier = "purge"` on a rule, when its candidates are removed, then
        they are **deleted outright**, not trashed
  - [ ] Given `tier = "purge"`, when the plan is previewed, then each such row
        says so and the closing summary never calls them recoverable
  - [ ] Given `tier = "purge"`, when `--safe` is passed, then they are **kept**
        — `--safe` drops what needs confirming, and purge needs none
  - [ ] Given a mixed plan, when `clean` runs, then the outcome reports trashed
        and purged as two totals, and the report prints both
  - [ ] Given `--purge`, when `clean` runs, then **every** candidate is deleted
        outright, whatever its tier
  - [ ] Given a denylisted path, when `--purge` or a purge-tier rule would reach
        it, then it is refused exactly as before — no flag and no rule reaches
        the denylist
  - [ ] Given each of `"purge"`, `"trash"`, `"confirm"` in the file, when it is
        parsed, then it is accepted
  - [ ] Given `tier = "auto"`, when it is parsed, then the error **names
        `trash`** as its replacement, and the run does not start
  - [ ] Given any other unknown tier, when it is parsed, then the error names
        all three
- **Tests first (TDD):** `plan()` unit tests asserting the destination on each
  candidate; a config test per tier value plus one for the renamed one;
  `#[ignore]`d smoke tests in `just smoke-trash` for a mixed run, since only
  those really remove anything.
- **Key files:** `core/src/rules.rs`, `core/src/clean.rs`, `core/src/trash.rs`,
  `core/src/lib.rs`, `cli/src/config/mod.rs`, `cli/src/config/write.rs`,
  `cli/src/render/clean.rs`
- **Dependencies:** Requires Task 1
- **Status:** Pending

#### Implementation Notes

**Three tiers, one field**, and the three names answer one question — *what
does `clean` do with this*:

| `tier` | What `clean` does | Confirmation | `--safe` admits |
|---|---|---|---|
| `purge` | destroys it | none | yes |
| `trash` | moves it to the trash | none | yes |
| `confirm` (default) | nothing, until `--yes` | per-path | no |

That uniformity is the point of the rename. The previous set — `purge`, `auto`,
`confirm` — mixed axes: `purge` named a destination and `auto` named a ceremony,
so the contrast between the two resolved on nothing.

`purge` is `trash` plus "no undo", which is why it is a value of the same field
rather than a second one. As two fields, `purge = true` with `tier = "confirm"`
is writable and has to be rejected at load; as one, it cannot be written.

**`--safe` is restated, not merely re-implemented.** It admits two of the three
now, so "only the regenerable safe-list categories" no longer describes it. What
it does is **drop everything that needs confirming** — a statement that stays
true if a fourth tier is ever added.

**`Removal` is deleted.** It has become a second name for `Tier`, and `apply`
already stopped taking one; partitioning reads `Candidate.tier` directly.
Trashing is still batched — one backend call, because on macOS each is a ~230 ms
`osascript` round-trip — so the implementation partitions once and makes two
batch calls.

`CleanOutcome` splits, because a single `reclaimed` figure over a mixed run does
not say what can be brought back:

```rust
pub struct Reclaimed { pub paths: Vec<PathBuf>, pub bytes: u64 }
pub struct CleanOutcome {
    pub trashed: Reclaimed,
    pub purged: Reclaimed,
    pub failed: Vec<TrashFailure>,
}
```

**The core's own guard.** `Rules::new` cannot receive a contradictory tier, since
there is none to receive. But a `Rule` built programmatically with
`tier: Tier::Purge` is honoured — the type says what it says. The safety comes
from the config surface, where the tier is one word and the word is checked.

### Task 4: `--json` for both verbs

- **Goal:** the whole plan, machine-readable, unaffected by display flags.
- **Acceptance Criteria:**
  - [ ] Given `preview --json`, when it runs, then stdout is a single JSON
        document and **stderr carries everything else**
  - [ ] Given `--json` with `-d 0` and `--sort size`, when it runs, then the
        output is byte-identical to `--json` alone
  - [ ] Given `--json`, when it runs, then every candidate carries its path,
        allocated bytes, rule, tier, destination and `shared` marker
  - [ ] Given `--json` with `--safe` or `--min-size`, when it runs, then the
        output reflects the narrowed plan — those change the plan, not its
        display
  - [ ] Given `clean --json`, when it runs, then the document reports what was
        *done*: the two totals and every failure
  - [ ] Given sizes, when they are encoded, then they are raw byte counts, never
        formatted strings — as `scan --json` already does
- **Tests first (TDD):** parse the output back with `serde_json` and assert on
  the value, never on the text; one test that a display flag cannot change a
  byte of it.
- **Key files:** `cli/src/render/json.rs`, `cli/src/args.rs`, `cli/src/main.rs`
- **Dependencies:** Requires Task 2, Task 3
- **Status:** Pending

#### Implementation Notes

The plan encoder sits beside the tree encoder and shares its rules: raw numbers,
stdout for the document and stderr for everything else — which is what keeps the
pipe clean.

`clean --json` and `preview --json` are different documents: one is a plan, the
other an outcome. Giving them one shape with half the fields null would make
every consumer branch on emptiness to find out which it had.

---

### Task 5: Inside a candidate

- **Goal:** `-d 2` and deeper break a candidate into its contents.
- **Acceptance Criteria:**
  - [ ] Given `-d 2`, when a candidate is a directory, then its immediate
        children are listed beneath it with their sizes
  - [ ] Given `-d 3`, when the same is printed, then two levels are shown
  - [ ] Given `-d` deeper than the tree, when it is printed, then it stops at
        the leaves rather than erroring
  - [ ] Given any depth, when the totals are summed, then they are unchanged —
        depth is display only, and a candidate is always removed whole
  - [ ] Given `--sort size`, when children are printed, then they are ordered by
        the same rule as their parents
- **Tests first (TDD):** unit tests over a hand-built `ScanTree`; one asserting
  that the level-0 total is identical at every depth.
- **Key files:** `cli/src/render/clean.rs`, `core/src/clean.rs`
- **Dependencies:** Requires Task 2
- **Status:** Pending

#### Implementation Notes

The children are already in hand: `clean` builds a full `ScanTree`, and
`ScanNode` carries `children`. What is missing is the link from a `Candidate`
back to its node — `plan()` currently keeps only the path and the size. Either
`Candidate` carries the subtree, or the renderer is handed the tree beside the
plan. **The second**: a `CleanPlan` that owned subtrees would be a plan carrying
1.4 GB of scan result, and `--json` would have to decide whether to serialise it.

Lowest value in this spec and scheduled last, deliberately. A candidate is
removed whole, so the breakdown never changes a decision — it answers "why is
this 4 GB", which is `scan`'s question. It is here because that question is
asked *about* a candidate often enough to be worth one flag value.

## 4. Boundaries

### In Scope
- The `preview` / `clean` split and the flag set both take
- Report depth levels and ordering
- `Tier::Purge` and per-candidate destinations
- `--json` for both verbs

### Out of Scope
- Duplicate detection (v0.6)
- Removal from the TUI — unchanged from v0.4's decision: marking writes a
  *rule*, and removal stays with the verb that has the denylist and the tiers
- Sorting by time. `--sort` takes a value so that `modified` can be added
  without a new flag; it is not implemented here
- Interactive prompts. There are none, and a prompt in a pipe is a hang
- Any published-binary or migration tooling

### Protected Elements (DO NOT CHANGE)
- **The denylist.** No flag, no rule, no tier reaches it — `--purge` included
- `scan`'s flags and output, `--json` shape included
- `core::scan`, `core::detect`, `core::measure` and the TUI
- "The core reads no clock, no environment and no config file"
- `#![deny(unsafe_code)]` with per-function exemptions only

### Constraints
- Anything that really deletes is `#[ignore]`d and run by `just smoke-trash`
- The plan is path-sorted and reproducible between runs
- stdout carries the report, stderr everything else
- MSRV 1.88; `just verify` is the gate

## 5. Codebase Context

### Project Structure

```
core/src/
  rules.rs    Rule, Rules, Tier            ← Tier gains a variant
  clean.rs    plan(), Candidate, CleanPlan ← destination per candidate
  trash.rs    apply(), CleanOutcome        ← two batches, two totals
cli/src/
  args.rs     the verbs and their flags    ← the split
  main.rs     dispatch, exit codes
  config/     the file, and writing it back
  render/
    clean.rs  the report                   ← depth, sort
    json.rs   machine-readable             ← a plan encoder
```

### Conventions
- Failures are data; the core never prints
- No overridable flag carries a clap `default_value` — an explicit `0` has to
  beat the file while an absent flag defers to it
- Precedence is flag > file > built-in default, expressed once in `Args::resolve`
- The config file may only make a cleanup **more** cautious

### Build & Test Commands
- `just verify` — fmt, clippy, Windows clippy, doc, minimal features, tests
- `just smoke-trash` — the `#[ignore]`d tests that really remove
- `just run <ARGS>`

## 7. Open Questions

None. Implementation may start.

*Resolved during drafting:* the three tiers are one field rather than a `purge`
key (P4), and they are named `purge` / `trash` / `confirm` (P4a) — which made
`Removal` redundant (P4b) and `"auto"` a config error (P4c).

*Considered and rejected:* a `--trash` flag, the symmetric counterpart of
`--purge`. The consequence is on record rather than hidden: **a rule marked
`tier = "purge"` has no per-run way back to the trash.** `--safe` is not one —
it admits `purge`. Changing that for a single run means editing the config. The
flag is one clap line if it is ever wanted.

## 8. Implementation Reference

### 8.1 Data Structures

#### `Tier`

```rust
pub enum Tier { Purge, Trash, Confirm }
```

| Value | What `clean` does | Confirmation | `--safe` admits |
|-------|-------------------|--------------|-----------------|
| `Purge` | destroys it | none | yes |
| `Trash` | moves it to the trash | none | yes |
| `Confirm` | nothing, until `--yes` | per-path | no |

`Default` stays `Confirm`: a rule that forgets to say gets the cautious answer.
`Auto` is renamed to `Trash`; `"auto"` in a config file is an error naming its
replacement (P4c).

`Removal` is deleted (P4b) — every use of it was this enum under another name.

### 8.2 Algorithms

#### 8.2.1 Deciding a destination

**Used by:** Task 3

1. `plan()` claims a candidate through `detect`, which names the rule.
2. The candidate's tier is the rule's tier.
3. If `CleanOptions::purge_all`, the tier is `Purge` regardless.
4. `--safe` drops `Confirm` and admits the other two — it removes what needs
   confirming, which is the whole of what it means.
5. The denylist is applied **after** all of the above and is not affected by any
   of it.

**Edge cases:**
- A rule with `tier = "purge"` matched under `--safe`: kept. Purge is a stronger
  claim of regenerability, not a weaker one.
- `--purge` with a plan of only confirm-tier candidates and no `--yes`: the
  refusal happens first, so nothing is destroyed.

#### 8.2.2 The report, by depth

**Used by:** Tasks 2 and 5

```
level 0:  fold candidates by rule → (rule, count, bytes, destinations)
level 1:  one row per candidate
level n:  one row per candidate, then n-1 levels of its ScanNode children
```

Ordering at every level: `--sort name` (default) or `--sort size` descending,
ties broken by path. The plan's own order is untouched.

#### 8.2.3 Applying a mixed plan

**Used by:** Task 3

1. Partition candidates by destination — once, not per item.
2. One batched trash call for the trash group.
3. One removal pass for the purge group.
4. Merge into a `CleanOutcome` whose two halves are never added together by the
   core. The report prints both; whether to sum them is the reader's business.

### 8.3 Validation Rules

| Rule | Condition | Behaviour | Task |
|------|-----------|-----------|------|
| Renamed tier | `tier = "auto"` | Config error naming `trash`; the run does not start | 3 |
| Unknown tier | `tier` is anything else outside the three | Config error naming all three | 3 |
| `allow-dirty` in the file | key present | Warned as unknown, as now | 1 |
| `--apply` passed | flag present | Usage error naming `preview` | 1 |
| Confirm-tier in a `clean` plan | no `--safe`, no `--yes` | Refuse, remove nothing, exit 1 | 1 |
| `--purge` | any plan | Every candidate destroyed; denylist unaffected | 3 |
