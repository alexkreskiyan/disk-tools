# Feature Spec: disk-tools v0.3 — configuration and declarative rules

## 1. Overview

v0.2 shipped a cleanup engine whose knowledge of what is disposable is four
hardcoded categories. A user can neither see what `rust-target` actually matches
nor adjust it — only switch it off.

v0.3 makes that knowledge **data**. Detection rules move into a TOML config file,
the four built-in categories become pre-written rules of the same shape, and a
user can write their own in the same vocabulary. The default config becomes the
tool's own documentation: what is matched, where, and with what confidence.

Two guarantees do not move. The **never-touch denylist stays in code**, beyond
the reach of any flag or file — a configurable denylist is no denylist. And
`scan <PATH>` stays exactly what it was: rules belong to `clean`.

- **Concept:** [2026.07.14-disk-tools.md](../../concepts/2026.07/2026.07.14-disk-tools.md)
- **Predecessor:** [v0.2 detectors and cleanup](2026.07.25-disk-tools-v0.2-detectors-cleanup.md)
- **Cost baseline:** [What detection costs](../../benchmarks/2026.07/2026.07.26-detect-budget.md)

This spec **departs from concept §5 in two places**, both deliberately and both
recorded as decisions with their price: §5 said config would "enable/disable
only, no new deletion rules", and that config would hold no scan roots. v0.3
does both.

## 2. Approach

### Architecture

```
  disk-tools clean [PATH] --config f.toml --min-size 1M
          │
          ▼
  ┌─────────────────────────────────────────────────┐
  │ cli/src/config.rs        NEW                    │
  │   locate()  XDG → ~/.config, %APPDATA%          │
  │   parse()   TOML → ConfigFile (all Option)      │
  │   defaults  the five built-in rules             │
  └───────────────┬─────────────────────────────────┘
                  │ ConfigFile
  ┌───────────────▼─────────────────────────────────┐
  │ cli/src/args.rs::resolve()                      │
  │   merge: flag > file > default                  │
  │   expand ~ / %LOCALAPPDATA% from env::user_dirs │
  └───────────────┬─────────────────────────────────┘
                  │ Vec<Rule>, ScanOptions, CleanOptions
  ┌───────────────▼─────────────────────────────────┐
  │ core                                            │
  │   scan()      unchanged — knows no rules        │
  │   Rules::new(Vec<Rule>) → one GlobSet, prefixes │
  │   detect(&ScanTree, &Rules) → Vec<Detection>    │
  │   plan()      denylist → guard → tier → filters │
  │   apply()     unchanged                         │
  └─────────────────────────────────────────────────┘
```

The core still reads no config file, no clock and no environment. `cli/src/env.rs`
resolves `UserDirs`; `cli/src/config.rs` reads the file; everything reaches the
core as explicit values. That is what keeps every rule testable with a temp
directory standing in for a home.

### Design Decisions

| # | Decision | Chosen | Rationale | Alternatives |
|---|----------|--------|-----------|--------------|
| D1 | Rule expressiveness | Users may write **new** rules, not only toggle built-ins | The default config documents the tool; one vocabulary for both | Concept §5's toggles-only — rejected: a toggle cannot express "node_modules under ~/work, over 10M" |
| D2 | Who sets the tier | The rule, including user rules setting `auto` | User's explicit choice | Force user rules to `confirm` — rejected by the user |
| D3 | `CONFIRM_ONLY_NAMES` | **Removed** | Follows from D2: two hardcoded names contradicting "the rule sets the tier" | Keep as a name-based floor |
| D4 | `root` | **Mandatory in the config schema**; `Option<String>` in the core, where `None` means "wherever the scan goes". `clean` with no PATH walks rule roots | Answers "what do I clean when no target is named". Task 1 narrowed this: rooting the built-ins at `~` would drop all five whenever no home is known and break ~25 v0.2 tests, so the *type* is permissive and Task 2 validates the *file* | Mandatory in the type too — rejected in Task 1; optional everywhere — leaves the no-argument case undefined |
| D5 | Scope of rules | `clean` only | `scan <PATH>` is exploration; requiring a configured rule to scan a directory would break the v0.1 use case | Rules drive scan too |
| D6 | Scan-level excludes | **None.** `excludes` exists only on a rule | Detection runs over the built tree, so no glob matching enters the hot walk at all | `[scan] never-walk` — dropped with D4/D5 |
| D7 | File format | TOML | `serde_yaml` is archived at `0.9.34+deprecated`; its forks last shipped in 2024. `toml` 1.1.3 is active, MIT/Apache-2.0, MSRV 1.85 — exactly ours | YAML via a stale fork; YAML on `yaml-rust2` with hand-written deserialization |
| D8 | Where parsing lives | CLI | `core/src/options.rs` states the core reads no config and no environment | Core-side parsing |
| D9 | Matching strategy | One `GlobSet` over all rules; one `Candidate` per node; prefix-prune by root at directory level | 285 ns/node is the measured budget; per-rule matching multiplies it by rule count | One GlobSet per rule |
| D10 | `min-size` on a rule | Filters the **plan**, does not block the match | A 4 KB `__pycache__` below threshold must stay one skipped candidate, not become a hundred tiny ones once the pass descends into it | Treat as a match condition |
| D11 | Path tokens | `~`, `%LOCALAPPDATA%`, `%APPDATA%`, expanded by the CLI. **An unresolvable token disables the rule** | Preserves `an_unknown_home_matches_no_caches`: unknown home is never "any home" | Fail the whole config; treat as literal |
| D12 | Denylist | Stays in code, unreachable from config or flags, `--purge` included | A configurable denylist is not a denylist | Expose as `[deny]` |
| D13 | Confirm-tier | `require-confirmation` makes `--apply` **refuse**; no interactive prompt. Defaults to **true** with no config, so the behaviour changes for everyone — in the direction the denylist already errs: over-refusing costs a flag, under-refusing costs data | Honours the concept's "never auto-removed" without building stdin/TTY machinery, which is v0.4 territory | A real per-target prompt |
| D14 | `Detection` payload | Rule **name** (`String`) replaces `Category` | Rules are open-ended; an enum cannot name a user's rule | Keep `Category` alongside for built-ins |
| D15 | The clock | `DetectOptions.now: SystemTime`, not `Option` | With per-rule `older-than`, `Age`'s threshold+clock pairing breaks; a non-Option `now` restores "cannot be half-armed" | Keep `Age` per rule |
| D16 | `min-size` for scan | Moves to `[report]`, not `[scan]` | It hides rows and never touches totals — that is the definition of `[report]`. Concept's sketch put it in `[scan]` | Follow the sketch |
| D17 | `purge`, `allow-dirty` | **Not configurable** | A file default would make deletion-without-trash and a disabled git guard invisible | Allow with a warning |
| D19 | Boolean settings | A file may turn one **on**; the command line cannot turn it back off | clap distinguishes only "passed" from "not passed". No criterion needs the inverse — all of them are numeric — and three `--no-…` flags for an unasked requirement is surface without a reason. For `[clean] safe` the one-way direction is also the right one: a file may only make a cleanup more cautious | A `--no-…` counterpart per boolean |
| D20 | `[report] n` and `depth` in the template | Both ship **commented out** | `n = 20` would change what `scan` prints for anyone who ran `config init`; `depth = 0` meant "unlimited" in the file and "the root alone" for the flag — one value, two opposite meanings | Write them, as the concept sketched |
| D18 | `[report]` scope | `scan` only; `clean` always lists **every** candidate | The dry-run list is the confirmation mechanism — a truncated one is approval of what was never shown. `depth` is meaningless for a flat list; `apparent` is unavailable, since `Candidate` carries only `allocated` | Share `[report]` across both verbs |

### Components

**New:**
- `cli/src/config.rs` — location, parsing, built-in defaults, `config init`
- `core/src/rules.rs` — `Rule`, `Rules` (compiled), tier, modifiers

**Modified:**
- `core/src/detect.rs` — `Category`/`CategorySet`/`Age` removed; `detect()` takes `&Rules`
- `core/src/clean.rs` — `is_build_output` replaced by the rule's `requires_clean_repo`; `CONFIRM_ONLY_NAMES` removed; tier comes from the rule
- `cli/src/args.rs` — overridable fields become `Option<T>`; `clean` PATH becomes optional; `config` subcommand
- `cli/src/main.rs` — `run_clean` handles a missing path by walking rule roots
- `cli/src/render/clean.rs` — `fn category(Category) -> &'static str` becomes
  printing the rule's own name; the column widens to the longest name present

**Unchanged, contrary to a first reading:**
- `cli/src/render/json.rs` — `--json` serializes `ScanTree` only and has never
  carried a category. `scan --json` is bit-identical after v0.3; `clean` still
  has no `--json`. The `Detection` change (D14) breaks the **library** API, not
  a wire format.
- `core/Cargo.toml` — `globset`
- `cli/Cargo.toml` — `toml`

## 3. Tasks

### Task 1: Declarative rules replace the hardcoded categories

- **Goal:** Detection becomes a pure function of a rule list, with the four
  shipped categories expressed as five built-in rules whose behaviour is
  bit-for-bit what v0.2 did.
- **Acceptance Criteria:**
  - [x] Given the five built-in rules and any tree, when `detect` runs, then the
        result is identical to v0.2's for that tree — all 21 existing
        `detect.rs` tests pass with only their construction changed
  - [x] Given two rules that both match a node, when `detect` runs, then the
        earlier rule in the list claims it and the later one does not appear
  - [x] Given a rule with `enabled = false`, when `detect` runs, then a later
        rule with `older-than` may still claim the same node
  - [x] Given a rule whose `root` contains an unresolvable token, when the rules
        are compiled, then that rule matches nothing and the others are unaffected
  - [x] Given `includes = ["**/node_modules/"]` and a **file** named
        `node_modules`, when `detect` runs, then it does not match
  - [x] Given a rule with `min-size = "1M"` and a 4 KB match, when `detect` runs,
        then the node is still claimed and not descended into, and the candidate
        is dropped by `plan` and counted in `too_small`
  - [x] Given a rule with `requires-sibling = "Cargo.toml"` and a `target/` with
        no such sibling, when `detect` runs, then it does not match
  - [x] Given a scan root that is itself `target/`, when `detect` runs, then it
        does not match — the root has no siblings
  - [x] Given a node claimed by any rule, when `detect` runs, then its children
        are not visited and produce no further candidates
  - [x] Given `~/Projects` (2.34M nodes), when `bench-phases` runs, then the
        `detect*` figure is **no more than 2× the 667 ms baseline**
- **Tests first (TDD):** every criterion above as a named test; the 21 v0.2 tests
  re-run as a regression suite; a `rules::tests` module for compilation,
  precedence and token resolution.
- **Key files:** `core/src/rules.rs` (new), `core/src/detect.rs`,
  `core/src/clean.rs`, `core/src/lib.rs`, `core/Cargo.toml`
- **Dependencies:** None
- **Status:** Done
- **Handoff:** [2026.07.26-disk-tools-v0.3-config-rules-task-1.md](../../handoffs/2026.07/2026.07.26-disk-tools-v0.3-config-rules-task-1.md)

#### Implementation Notes
- **Data structures:** §8.1
- **Algorithm:** §8.2.1 (compilation), §8.2.2 (the pass)
- **Removal list:** `Category`, `CategorySet`, `Age`, `CONFIRM_ONLY_NAMES`,
  `is_build_output`, `UserDirs::cache_roots`
- **Budget:** 285 ns/node measured; see the benchmark note. Prefix-prune before
  matching, one `Candidate` per node, one `GlobSet` for all rules.

### Task 2: The config file — location, schema, parsing, `config init`

- **Goal:** A TOML file at a platform-appropriate path, parsed into the rule list
  and flag defaults, with a subcommand that writes the built-ins out so they can
  be edited.
- **Acceptance Criteria:**
  - [x] Given `$XDG_CONFIG_HOME` is set, when the config is located, then the
        path is `$XDG_CONFIG_HOME/disk-tools/config.toml`
  - [x] Given `$XDG_CONFIG_HOME` is unset on macOS or Linux, when the config is
        located, then the path is `~/.config/disk-tools/config.toml`
  - [x] Given Windows, when the config is located, then the path is
        `%APPDATA%\disk-tools\config.toml`
  - [x] Given `--config <path>`, when the config is located, then that path is
        used and the platform path is not consulted
  - [x] Given no config file exists, when `clean` runs, then the five built-in
        rules apply and no error is reported
  - [x] Given `--config <path>` naming a file that does not exist, when the tool
        runs, then it exits with a usage error — an explicitly named file that is
        missing is a mistake, unlike an absent default
  - [x] Given a file with a TOML syntax error, when it is parsed, then the tool
        exits non-zero naming the **line number**, and nothing is scanned
  - [x] Given a file with an unknown key, when it is parsed, then a warning names
        the key on **stderr** and parsing continues
  - [x] Given a rule with no `root`, no `includes`, or an empty `includes`, when
        it is parsed, then the tool exits with an error naming the rule
  - [x] Given two rules with the same `name`, when parsed, then the tool exits
        with an error naming the duplicate
  - [x] Given `disk-tools config init`, when it runs, then the built-in rules are
        written to the platform path and the file it wrote parses back to an
        identical rule list
  - [x] Given `config init` and an existing file, when it runs, then it refuses
        rather than overwriting, unless `--force` is given
- **Tests first (TDD):** one test per criterion; location tests drive the
  environment through a seam as `cli/src/env.rs` already does, never the real
  process environment.
- **Key files:** `cli/src/config.rs` (new), `cli/src/args.rs`, `cli/src/env.rs`,
  `cli/Cargo.toml`, `cli/tests/cli.rs`
- **Dependencies:** Requires Task 1
- **Status:** Done
- **Handoff:** [2026.07.26-disk-tools-v0.3-config-rules-task-2.md](../../handoffs/2026.07/2026.07.26-disk-tools-v0.3-config-rules-task-2.md)

#### Implementation Notes
- **Schema:** §8.1. Every field of every section is `Option<T>` in the parsed
  form — absence must be distinguishable from a written default (Task 3).
- **Validation:** §8.3
- **`config init`** writes the same text shown in §8.4, comments included: the
  comments are the point of the feature.

### Task 3: Precedence — flag beats file beats default

- **Goal:** Every overridable setting resolves in one documented order, and a
  written value is distinguishable from an unwritten one.
- **Acceptance Criteria:**
  - [x] Given a config with `[report] n = 5` and no `-n` flag, when args resolve,
        then `n` is 5
  - [x] Given a config with `[report] n = 5` and `-n 10`, when args resolve, then
        `n` is 10
  - [x] Given no config and no flag, when args resolve, then `n` is the built-in
        default — **unlimited**, not 20 (deviated; v0.1 behaviour kept by decision)
  - [x] Given a config with `[report] min-size = "1M"` and the flag
        `--min-size 0`, when args resolve, then `min_size` is 0 — an explicit
        zero must beat the file, which today is indistinguishable from absence
  - [x] Given a config setting a value the CLI has no flag for, when args
        resolve, then the config value is used
  - [x] Given a size or duration string the parser rejects, when the config is
        read, then the error names the key and the offending value
  - [x] Given `[report] n = 5` and a plan of 151 candidates, when `clean` runs,
        then **all 151 are listed** — `[report]` does not reach `clean` (D18)
- **Tests first (TDD):** a table-driven test over (config value, flag value,
  expected) for each overridable setting.
- **Key files:** `cli/src/args.rs`, `cli/src/config.rs`
- **Dependencies:** Requires Task 2
- **Status:** Done
- **Handoff:** [2026.07.26-disk-tools-v0.3-config-rules-task-3.md](../../handoffs/2026.07/2026.07.26-disk-tools-v0.3-config-rules-task-3.md)

#### Implementation Notes
- Fields in `ScanArgs`/`CleanArgs` lose `default_value` and become `Option<T>`;
  defaults are applied by the merge, not by clap. This is the only way `0` can
  mean "the user typed zero".
- `--help` must still show the defaults. Use `default_value_t` only where the
  setting is **not** config-overridable, and document the rest in the help text.

### Task 4: `clean` with no path — rule roots drive the scan

- **Goal:** `disk-tools clean` with no argument does the obvious thing: cleans
  what the rules cover.
- **Acceptance Criteria:**
  - [x] Given rules rooted at `~/a` and `~/b`, when `clean` runs with no path,
        then both trees are scanned and candidates from both appear
  - [x] Given rules rooted at `~/a` and `~/a/b`, when `clean` runs with no path,
        then `~/a` is scanned once and `~/a/b` is not scanned again
  - [x] Given a rule whose `root` does not exist, when `clean` runs with no path,
        then it is reported as skipped and the other roots are still scanned
  - [x] Given `clean ~/a` and a rule rooted at `~/b`, when it runs, then that rule
        contributes nothing — rules are intersected with the path
  - [x] Given `clean ~/a` and a rule rooted at `~`, when it runs, then the rule
        applies within `~/a`
  - [x] Given every rule disabled, when `clean` runs with no path, then it exits
        0 saying there are no enabled rules, and nothing is scanned
  - [x] Given `scan` with no path, when it runs, then it is still a usage error —
        rules do not apply to `scan`
- **Tests first (TDD):** integration tests over temp trees; the root-merging
  logic unit-tested without a filesystem.

## 4. Boundaries

### In Scope
- Declarative rules, TOML config, `--config`, `config init`
- Precedence: flag > file > default
- `clean` with no path
- `require-confirmation` as a refusal

### Out of Scope
- **An interactive per-target prompt** (D13) — v0.4, with the TUI
- **`--json` for `clean`** — carried from v0.2
- **Project-local config and merge rules** — one global file, by concept §5
- **A `--exclude` flag** — excludes are a rule's property
- **Parallelising the walk within one directory** — unrelated, still open

### Protected Elements (DO NOT CHANGE)
- `DENIED_ROOTS` and `denylist()` in `core/src/clean.rs` — content and
  reachability both. No config key, no flag, `--purge` included
- The dual raw/normalised denylist check (`is_denied`)
- `scan <PATH>` behaviour and output, `--json` for `scan` excepted (D14)
- Dry-run as the default; nothing removed without `--apply`
- Trash as the default destination; `--purge` explicit and never described as
  recoverable
- `#![deny(unsafe_code)]` and the four per-function exemptions
- The pipeline order in `plan()`: detect → denylist → guard → tier → filters

### Constraints
- The core reads no config file, no clock and no environment
- Never call `canonicalize()`
- MSRV 1.85; `toml` 1.1.3 pins to exactly that, so an MSRV bump upstream breaks CI
- Anything that really deletes is `#[ignore]`d, run by `just smoke-trash`
- Detection must stay within 2× of 667 ms on the reference tree

## 5. Codebase Context

### Project Structure
```
core/src/
  lib.rs        deny(unsafe_code); scan(); re-exports; phase_split diagnostic
  options.rs    ScanOptions — states the core reads no config, no environment
  walk.rs       parallel walk; untouched by v0.3
  detect.rs     the rules — rewritten in Task 1
  rules.rs      NEW — Rule, compiled Rules
  clean.rs      denylist, tiers, totals → CleanPlan
  git.rs        the dirty-repo guard
  paths.rs      same_path, is_within, under_root, normalize_lexically
cli/src/
  args.rs       clap derive; parse_size, parse_duration; Mode
  config.rs     NEW — location, parsing, defaults, init
  env.rs        UserDirs from the environment
  main.rs       verb dispatch
  render/       tree, json, clean, skipped
```

### Conventions
- Failures come back as data; the core never prints
- `#[cfg(windows)]` splits are per function, listed in `lib.rs`
- Tests are named as sentences describing the behaviour, not the function
- Case-insensitive comparison on Windows only — `paths::same_path` is the
  reference; `GlobSet` must follow it via `case_insensitive(cfg!(windows))`
- stdout is the report, stderr is everything else

### Build & Test Commands
- Build: `just build`
- Test: `just test`
- Gate: `just verify` (fmt-check + lint + doc + check-minimal + test)
- Deletion smoke: `just smoke-trash`
- Detection budget: `just bench-phases ~/Projects`

## 6. Testing Strategy

**TDD workflow:** one failing test per acceptance criterion, then the simplest
code that passes, then refactor.

### Per-Task Testing
| Task | What to Test | Test Type |
|------|--------------|-----------|
| 1 | Rule compilation, precedence by list order, token resolution, directory-only globs, nesting, the 21-test regression suite, the 2× budget | Unit + benchmark |
| 2 | Location per platform, parse errors with line numbers, validation, `config init` round-trip | Unit + integration |
| 3 | Merge table over every overridable setting; explicit-zero beats file | Unit |
| 4 | Root merging, nested-root dedup, intersection with PATH, missing root skipped | Unit + integration |
| 5 | Refusal predicate; fixture untouched after refusal | Unit + integration |
| 6 | — | Manual review |

### Test Patterns
- Detection tests build `ScanNode`/`ScanTree` literals — no filesystem
  (`core/src/detect.rs` `fn file`, `fn dir`, `fn tree`)
- Environment-dependent tests go through a seam, never `std::env` directly
  (`cli/src/env.rs::as_path`)
- Anything that really deletes is `#[ignore]`d
- Windows-only and non-Windows behaviour each get their own `#[cfg]` test, so
  the pair documents the decision (`a_windows_cache_root_matches_whatever_its_case`
  / `case_is_significant_off_windows`)

## 7. Open Questions

None. All three raised during drafting were resolved against the code:

- **Do `[report]` settings apply to `clean`'s listing?** **No — `[report]` is
  `scan` only** (D18). `write_candidates` (`cli/src/render/clean.rs:171`) prints
  every candidate today, with no `take(n)`. Applying `n` would mean a user with
  151 candidates sees 20 and then types `--apply`: the dry-run list *is* the
  confirmation mechanism, so truncating it is approving what was never shown.
  `depth` has no meaning for a flat list of non-overlapping paths, and `apparent`
  is not a choice at all — `Candidate` carries only `allocated`.
- **What does `config init` write when `~` cannot be resolved?** The question was
  malformed. `~` is stored **literally** and resolved on every read, so a file
  written on one machine works on another; `init` never resolves it to produce
  valid content. It needs only a destination — and the default destination on
  macOS and Linux is itself under `~`. So this is a *location* failure, already
  specified in Task 2, not a separate decision. With `--config <path>` it always
  succeeds.
- **Is a `--json-version` field needed?** No: `--json` never changes.
  `cli/src/render/json.rs` serializes `ScanTree` alone and has never carried a
  category; `clean` has no `--json`. D14 breaks the library API, not a wire
  format.

## 8. Implementation Reference

### 8.1 Data Structures

#### `Rule` (core, and the config's `[[rules]]`)

| Field | Type | Default | Meaning |
|-------|------|---------|---------|
| `name` | `String` | — | Required, unique. Carried in `Detection` |
| `root` | `PathBuf` | — | **Required** in the file; `"*"` means "wherever the scan goes" and becomes `None` in the core. Tokens expanded by the core from a supplied `UserDirs` |
| `includes` | `Vec<String>` | — | Required, non-empty. Globs relative to `root` |
| `excludes` | `Vec<String>` | `[]` | Globs relative to `root`; walked and counted, but this rule does not claim |
| `requires_sibling` | `Vec<String>` | `[]` | A file that must exist beside the match |

| `older_than` | `Option<Duration>` | `None` | mtime threshold, boundary inclusive |

| `tier` | `Tier` | `Confirm` | Safe default: unstated means ask |
| `enabled` | `bool` | `true` | Skip without deleting the entry |

#### `Rules` (compiled, core-internal)

| Field | Purpose |
|-------|---------|
| `set: GlobSet` | Every enabled rule's includes, in one automaton |

| `excludes: GlobSet` + `owner` | Same, for exclusion |
| `roots: Vec<PathBuf>` | Resolved, for prefix pruning |
| `rules: Vec<Rule>` | The rules themselves, for modifiers after a match |

|-------|-----|-----|

### 8.2 Algorithms

#### 8.2.1 Compiling rules

**Used by:** Task 1

1. For each rule, in file order:
   1. If `enabled` is false, skip.
   2. Expand tokens in `root`. If any token is unresolvable, **skip the rule**
      (D11) — it matches nothing; the others are unaffected.
   3. For each include, join it to the resolved root and add it to the builder
      with `case_insensitive(cfg!(windows))`. Record `owner[pattern] = rule`.
   4. A pattern ending in `/` is marked directory-only; the marker is kept
      alongside, since `GlobSet` itself does not distinguish.
   5. Same for excludes, into a second builder.
2. Build both `GlobSet`s once. A malformed glob is a config error naming the
   rule and the pattern.
3. Collect the resolved roots for pruning.

**Edge cases:**
- All rules disabled or skipped → an empty `Rules` that claims nothing. Not an
  error; `clean` says so and exits 0.
- Two rules matching the same path → the lower rule index wins, which is file
  order, which is the documented precedence.

#### 8.2.2 The detection pass

**Used by:** Task 1

At each node, depth first:

1. If the node is a directory and its path is under **no** rule root and contains
   no rule root, skip the whole subtree.
2. Build one `globset::Candidate` from the node's path.
3. `set.matches(&candidate)` → pattern indices → rule indices. Take the lowest.
4. If none, descend and stop.
5. If the winning pattern is directory-only and the node is not a directory,
   drop that match and consider the next-lowest.
6. Check the winning rule's `excludes` against the same candidate; if excluded,
   consider the next-lowest rule.
7. Check `requires_sibling` against the sibling list, then `older_than` against
   the node's mtime. Either failing drops that rule and moves to the next-lowest.
8. On a win: push `Detection { path, rule: name, allocated }` and **do not
   descend** — the subtree is one candidate.

**Edge cases:**
- Root node: no siblings, so `requires_sibling` cannot be satisfied. Matches
  v0.2's `target_at_the_scan_root_does_not_match`.
- Missing mtime: `older_than` never matches. Absence of evidence is not evidence.
- `min_size` is **not** consulted here (D10).

#### 8.2.3 Choosing what to scan when `clean` has no path

**Used by:** Task 4

1. Collect the resolved roots of all enabled rules.
2. Sort, then drop any root contained in another (`paths::is_within`) — a scan of
   the parent already covers it, and scanning both would double-count.
3. Scan each surviving root. A root that does not exist becomes a `SkippedEntry`,
   not an error.
4. Plan over the union.

With a path given, step 1 becomes "roots intersected with the path": a root
outside it contributes nothing, a root containing it is narrowed to it.

### 8.4 The default config

What `config init` writes.

```toml
# disk-tools configuration.
#
# Precedence: command-line flag > this file > built-in default.
# The never-touch denylist is NOT here and cannot be configured.

[scan]                          # walk behaviour, for `scan <PATH>` only
one-file-system = false

[report]                        # `scan` only; display only, never changes a total.
n         = 20                  # `clean` always lists every candidate — the
depth     = 0                   # 0 = unlimited      dry-run list is what you
min-size  = "0"                 #                    approve with --apply.
apparent  = false

[clean]
require-confirmation = true     # --apply refuses while confirm-tier remains
safe                 = false    # as if --safe were always passed

# Rules. List order is precedence: the first match claims the node, and a
# claimed node is never descended into.

[[rules]]
name                = "rust-target"
root                = "*"
includes            = ["**/target/"]
requires-sibling    = "Cargo.toml"   # without it, target/ is an ordinary directory
requires-clean-repo = true
tier                = "auto"

[[rules]]
name     = "node-modules"
root     = "*"
includes = ["**/node_modules/"]
tier     = "auto"

[[rules]]
name     = "pycache"
root     = "*"
includes = ["**/__pycache__/", "**/*.pyc"]
tier     = "auto"

[[rules]]
name     = "user-caches"
root     = "~"
includes = [".cache/", "Library/Caches/"]   # no ** — the cache root itself only
tier     = "auto"
```

A trailing `/` in `includes` means **directory only**, as in gitignore. That is
why `**/*.pyc` matches files and `**/node_modules/` does not match a file of that
name.
