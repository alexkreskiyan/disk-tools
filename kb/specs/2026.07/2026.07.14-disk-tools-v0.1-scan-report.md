# Feature Spec: disk-tools v0.1 — scan + tree report

## 1. Overview

Build `disk-tools` v0.1: a cross-platform (macOS/Linux/Windows) Rust CLI that scans a directory tree in parallel, measures **real on-disk (allocated) size**, and prints a **dust-style size-sorted tree** of the biggest consumers — or JSON. This is the anchoring capability of a wider disk-utilities suite; cleanup, detectors, config and TUI are later versions.

- **Concept:** [2026.07.14-disk-tools.md](../../concepts/2026.07/2026.07.14-disk-tools.md) (v0.1 row of its Roadmap)
- **Plan:** [2026.07.14-disk-tools-mvp.md](../../plans/2026.07/2026.07.14-disk-tools-mvp.md)
- **Research:** [2026.07.14-technical-rust-disk-cleanup.md](../../research/2026.07/2026.07.14-technical-rust-disk-cleanup.md)

**Codebase state: greenfield.** The repo contains only `.gitignore`, `CLAUDE.md` and `kb/`. No `Cargo.toml`, no `src/`. Everything in this spec is new.

## 2. Approach

### Architecture

```
disk-tools/                          (cargo workspace)
├── core/   disk-tools-core (lib)    ── no logging, no printing, #![deny(unsafe_code)]
│   ├── lib.rs      pub fn scan(&ScanOptions) -> ScanTree
│   ├── options.rs  ScanOptions
│   ├── walk.rs     read_dir + rayon::scope recursion
│   ├── size.rs     allocated (blocks*512 | GetCompressedFileSizeW) + apparent
│   ├── dedup.rs    (dev,inode) / (volume,file_index) → deterministic attribution
│   ├── tree.rs     ScanNode / ScanTree, bottom-up aggregation
│   └── units.rs    size formatting
└── cli/    disk-tools (bin)
    ├── main.rs     args → ScanOptions → core::scan → render
    ├── args.rs     clap derive
    └── render/{tree.rs, json.rs}

flow:  args → ScanOptions → core::scan ─┬─ walk   (parallel, per-directory)
                                        ├─ size   (allocated + apparent)
                                        ├─ dedup  (resolve attribution)
                                        └─ aggregate ⇒ ScanTree { root, skipped }
                                                          ↓
                          CLI: tree-render (bars) │ json    + skipped summary
```

### Design Decisions

| Decision | Chosen | Rationale | Alternatives |
|----------|--------|-----------|--------------|
| Walker | **`std::fs::read_dir` + `rayon::scope` recursion** | True diskus-style. `walkdir` is a *sequential recursive* iterator — it cannot sit inside a parallel recursion (only `max_depth(1)`, i.e. `read_dir` with overhead). Since symlinks are not followed, loop detection is a non-issue; `same_file_system` is a simple `st_dev` check. **`walkdir` drops from dependencies.** | `walkdir` sequential + `rayon` par_iter on sizing (parallelizes the real bottleneck, keeps error-context free); `jwalk` (stale); `ignore` (gitignore hides the artifacts we hunt) |
| Hardlink attribution | **Lexicographically-first path**, resolved in a post-collection pass | "First occurrence" is *nondeterministic under a parallel walk* — dir totals would drift run-to-run and tests would flake. Lex-first is reproducible and still sums to the root total. | First-walked (nondeterministic); dedup only the root total (dir totals then double-count) |
| `--depth` semantics | **Display depth; traversal always full** | Matches real `du --max-depth`, which limits *output*, not counting. Limiting traversal would make directory sizes partial and misleading. | Traversal limit (faster, but sizes lie — would need an explicit "incomplete" marker) |
| `--min-size` semantics | **Display filter** | Same trap as `--depth`: filtering during aggregation would corrupt parent totals. | Aggregation filter (wrong totals) |
| Phase order | collect → resolve dedup → aggregate | Attribution must settle before any sums are computed | Dedup during walk (nondeterministic, see above) |
| serde in core | Behind a `serde` feature flag | Don't force serde on library consumers; the CLI enables it for `--json` | Always-on serde; CLI-side DTO mapping |
| Terminal width | `terminal_size` crate, fixed fallback | Bars must degrade gracefully when piped (non-tty) | Hardcoded width (breaks in wide/narrow terminals) |
| JSON purity | JSON → **stdout**; spinner + skipped summary → **stderr** | Keeps `--json` output machine-parseable when piped | Everything to stdout (corrupts JSON) |
| Progress | `indicatif` **spinner** (unbounded) | Total file count is unknown before the walk finishes | Progress bar (needs a total) |

#### Implementation Notes
- **Implemented in-crate; the `filesize` crate was rejected** *(Task 2)*. Its Windows `file_real_size_fast` calls `std::fs::canonicalize` on every file — violating §4's "never call `canonicalize()`" constraint, adding a syscall to the hot path, and failing outright on RAM disks / network drives / Docker mounts. It also ignores the `metadata` argument on Windows, so the "fast" variant isn't. On Unix it is a one-line wrapper over `metadata.blocks() * 512`. See §8.2.1 for what replaced it.
- Use `DirEntry::file_type()` for dir/file/symlink decisions — **never** `metadata()` speculatively; the single metadata call happens once per real file, where size is needed anyway.

#### Implementation Notes
- CI is a `fail-fast: false` matrix over `ubuntu`/`macos`/`windows-latest` running `just verify` then `just build` as separate steps (`checkout@v4` → `dtolnay/rust-toolchain@stable` with rustfmt+clippy → `Swatinem/rust-cache@v2` → `extractions/setup-just@v4`); push-to-`main` + PR triggers with `concurrency` cancellation. The Windows job compiles out 19 unix-gated tests (83 run vs 102 on macOS, `0 ignored`) and needs no privilege setup.
- **The first CI run went red on Windows and found a real defect in a Task 2 test.** `GetCompressedFileSizeW` returned `10` for a 10-byte file because NTFS keeps a file that small **resident in its MFT record**, owning no cluster. Task 2's third AC ("allocated is a whole number of filesystem blocks") therefore holds on **Unix only**; `allocated_is_block_multiple` now gates the 512-multiple assert to Unix and asserts "whole units **or** exactly the logical length" on Windows.
- `.gitattributes` pins `* text=auto eol=lf` so a CRLF checkout under Git for Windows cannot break `cargo fmt --check`.
- README documents `--one-file-system` as a Unix-only flag: `device_of` returns `None` off Unix, so the flag is silently a no-op there (`core/src/walk.rs:225`).

### 8.2 Algorithms

#### 8.2.1 Per-file sizing
**Used by:** Task 2 — implemented in `core/src/size.rs` as `measure(path, &metadata) -> io::Result<Sizes>`

1. From `DirEntry::file_type()` decide dir / file / symlink — **no** `metadata()` for this.
2. For a regular file, take metadata **once**; hand it to `measure` rather than re-statting.
3. `apparent = metadata.len()`.
4. `allocated`, per platform (no `filesize` crate — see Task 2 notes):
   - **unix:** `metadata.blocks() * 512` via `std::os::unix::fs::MetadataExt`. `st_blocks` is 512-byte units by POSIX definition whatever the filesystem's block size — *not* `blksize()`, which is the preferred I/O chunk.
   - **windows:** `GetCompressedFileSizeW` via `windows-sys` (target-scoped dep), path encoded with `OsStrExt::encode_wide` + NUL, **never canonicalized**. A drive-letter path past `MAX_PATH` first gets the `\\?\` verbatim prefix (`verbatim_if_long`, added in Task 3 — this raw FFI is the one place std's own `maybe_verbatim` doesn't reach). `INVALID_FILE_SIZE` (`u32::MAX`, not exported by `windows-sys`) only means failure when `GetLastError()` is non-zero — it is a legitimate low dword otherwise. Result is `high << 32 | low`. This is the crate's sole `#[allow(unsafe_code)]`.
   - **Known v0.1 limitation** *(Task 3)*: only `C:\`-style drive paths are prefixed. A UNC path (`\\server\share\…`) needs the distinct `\\?\UNC\server\share` form, not a naive `\\?\` prefix; rather than get that subtly wrong, long UNC paths are left unconverted and may hit `MAX_PATH` and become a `SkippedEntry`. Acceptable for a local-disk tool; full UNC support is deferred.
   - **neither:** falls back to `metadata.len()`, so `allocated == apparent` and sparse files look full-size.

**Edge cases:** sparse → `allocated < apparent`; compressed (NTFS/APFS) → `allocated < apparent`; metadata or FFI fails → `io::Error`, which Task 3 turns into a `SkippedEntry`.

**Test fixture gotcha:** on APFS, seek-then-write does **not** produce a sparse file (the whole range is allocated) — `File::set_len` (ftruncate) does. Measured: seek+write → apparent 1048577 / allocated 1052672; `set_len` after a 1-byte write → apparent 4194304 / allocated 4096.

#### 8.2.2 Parallel walk
**Used by:** Task 3 — implemented in `core/src/walk.rs` as `walk(&ScanOptions) -> Walked { entries, skipped }`

1. Stat the root (`symlink_metadata`); record it as an entry and keep its `st_dev`. Unreadable root → one skip, never an error.
2. `read_dir(dir)`; on error → push `SkippedEntry`, return.
3. For each entry: `file_type()` — free, it rides along with `readdir`. Then **one** `DirEntry::metadata()` (does not traverse symlinks). Never a second `stat`.
4. Symlink → record as a (tiny) entry, do **not** follow. No loop detection is needed *because* of that.
5. Directory → if `one_file_system` and its `st_dev` differs from the root's, neither record nor descend (`du -x` behaviour); else recurse.
6. **Record every entry — directories included**, each with its own size from its own metadata. *(Revised in Task 3: the original text recorded only files. Directories occupy a block on ext4 and `du` counts them; on APFS they report `blocks = 0`, so omitting them is invisible on macOS and would have silently failed Task 5's "root total matches `du -sh`" AC on Linux CI only. A directory's total is its own size + Σ children.)*
7. Files also carry an `identity_key` for Task 4 (§8.2.3).
8. Subdirectories recurse via rayon `into_par_iter()`, each returning its own `Walked`; the parent concatenates. *(Revised in Task 3: the original said `rayon::scope`. Same crate, same directory-level parallelism, but results are returned rather than funnelled through a channel — no shared lock.)*

**Edge cases:** permission denied → skipped, continue; vanished mid-walk (`NotFound`) → skipped, continue; **never** `canonicalize()`.

**Windows long paths** *(revised in Task 3; corrected during Task 3 review)*: paths past a length threshold get the `\\?\` verbatim prefix **proactively by length** via `std::path::absolute()` — not by retrying after a failure (guessing which io error means "too long"), and never via the banned `canonicalize()`. The conversion lives in **`size::verbatim_if_long`**, applied just before the `GetCompressedFileSizeW` FFI — *not* in the walk. `std::fs::read_dir`/`symlink_metadata` already prefix internally (`maybe_verbatim`), so the raw FFI in `size` is the one and only place std doesn't cover. An earlier Task 3 draft prefixed the directory path before `read_dir`, which was both redundant (std does it) and unsound (it left the per-file path that actually reaches the FFI unconverted, so a long child name would wrongly become a `SkippedEntry`).

**Verified against reality** (Task 3, APFS): a fixture of 7 files in 4 directories → walk reports 11 entries and 147456 allocated bytes; `find -mindepth 1` counts 10 (+ the root itself = 11) and `du -sk` reports 144 KiB = 147456 bytes. Exact match.

#### 8.2.3 Deterministic hardlink attribution
**Used by:** Task 4
1. During the walk, record each file's identity key — `(st_dev, st_ino)` on Unix. **Windows carries `None`** (see below).
2. After collection, group entries by identity key.
3. For each group with >1 path, sort paths **byte-lexicographically** (`OsStr::cmp`, *not* `Path::cmp` — the latter orders component-wise and disagrees when a component holds a byte below `/`, e.g. `a-b.bin` vs `a/c.bin`; byte order matches `sort(1)`); attribute full bytes — `allocated` **and** `apparent` — to the **first**, zero to the rest. *(Clarified in Task 4.)*
4. Aggregate (§8.2.4) using attributed sizes.

**Windows identity is not available from a walk** *(established in Task 3 — this section previously claimed both keys were "available on `std` `MetadataExt`", which is wrong twice over)*:
- `volume_serial_number()` and `file_index()` are `#[unstable(feature = "windows_by_handle", issue = "63010")]` — nightly only, and the project is stable-only (MSRV 1.85).
- More decisively: even on nightly they would return `None` here. std's `From<WIN32_FIND_DATAW> for FileAttr` — the path `DirEntry::metadata()` takes — hardcodes `volume_serial_number: None, number_of_links: None, file_index: None`. Those fields are `Some` only when the metadata came from an **open handle** (`GetFileInformationByHandle`).
- `number_of_links()` is `None` for the same reason, so we cannot even cheaply identify *which* files have links worth checking.
- The only route is an `open()` per file — the exact syscall cost §8.2.1 exists to avoid.

**Consequence:** hardlinks are **not deduplicated on Windows** in v0.1; they double-count. Documented as a known limitation. **Task 4 may close this cheaply**: hardlinks necessarily share a size, so it need only open handles for files whose sizes collide — a small fraction of any tree, and the same staged trick `fclones` uses.

**Edge cases:** links spanning directories → dir totals still sum to root; ReFS 64-bit file IDs are not unique (out of scope).

#### 8.2.4 Bottom-up aggregation
**Used by:** Task 5
1. Build the node tree from attributed entries.
2. Post-order: `dir.allocated = Σ children.allocated`; same for apparent.
3. Do **not** apply `min_size` / `depth` here — they are display-time filters (§8.2.5).

#### 8.2.5 Tree rendering
**Used by:** Task 7
1. Choose the ranking unit: `apparent` ? apparent : allocated.
2. Sort each node's children by that unit, descending.
3. Walk the tree emitting entries until `n` is exhausted, pruning branches deeper than `depth` and entries below `min_size` — **totals shown are the full-subtree totals**, unaffected by these filters.
4. Each entry shows its **share of its parent** (the parent is 100%) as a percentage and a fixed-width bar whose filled blocks are **right-aligned**. The size + name + bar + percent columns fill the terminal width so the bar/percent block sits flush against the **right edge**; over-long names are truncated with `…` to keep that alignment. A fixed fallback width applies when stdout is non-tty (`terminal_size`). *(Revised in Task 7 per user: bars are parent-relative and right-aligned, not proportional to the largest sibling.)*
