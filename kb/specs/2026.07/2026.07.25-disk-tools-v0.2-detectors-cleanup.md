# Feature Spec: disk-tools v0.2 — detectors + cleanup engine

## 1. Overview

v0.1 answers *what is eating my disk*. v0.2 answers the question the project was
started for: **so you can clean it**. It adds two detectors (junk patterns, old
files) and a cleanup engine behind a new `disk-tools clean` subcommand — dry-run by
default, OS trash on apply, and four independent safety mechanisms.

This is the first version that **deletes files**, which sets the tone for every
decision below: the planning half is a pure function with no filesystem writes, all
failures are data, and the documentation of the safety model is a task in its own
right.

- **Concept:** [2026.07.14-disk-tools.md](../../concepts/2026.07/2026.07.14-disk-tools.md) (§3, §4; Roadmap v0.2)
- **Predecessor:** [v0.1 spec](2026.07.14-disk-tools-v0.1-scan-report.md) — all 11 tasks Done
- **Related plan:** [walk parallelism](../../plans/2026.07/2026.07.25-walk-parallelism.md) — deliberately after v0.2, since detectors touch the same loop

## 2. Approach

### Architecture

```
                    disk-tools (cli)                         disk-tools-core
                    ────────────────                         ───────────────
  disk-tools <PATH>            ──ScanOptions──────────────►  scan()  → ScanTree
  disk-tools clean <PATH> …    ──ScanOptions──────────────►  scan()  → ScanTree
           │                                                        │
           │                   ──CleanOptions─────────────►  clean::plan(&ScanTree, &CleanOptions)
           │                                                        │
           │                                                        │  detect::junk()   siblings via children
           │                                                        │  detect::old()    mtime threshold
           │                                                        │  denylist  → drop
           │                                                        │  tiers     → auto | confirm
           │                                                        │  git guard → drop with reason
           │                                                        ▼
           │                                                    CleanPlan
           │                                          { candidates, reclaimable, excluded }
           ├─ render/clean.rs  ◄─────────────────────────────────────┤   dry-run: flat list + total
           │                                                         │
           └─ --apply  ────────────────────────────────►  clean::apply(&CleanPlan) → CleanOutcome
                                                             trash; per-item failures as data
```

The split that matters: **`plan()` is pure** — it reads a `ScanTree` and produces a
decision, touching nothing. Every rule, every exclusion and every byte of the
reclaimable total is therefore testable without a filesystem that can be damaged.
`apply()` is the only code in the project that removes anything.

### Design decisions

| # | Decision | Chosen approach | Rationale | Alternatives considered |
|---|----------|-----------------|-----------|------------------------|
| D1 | Where detection runs | **Post-aggregate pass over the built `ScanTree`** | `ScanNode.children` already groups siblings, which is exactly what marker-aware rules need (`target/` beside `Cargo.toml`); the hot parallel walk is untouched; the concept explicitly says not to build the `Detector` abstraction early | A `Detector` trait threaded through `walk_dir` — invasive, and the walk has no sibling view to give it |
| D2 | Age signal | **mtime**, via `modified: Option<SystemTime>` on `WalkEntry` and `ScanNode` | `entry.metadata()` is already called per entry (`walk.rs:170`), so this costs **no extra syscall**; on Windows `LastWriteTime` already arrives in the directory listing. atime is rejected: `relatime`/`noatime` are common defaults, which makes it least trustworthy on exactly the caches this rule targets | atime (unreliable); an `--age-by` flag offering both (surface and tests for a rare case) |
| D3 | CLI grammar | clap's default-subcommand pattern: `args_conflicts_with_subcommands`, flattened scan args, `Option<Command>` | `disk-tools <PATH>` keeps working verbatim, which the v0.1 spec's forward-compat note anticipated | Manual first-token sniffing (fragile, breaks `--help`); migrating to `disk-tools scan <PATH>` (breaks the existing surface for no gain yet) |
| D4 | Engine location | `core::clean`, split pure `plan()` / effectful `apply()` | Detectors belong in core; the split makes deletion decisions testable without a filesystem | Cleanup in the CLI — untestable and splits the rules from the model |
| D5 | Failure handling | Per-item outcomes as data, mirroring `SkippedEntry` | The core's standing rule is "never fails, returns what went wrong as data"; a half-completed trash must be reported, never swallowed | `Result` per item — contradicts the existing model and loses the partial-success detail |
| D6 | git-dirty guard | Shell out to `git status --porcelain`; repo present but `git` missing ⇒ treat as dirty | Avoids a heavy dependency for one boolean (`gix` is large, `git2` needs libgit2); conservative when it cannot know | Vendoring a git implementation; skipping the guard when git is absent (unsafe default) |
| D7 | Reclaimable size | Sum of attributed `allocated`, with candidates whose content is **shared outside the candidate** marked and the total stated as an upper bound | Only one of three hardlink cases over-reports (§8.3), and it is detectable from two signals the scan already produces: `nlink` (total names for the inode) and the link groups `dedup` already builds (names visible in this scan). Their difference is the number of links outside the scan — no census needed | A README-only caveat (user cannot see *which* number is soft); a full filesystem link census (expensive, a project of its own) |
| D8 | Safe-list defaults | Built into the binary; no config required to clean | Concept §4: "Categories ship with built-in defaults in v0.2"; config (v0.3) only toggles them | Requiring config first — would make v0.2 unusable standalone |
| D9 | Age rule activation | **Opt-in**: `--older-than <DURATION>`, no default; absent flag means the rule does not run | An always-on age rule would flood the first dry run with confirm-tier entries and bury the safe-list candidates that are the point of the feature. `--safe` ignores them anyway, so a default buys nothing | A 90-day default (noisy); dropping old-file detection from v0.2 (loses a nearly-free capability) |
| D10 | Sharing signals and their portability | **Two signals.** `ScanTree.link_groups` — the paths sharing an inode within this scan, from the groups `dedup` already computes, available on **both** platforms. Plus `links: Option<u32>` — `nlink`, `Some` on Unix, `None` on Windows | The groups answer "is a partner outside this candidate but inside the scan?" exactly, everywhere. `nlink` adds "are there partners outside the scan entirely?" — on Unix the two together are exact. `FILE_ID_BOTH_DIR_INFO` carries no link count, so obtaining `nlink` on Windows would need a handle per file, the exact cost `windows_dir` exists to avoid | `nlink` alone (blind on Windows, and over-marks when both links sit inside the candidate); groups alone (misses links outside the scan); a handle per file on Windows (defeats the v0.1 design) |

#### Implementation Notes
- `entry.metadata()` is already called at `core/src/walk.rs:170`, so both `modified()` and Unix's `nlink()` are free. Do **not** add a second stat, and do **not** open a handle per file on Windows to chase the link count.
- **`link_groups` costs nothing to produce.** `dedup::attribute` (`core/src/dedup.rs:17`) already builds `HashMap<FileId, Vec<usize>>` and discards it after zeroing. Keep the groups of size > 1, mapped to paths. This works on Windows too — `FileId` there is `(volume serial, file id)` from the directory listing.
- **`links` is `None` on Windows and that is deliberate** (D10). The consequence is narrow, not total: `link_groups` still answers "is a partner elsewhere in this scan?" everywhere; only "are there partners outside the scan?" is Unix-only.
- `EntryFacts` (`walk.rs`) already exists as the Windows carrier and needs one more field; `FILE_ID_BOTH_DIR_INFO.LastWriteTime` is already read in `windows_dir.rs` and currently discarded.
- `ScanNode` and `ScanTree` are public and serde-derived. These additions are backward-compatible for JSON consumers, but they **are** a public API change — note it in the handoff.
- A directory's `modified` is its own, never derived from children (see Task 3).
- *(Implemented.)* Two decisions the spec did not anticipate, both now pinned by tests: **`modified` is not serialized by serde's `SystemTime` impl** — that one emits a nested object and refuses any pre-1970 instant, so a single file with a bad clock would fail an entire `--json` run; it goes on the wire as a bare i64 of whole seconds instead. And **directories carry `links: None`**, because a directory's `st_nlink` counts subdirectories, a different quantity that would make Task 4's out-of-scan test fire on every directory.

### Task 3: Detectors — junk patterns and old files

- **Goal:** `core/src/detect.rs`: the four safe-list categories plus an age rule, as pure functions over the built tree.
- **Acceptance Criteria:**
  - [x] Given `target/` with a sibling `Cargo.toml`, when detected, then it matches `rust-target`
  - [x] Given `target/` **without** a sibling `Cargo.toml`, when detected, then it does not match
  - [x] Given `node_modules/`, when detected, then it matches with no marker required
  - [x] Given `__pycache__/` and a loose `*.pyc`, when detected, then both match `pycache`
  - [x] Given a cache directory outside the user's home, when detected, then it does not match `user-caches`
  - [x] Given a matched directory, when detected, then its children are not separately reported
  - [x] Given no `--older-than`, when detected, then **no `old` candidates are produced at all**
  - [x] Given a file older than the age threshold, when detected, then it matches `old`
  - [x] Given a file exactly at the threshold, when detected, then the boundary is inclusive
  - [x] Given a file whose `modified` is `None`, when the age rule runs, then it never matches
  - [x] Given a directory, when the age rule runs, then it is judged by its own mtime, not its children's

  - [ ] `node_modules_matches_without_a_marker`
  - [ ] `pycache_matches_directory_and_loose_pyc`
  - [ ] `user_caches_are_scoped_to_home`
  - [ ] `children_of_a_match_are_not_reported_separately`
  - [ ] `age_rule_is_off_without_the_flag`
  - [ ] `old_file_past_threshold_matches`, `threshold_boundary_is_inclusive`, `directory_age_is_its_own`
  - [ ] `unknown_timestamp_never_matches`
- **Key files:** `core/src/detect.rs`, `core/src/lib.rs`
- **Dependencies:** Requires Task 2
- **Status:** Done
- **Handoff:** [2026.07.25-disk-tools-v0.2-detectors-cleanup-task-3.md](../../handoffs/2026.07/2026.07.25-disk-tools-v0.2-detectors-cleanup-task-3.md)

#### Implementation Notes
- **Marker awareness comes free from the tree.** A rule receives a `&ScanNode` and its parent's `children`, so "is there a `Cargo.toml` beside this `target/`?" is a lookup in a slice the aggregation already built. No walk changes.
- **Do not descend into a match.** Once `node_modules/` matches, its subtree is one candidate — reporting 40,000 children would be both useless and dangerous.
- Categories per concept §4: `rust-target`, `node-modules`, `pycache`, `user-caches`. `user-caches` matches `~/Library/Caches`, `~/.cache`, `%LOCALAPPDATA%\Temp` — **user-scoped only**, never their system counterparts (that is the denylist's job in Task 4, but the rule itself must not match them either).
- See §8.2.1 and §8.2.2 for the rule algorithms.
- **The age rule is opt-in** (D9): with `older_than == None` it produces nothing. That is why its first acceptance criterion is the *absence* of output — the default path must be provably quiet.
- *(From Task 2.)* `modified` is `Option<SystemTime>` and **`None` means unknown** — never "old", never "new". A directory's value is already its own rather than its children's, so the rule needs no special case for that.
- *(Implemented.)* Three points §8.2 left open, settled here:
  1. **A disabled category still lets the age rule claim the node.** "Not already claimed by a junk rule" (§8.2.2 step 1) means claimed by an *enabled* one — turning `node-modules` off says "do not treat this as junk", not "never mention it". An ancient `node_modules` then surfaces as `Old`, which is confirm-tier and so needs per-item confirmation. Pinned by `a_disabled_category_can_still_be_claimed_by_age`.
  2. **The no-descend rule extends to age matches.** §8.2.1 step 5 states it only for junk. Without it an old directory full of old files would yield a candidate for each, and Task 4's total — a plain sum of `allocated` — would count the same bytes repeatedly, since a directory's `allocated` already covers its subtree.
  3. **`now` and the threshold travel together** in one `Age` value, so a threshold cannot be set without an instant to measure it from. Both are inputs: the core consults no clock, exactly as it consults no environment.

### Task 4: Plan — denylist, tiers, reclaimable size

- **Goal:** `clean::plan(&ScanTree, &CleanOptions) -> CleanPlan`, a pure function that writes nothing.
- **Acceptance Criteria:**
  - [x] Given `/System`, `/Library/Caches` (no tilde), `~/Library/Application Support` or `%APPDATA%`, when planning, then they are never candidates whatever else matched
  - [x] Given a `venv/` or `.venv/`, when planning, then it is confirm-tier, never auto
  - [x] Given a safe-list category match, when planning, then it is auto-tier
  - [x] Given an old-file match, when planning, then it is confirm-tier
  - [x] Given `--safe`, when planning, then only auto-tier candidates are included
  - [x] Given a plan, when totalled, then reclaimable equals the sum of attributed `allocated` over its candidates
  - [x] Given a candidate containing a file whose link group has a member **outside** that candidate, when planned, then the candidate is marked `shared` and the total is reported as an upper bound
  - [x] Given a candidate whose hardlinks all sit **inside** it, when planned, then it is **not** marked — deleting it does free those bytes
  - [x] Given a file whose `links` exceeds its link-group size, when planned, then the candidate is marked — a link exists outside the scan entirely
  - [x] Given a candidate with no multi-link content, when planned, then it is not marked and the total is exact
  - [x] Given `links == None` (Windows) and an out-of-scan link, when planned, then the candidate is not marked — the gap is in the signal, not the content
  - [x] Given the same tree twice, when planned, then the two plans are identical including ordering
  - [x] Given a tree where nothing matches, when planned, then the plan is empty and reclaimable is 0
  - [x] Given `plan()` on any input, when it returns, then no filesystem write has occurred

#### Implementation Notes
- *(Resolved in Task 4.)* Task 1 deferred a decision to here: `plan()` would land inside the feature that gates `trash`, though planning needs nothing from it. **The module was split** — `core/src/clean.rs` holds the pure planning half and is always compiled; `core/src/trash.rs` holds removal and is the only thing behind the feature, now named **`trash`** rather than `clean` (a feature called `clean` that gated only removal would misdescribe itself). `--no-default-features` therefore means "scan and plan, but cannot remove", which is coherent and enforced by `just check-minimal`.
- **Denylist beats every rule.** It is applied last and unconditionally; no flag overrides it. `--allow-dirty` relaxes the git guard only (Task 5), never this.
- Note the tilde distinction from the concept: `~/Library/Caches` is a **candidate**, `/Library/Caches` is **denied**. Same for the Windows pair.
- Ordering must be deterministic — sort candidates by path, as `tree::aggregate` already does for children, since the walk order is nondeterministic.
- **Two signals, one question** (D10). "Would deleting this candidate actually free its bytes?" decomposes into:
  1. *Is a partner link elsewhere in this scan, outside the candidate?* — answered exactly by `ScanTree.link_groups`, **on both platforms**.
  2. *Are there partners outside the scan entirely?* — `links > group.len()`. Unix only.

  On Unix the two together are exact. On Windows only the first applies, so a link into, say, a pnpm store outside the scanned tree goes undetected. That is a gap in the signal, never a statement about the content, and the report must not imply otherwise.
- *(From Task 2.)* Three properties of `link_groups` this task can rely on rather than re-establish: it is **already sorted** — groups by their first path, paths within a group by raw bytes — so a plan built from it is deterministic without sorting again; the **first path in each group is the keeper**, the one still carrying the bytes, which is what makes "is a partner outside this candidate?" answerable from the group alone; and **`links == None` is not `1`** — on Windows every entry is `None`, and reading that as "one name, unshared" would claim a total is exact when it is merely unknown.
- *(From Task 4.)* Two things the implementation settled that the spec did not state. **`CleanOptions` embeds `DetectOptions`** rather than restating `older_than` and `categories`, since Task 3 folded `older_than` + `now` into an `Age` and added `user_dirs`. And **the denylist is expressed root-relative** — component sequences anchored at the filesystem root — so `Windows` protects a system on `D:` as well as on `C:`; it is also not `#[cfg]`-gated per platform, because over-denying costs one cleanable directory while under-denying costs a system one.
- *(From Task 4.)* **`..` must be resolved before comparing.** `Path` never resolves `..` and cannot, so `disk-tools clean /home/me/../../System` would carry the traversal into every node path and walk straight past a literal denylist comparison. `is_denied` checks the raw **and** the lexically-normalised form: normalising alone would *weaken* the check, since `/System/../Users/x` matches `System` literally and stops once resolved.
- **Sanctioned simplification.** If this task runs long, degrade to marking whenever `links > 1`, dropping the group check. It over-marks (a candidate whose links all sit inside it is flagged anyway) and does nothing on Windows — but **no other part of the spec changes**: the model, the report and the upper-bound wording all stay. Take the simplification deliberately rather than inventing a third design under time pressure.

### Task 5: git-dirty guard

- **Goal:** Refuse to clean build output of a project that has uncommitted work.
- **Acceptance Criteria:**
  - [x] Given a build directory whose repository has uncommitted changes, when planning, then it is excluded and the plan states the reason
  - [x] Given a clean repository, when planning, then the build directory is included
  - [x] Given `--allow-dirty`, when planning, then the guard excludes nothing
  - [x] Given a candidate in no repository at all, when planning, then the guard does not apply
  - [x] Given a repository but no `git` binary on `PATH`, when planning, then the candidate is treated as dirty
- **Tests first (TDD):**
  - [ ] `dirty_repo_excludes_the_build_directory_with_a_reason`
  - [ ] `clean_repo_keeps_the_candidate`
  - [ ] `allow_dirty_disables_the_guard`
  - [ ] `path_outside_any_repo_is_unaffected`
  - [ ] `repo_without_git_binary_is_treated_as_dirty`
- **Key files:** `core/src/clean.rs`
- **Dependencies:** Requires Task 4
- **Status:** Done
- **Handoff:** [2026.07.25-disk-tools-v0.2-detectors-cleanup-task-5.md](../../handoffs/2026.07/2026.07.25-disk-tools-v0.2-detectors-cleanup-task-5.md)

#### Implementation Notes
- `git status --porcelain` in the candidate's owning repository; non-empty output means dirty. Find the repository by walking up for a `.git` entry — do **not** call `canonicalize()` (project-wide constraint).
- *(From Task 5.)* Four details the algorithm sketch omits, each of which otherwise leaves a repository **unguarded** — the dangerous direction:
  1. **Anchor the path first.** `Path::ancestors` on a relative path stops at `""`, so `clean target` run from inside a repository never reaches the `.git` above the working directory. `std::path::absolute` fixes it lexically without resolving symlinks.
  2. **Strip `GIT_DIR` and friends from the child's environment.** They override `-C` entirely, so an inherited one — a git hook, an IDE integration — has git answer about a different repository.
  3. **Spell out `--untracked-files=normal`.** `status.showUntrackedFiles = no` in the user's config hides brand-new files, so genuine uncommitted work produces empty output and reads as clean.
  4. **`symlink_metadata`, not `exists()`,** when looking for `.git`: `exists()` follows links and reports `false` for a broken one.
- *(From Task 5.)* The verdict is **memoised per repository** inside one `plan()` call — several candidates commonly share one, and each miss costs a process spawn.
- The guard applies to build-output categories (`rust-target`), where "mid-work" is meaningful. It is not meaningful for `user-caches`; see §8.2.3 for which categories it gates.
- Treating a repository with no `git` binary as dirty is the conservative arm of D6: when the tool cannot know, it does not delete.
- Exclusions are **recorded in the plan with a reason**, not silently dropped — the user needs to know why something they expected is absent.

### Task 6: CLI — `clean` subcommand and dry-run report

- **Goal:** The new grammar, and the report that makes a dry run worth reading.
- **Acceptance Criteria:**

#### Implementation Notes
- **Progress is required, not decoration — and its granularity is fixed by the backend.** Task 1 measured 10,000 files trashing in 443 µs on Linux, ~170 ms on macOS and **3.1 s on Windows** ([note](../../benchmarks/2026.07/2026.07.25-trash-backend.md)). Windows is squarely in the range where a user assumes a hang. But the backend reports no per-file completion, so progress can only advance **per candidate** — show which tree is being removed, never a percentage within one.
- **One failure mode cannot be caught.** `trash` 5.2.6 `unwrap()`s `CoCreateInstance` on its Windows delete path, so a COM failure panics rather than returning. The "partial failure names the survivors" criterion below therefore holds for every failure the backend *reports*, and not for that one. `just smoke-trash` runs in CI on all three platforms as the guard.
- **On macOS, no test can prove the deletion was recoverable** — `~/.Trash` needs Full Disk Access and `trash::os_limited::list()` does not exist there. An automated test can assert only that the original path is gone, which an unrecoverable delete would also satisfy. Linux and Windows can do better if a stronger assertion is wanted.
- Per the concept: **no partial silent delete.** If trashing a tree fails midway, the outcome must say what moved and what did not.
- `apply()` returns `CleanOutcome` (§8.1) — a vector of per-candidate results. It never returns `Result` for the operation as a whole, consistent with D5.
- Deletion tests use `tempfile` fixtures exclusively and skip loudly when the environment has no trash, following the established `chmod 000` fixture pattern.

- **`disk-tools <PATH>` must behave exactly as v0.1.** Its 16 `args.rs` tests and 16 `cli/tests/cli.rs` tests are the contract.

|-------|------|-------------|

### 8.2 Algorithms

#### 8.2.1 Marker-aware junk detection

**Used by:** Task 3

1. Walk the `ScanTree` depth-first from the root.
2. For each node, test each enabled category rule against the node's file name,
   passing the parent's `children` slice so the rule can inspect siblings.
3. `rust-target` matches when the name is `target`, the node is a directory, **and**
   a sibling named `Cargo.toml` exists.
4. `node-modules` matches on the name alone. `pycache` matches `__pycache__`
   directories and `*.pyc` files. `user-caches` matches the three user-scoped cache
   roots only.
5. **On a match, record the node and do not descend into it** — the whole subtree is
   one candidate.
6. On no match, recurse into the node's children.

**Edge cases:**
- `target/` at the scan root with no visible parent: no sibling list, so no marker, so no match. Conservative and correct.
- Nested matches (`node_modules` inside `node_modules`): unreachable, since step 5 stops at the outer one.

#### 8.2.2 Old-file detection

**Used by:** Task 3

0. **If `older_than` is `None`, the rule does not run.** It is opt-in (D9); there is
   no default threshold, and no `old` candidate can exist without the flag.
1. For each node not already claimed by a junk rule, compare `modified` against
   `now - older_than`.
2. Older or exactly equal ⇒ match `old`, confirm-tier.
3. `modified == None` ⇒ never matches. Absence of evidence is not evidence of age.
4. Directories are judged on their own `modified`, not their children's — a
   directory's mtime changes when its entries change, which is the intended signal.

**Why mtime and not atime** (D2): concept §3 offers "atime/mtime", but `relatime`
and `noatime` are widespread mount defaults, and under them atime either lags by a
day or never updates. That makes it least reliable precisely on the cache
directories this rule exists to find — the opposite of what an "unused for N days"
signal needs.

#### 8.2.3 git-dirty guard

**Used by:** Task 5

1. Applies to build-output categories only — `rust-target` in v0.2. Caches and old
   files are unaffected: "mid-work" has no meaning for them.
2. Walk up from the candidate looking for a `.git` entry. No `.git` found ⇒ the
   guard does not apply.
3. `.git` found and no `git` binary on `PATH` ⇒ treat as dirty (conservative).
4. Otherwise run `git status --porcelain` in that repository. Non-empty output ⇒
   dirty ⇒ exclude with reason.
5. `--allow-dirty` skips steps 2–4 entirely.

**Edge cases:**
- `git` present but the repository is corrupt: non-zero exit ⇒ treat as dirty.
- Nested repositories: the nearest `.git` ancestor wins.

### 8.3 Validation Rules

| Rule | Condition | Behaviour | Task |
|------|-----------|-----------|------|
| Denylist | Path is or is under a never-touch root | Never a candidate; no flag overrides | 4 |
| Tilde distinction | `/Library/Caches` vs `~/Library/Caches` | System denied, user-scoped allowed | 3, 4 |
| Virtualenv tier | Name is `venv` or `.venv` | Confirm-tier, never auto | 4 |
| Safe filter | `--safe` set | Confirm-tier candidates excluded | 4 |
| Apply gate | `--apply` absent | Nothing is removed | 6, 7 |
| Age rule off | `older_than == None` | The rule does not run; no `old` candidates | 3, 6 |
| Missing timestamp | `modified == None` | Never matches the age rule | 3 |
| Shared marker | Candidate contains a file linked from outside it — a `link_groups` partner beyond its subtree, or `links > link_group.len()` | Marked `shared`; total labelled an upper bound | 4, 6 |
| Purity | Any call to `plan()` | No filesystem write | 4 |

**Never-touch denylist:** `/System`, Windows system directories, `/Library/Caches`
(no tilde), `~/Library/Application Support`, `%APPDATA%`.

**Reclaimable size and hardlinks.** `dedup::attribute` charges a hardlink group's
bytes to its lexicographically first path. Three cases follow, and only one is
wrong:

| Case | Where the keeper is | Total claims | Deleting actually frees | Verdict |
|------|--------------------|--------------|------------------------|---------|
| Every link inside the candidate | inside | the bytes, once | the bytes | **correct** |
| Keeper inside, another link **outside** | inside | the bytes | nothing — the outside link still holds the inode | **over-reports** |
| Keeper outside, a link inside | outside | 0 (the inside node was zeroed) | nothing | **correct** |

So the total is an **upper bound**, loose only in the middle case. Two signals
locate that case, and between them they need no census (D10):

| Signal | Answers | Available |
|--------|---------|-----------|
| `link_groups` — a partner path outside the candidate's subtree | "shared with somewhere else **in this scan**" | both platforms |
| `links > link_group.len()` | "shared with somewhere **outside the scan**" | Unix only (`links` is `None` on Windows) |

Row 1 alone already separates case 1 from case 2, which is what stops the marker
from firing on a `node_modules` whose internal hardlinks are entirely self-contained.
Row 2 catches the case that matters most in practice — a package manager such as
pnpm hardlinking into a store outside the scanned tree — and that one is invisible
on Windows.

**Platform note:** on Windows a candidate sharing content with a path outside the
scan is not marked. That is a gap in the signal, never a statement about the
content; the report and the README must both say so, or a user comparing macOS and
Windows will draw the wrong conclusion.
