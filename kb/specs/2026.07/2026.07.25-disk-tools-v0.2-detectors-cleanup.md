# Feature Spec: disk-tools v0.2 — detectors + cleanup engine

## 1. Overview

v0.1 answers *what is eating my disk*. v0.2 answers the question the project was
started for: **so you can clean it**. It adds two detectors (junk patterns, old
files) and a cleanup engine behind a new `disk-tools clean` subcommand — dry-run by
default, OS trash on apply, and four independent safety mechanisms.

This is the first version that **deletes files**, which sets the tone for every
decision below: the planning half is a pure function with no filesystem writes, all
failures are data, and the documentation of the safety model is a task in its own
right.

- **Concept:** [2026.07.14-disk-tools.md](../../concepts/2026.07/2026.07.14-disk-tools.md) (§3, §4; Roadmap v0.2)
- **Predecessor:** [v0.1 spec](2026.07.14-disk-tools-v0.1-scan-report.md) — all 11 tasks Done
- **Related plan:** [walk parallelism](../../plans/2026.07/2026.07.25-walk-parallelism.md) — deliberately after v0.2, since detectors touch the same loop

## 2. Approach

### Architecture

```
                    disk-tools (cli)                         disk-tools-core
                    ────────────────                         ───────────────
  disk-tools <PATH>            ──ScanOptions──────────────►  scan()  → ScanTree
  disk-tools clean <PATH> …    ──ScanOptions──────────────►  scan()  → ScanTree
           │                                                        │
           │                   ──CleanOptions─────────────►  clean::plan(&ScanTree, &CleanOptions)
           │                                                        │
           │                                                        │  detect::junk()   siblings via children
           │                                                        │  detect::old()    mtime threshold
           │                                                        │  denylist  → drop
           │                                                        │  tiers     → auto | confirm
           │                                                        │  git guard → drop with reason
           │                                                        ▼
           │                                                    CleanPlan
           │                                          { candidates, reclaimable, excluded }
           ├─ render/clean.rs  ◄─────────────────────────────────────┤   dry-run: flat list + total
           │                                                         │
           └─ --apply  ────────────────────────────────►  clean::apply(&CleanPlan) → CleanOutcome
                                                             trash; per-item failures as data
```

The split that matters: **`plan()` is pure** — it reads a `ScanTree` and produces a
decision, touching nothing. Every rule, every exclusion and every byte of the
reclaimable total is therefore testable without a filesystem that can be damaged.
`apply()` is the only code in the project that removes anything.

### Design decisions

| # | Decision | Chosen approach | Rationale | Alternatives considered |
|---|----------|-----------------|-----------|------------------------|
| D1 | Where detection runs | **Post-aggregate pass over the built `ScanTree`** | `ScanNode.children` already groups siblings, which is exactly what marker-aware rules need (`target/` beside `Cargo.toml`); the hot parallel walk is untouched; the concept explicitly says not to build the `Detector` abstraction early | A `Detector` trait threaded through `walk_dir` — invasive, and the walk has no sibling view to give it |
| D2 | mtime | Add `modified: Option<SystemTime>` to `WalkEntry` and `ScanNode` | `entry.metadata()` is already called per entry (`walk.rs:170`), so this costs **no extra syscall**; on Windows `LastWriteTime` already arrives in the directory listing | A second metadata pass — pure cost for data already in hand |
| D3 | CLI grammar | clap's default-subcommand pattern: `args_conflicts_with_subcommands`, flattened scan args, `Option<Command>` | `disk-tools <PATH>` keeps working verbatim, which the v0.1 spec's forward-compat note anticipated | Manual first-token sniffing (fragile, breaks `--help`); migrating to `disk-tools scan <PATH>` (breaks the existing surface for no gain yet) |
| D4 | Engine location | `core::clean`, split pure `plan()` / effectful `apply()` | Detectors belong in core; the split makes deletion decisions testable without a filesystem | Cleanup in the CLI — untestable and splits the rules from the model |
| D5 | Failure handling | Per-item outcomes as data, mirroring `SkippedEntry` | The core's standing rule is "never fails, returns what went wrong as data"; a half-completed trash must be reported, never swallowed | `Result` per item — contradicts the existing model and loses the partial-success detail |
| D6 | git-dirty guard | Shell out to `git status --porcelain`; repo present but `git` missing ⇒ treat as dirty | Avoids a heavy dependency for one boolean (`gix` is large, `git2` needs libgit2); conservative when it cannot know | Vendoring a git implementation; skipping the guard when git is absent (unsafe default) |
| D7 | Reclaimable size | Sum of attributed `allocated`; the hardlink caveat is **documented, not solved** | The concept defers the link census as an open question; an honest estimate beats a precise-looking wrong number | Full-filesystem link census — expensive, and a project of its own |
| D8 | Safe-list defaults | Built into the binary; no config required to clean | Concept §4: "Categories ship with built-in defaults in v0.2"; config (v0.3) only toggles them | Requiring config first — would make v0.2 unusable standalone |

## 3. Tasks

### Task 1: Trash backend + macOS smoke test

- **Goal:** A thin wrapper over the `trash` crate, and a definitive answer to whether it is usable here at all.
- **Acceptance Criteria:**
  - [ ] Given a file in a temp dir, when trashed, then the original path no longer exists and the call reports success
  - [ ] Given a path that cannot be trashed, when trashed, then the failure comes back as data — never a panic, never a process exit
  - [ ] Given an environment with no desktop trash (CI), when the smoke test runs, then it skips loudly rather than failing
  - [ ] Given a 10,000-file tree, when trashed, then the wall-clock cost is recorded in `kb/`
- **Tests first (TDD):**
  - [ ] `trashing_a_file_removes_the_original` (`#[ignore]` — needs a real trash)
  - [ ] `trash_failure_is_reported_as_data`
  - [ ] `missing_trash_backend_skips_loudly`
- **Key files:** `core/src/clean.rs`, `core/Cargo.toml`, `kb/benchmarks/`
- **Dependencies:** None
- **Status:** Pending

#### Implementation Notes
- **First on purpose.** The concept records a downstream report of a macOS build issue with the `trash` crate and says to smoke-test before relying on it. Every apply path rests on this; if it fails, the whole approach to deletion needs rethinking, and that must surface now rather than at Task 7.
- Wrapper shape: `fn to_trash(path: &Path) -> Result<(), TrashFailure>` where `TrashFailure` carries the path and a reason string — the shape `CleanOutcome` will collect.
- The 10k-file timing answers the concept's warning that trashing a large tree "can be slow or fail on some volumes".

### Task 2: `modified` through the model

- **Goal:** Every entry carries its mtime, at zero syscall cost.
- **Acceptance Criteria:**
  - [ ] Given a file with a known mtime, when scanned, then `ScanNode.modified` equals it
  - [ ] Given `--json`, when emitted, then `modified` appears and an existing consumer still parses the payload
  - [ ] Given a Windows scan, when entries come from the directory listing, then `modified` is taken from `LastWriteTime` with no additional call
  - [ ] Given an entry whose metadata carries no usable timestamp, when scanned, then `modified` is `None` rather than an error
- **Tests first (TDD):**
  - [ ] `modified_matches_the_files_mtime`
  - [ ] `json_carries_modified`
  - [ ] `windows_modified_comes_from_the_listing` (`#[cfg(windows)]`)
  - [ ] `missing_timestamp_yields_none`
- **Key files:** `core/src/walk.rs`, `core/src/tree.rs`, `core/src/windows_dir.rs`, `cli/src/render/json.rs`
- **Dependencies:** None
- **Status:** Pending

#### Implementation Notes
- `entry.metadata()` is already called at `core/src/walk.rs:170`, so `modified()` is free. Do **not** add a second stat.
- `EntryFacts` (`walk.rs`) already exists as the Windows carrier and needs one more field; `FILE_ID_BOTH_DIR_INFO.LastWriteTime` is already read in `windows_dir.rs` and currently discarded.
- `ScanNode` is public and serde-derived. Adding a field is backward-compatible for JSON consumers, but it **is** a public API change — note it in the handoff.
- A directory's `modified` is its own, never derived from children (see Task 3).

### Task 3: Detectors — junk patterns and old files

- **Goal:** `core/src/detect.rs`: the four safe-list categories plus an age rule, as pure functions over the built tree.
- **Acceptance Criteria:**
  - [ ] Given `target/` with a sibling `Cargo.toml`, when detected, then it matches `rust-target`
  - [ ] Given `target/` **without** a sibling `Cargo.toml`, when detected, then it does not match
  - [ ] Given `node_modules/`, when detected, then it matches with no marker required
  - [ ] Given `__pycache__/` and a loose `*.pyc`, when detected, then both match `pycache`
  - [ ] Given a cache directory outside the user's home, when detected, then it does not match `user-caches`
  - [ ] Given a matched directory, when detected, then its children are not separately reported
  - [ ] Given a file older than the age threshold, when detected, then it matches `old`
  - [ ] Given a file exactly at the threshold, when detected, then the boundary is inclusive
  - [ ] Given a directory, when the age rule runs, then it is judged by its own mtime, not its children's
- **Tests first (TDD):**
  - [ ] `rust_target_requires_a_sibling_manifest`, `bare_target_directory_is_not_junk`
  - [ ] `node_modules_matches_without_a_marker`
  - [ ] `pycache_matches_directory_and_loose_pyc`
  - [ ] `user_caches_are_scoped_to_home`
  - [ ] `children_of_a_match_are_not_reported_separately`
  - [ ] `old_file_past_threshold_matches`, `threshold_boundary_is_inclusive`, `directory_age_is_its_own`
- **Key files:** `core/src/detect.rs`, `core/src/lib.rs`
- **Dependencies:** Requires Task 2
- **Status:** Pending

#### Implementation Notes
- **Marker awareness comes free from the tree.** A rule receives a `&ScanNode` and its parent's `children`, so "is there a `Cargo.toml` beside this `target/`?" is a lookup in a slice the aggregation already built. No walk changes.
- **Do not descend into a match.** Once `node_modules/` matches, its subtree is one candidate — reporting 40,000 children would be both useless and dangerous.
- Categories per concept §4: `rust-target`, `node-modules`, `pycache`, `user-caches`. `user-caches` matches `~/Library/Caches`, `~/.cache`, `%LOCALAPPDATA%\Temp` — **user-scoped only**, never their system counterparts (that is the denylist's job in Task 4, but the rule itself must not match them either).
- See §8.2.1 and §8.2.2 for the rule algorithms.
- **Blocked on Open Questions 1 and 2** — atime vs mtime, and the default threshold and flag name.

### Task 4: Plan — denylist, tiers, reclaimable size

- **Goal:** `clean::plan(&ScanTree, &CleanOptions) -> CleanPlan`, a pure function that writes nothing.
- **Acceptance Criteria:**
  - [ ] Given `/System`, `/Library/Caches` (no tilde), `~/Library/Application Support` or `%APPDATA%`, when planning, then they are never candidates whatever else matched
  - [ ] Given a `venv/` or `.venv/`, when planning, then it is confirm-tier, never auto
  - [ ] Given a safe-list category match, when planning, then it is auto-tier
  - [ ] Given an old-file match, when planning, then it is confirm-tier
  - [ ] Given `--safe`, when planning, then only auto-tier candidates are included
  - [ ] Given a plan, when totalled, then reclaimable equals the sum of attributed `allocated` over its candidates
  - [ ] Given the same tree twice, when planned, then the two plans are identical including ordering
  - [ ] Given a tree where nothing matches, when planned, then the plan is empty and reclaimable is 0
  - [ ] Given `plan()` on any input, when it returns, then no filesystem write has occurred
- **Tests first (TDD):**
  - [ ] `denylisted_paths_are_never_candidates` (one case per denylist entry)
  - [ ] `virtualenvs_are_confirm_tier`
  - [ ] `safe_flag_admits_only_auto_tier`
  - [ ] `reclaimable_is_the_sum_of_candidate_allocated`
  - [ ] `plan_is_deterministic_across_runs`
  - [ ] `empty_tree_yields_empty_plan`
- **Key files:** `core/src/clean.rs`, `core/src/lib.rs`
- **Dependencies:** Requires Task 3
- **Status:** Pending

#### Implementation Notes
- **Denylist beats every rule.** It is applied last and unconditionally; no flag overrides it. `--allow-dirty` relaxes the git guard only (Task 5), never this.
- Note the tilde distinction from the concept: `~/Library/Caches` is a **candidate**, `/Library/Caches` is **denied**. Same for the Windows pair.
- Ordering must be deterministic — sort candidates by path, as `tree::aggregate` already does for children, since the walk order is nondeterministic.
- Reclaimable carries a known imprecision; see §8.3 and Open Question 3.

### Task 5: git-dirty guard

- **Goal:** Refuse to clean build output of a project that has uncommitted work.
- **Acceptance Criteria:**
  - [ ] Given a build directory whose repository has uncommitted changes, when planning, then it is excluded and the plan states the reason
  - [ ] Given a clean repository, when planning, then the build directory is included
  - [ ] Given `--allow-dirty`, when planning, then the guard excludes nothing
  - [ ] Given a candidate in no repository at all, when planning, then the guard does not apply
  - [ ] Given a repository but no `git` binary on `PATH`, when planning, then the candidate is treated as dirty
- **Tests first (TDD):**
  - [ ] `dirty_repo_excludes_the_build_directory_with_a_reason`
  - [ ] `clean_repo_keeps_the_candidate`
  - [ ] `allow_dirty_disables_the_guard`
  - [ ] `path_outside_any_repo_is_unaffected`
  - [ ] `repo_without_git_binary_is_treated_as_dirty`
- **Key files:** `core/src/clean.rs`
- **Dependencies:** Requires Task 4
- **Status:** Pending

#### Implementation Notes
- `git status --porcelain` in the candidate's owning repository; non-empty output means dirty. Find the repository by walking up for a `.git` entry — do **not** call `canonicalize()` (project-wide constraint).
- The guard applies to build-output categories (`rust-target`), where "mid-work" is meaningful. It is not meaningful for `user-caches`; see §8.2.3 for which categories it gates.
- Treating a repository with no `git` binary as dirty is the conservative arm of D6: when the tool cannot know, it does not delete.
- Exclusions are **recorded in the plan with a reason**, not silently dropped — the user needs to know why something they expected is absent.

### Task 7: Apply — trash execution with per-item outcomes

- **Goal:** The only task in the project that deletes anything.
- **Acceptance Criteria:**
  - [ ] Given no `--apply`, when run against a real fixture, then nothing has been trashed
  - [ ] Given `--apply`, when run, then each candidate moves to the trash and its original path is gone
  - [ ] Given one candidate that fails, when applied, then the remaining candidates still proceed and the failure is reported per item
  - [ ] Given a partial failure, when it completes, then the exit code is non-zero and the summary names what survived
  - [ ] Given a large tree, when applied, then progress is shown on stderr
- **Tests first (TDD):**
  - [ ] `without_apply_the_fixture_is_untouched` (integration)
  - [ ] `apply_moves_candidates_to_trash` (`#[ignore]` — needs a real trash)
  - [ ] `one_failure_does_not_stop_the_rest`
  - [ ] `partial_failure_exits_non_zero_and_names_survivors`
- **Key files:** `core/src/clean.rs`, `cli/src/main.rs`, `cli/src/render/clean.rs`, `cli/tests/cli.rs`
- **Dependencies:** Requires Tasks 1, 4, 6
- **Status:** Pending

#### Implementation Notes
- Per the concept: **no partial silent delete.** If trashing a tree fails midway, the outcome must say what moved and what did not.
- `apply()` returns `CleanOutcome` (§8.1) — a vector of per-candidate results. It never returns `Result` for the operation as a whole, consistent with D5.
- Deletion tests use `tempfile` fixtures exclusively and skip loudly when the environment has no trash, following the established `chmod 000` fixture pattern.

## 4. Boundaries

### In Scope
- Junk-pattern detection for four safe-list categories with built-in defaults
- Old-file detection by age threshold
- `disk-tools clean <PATH> [--safe] [--apply] [--allow-dirty]`
- Dry-run report with reclaimable total; apply through the OS trash
- Never-touch denylist, two-tier eligibility, git-dirty guard
- `modified` on the public scan model

### Out of Scope
- **Candidate source (b) from concept §4** — "entries a user selects in the report/TUI". Needs the TUI (v0.4). v0.2 covers sources (a) detectors and (c) safe-list.
- Config file and category toggles (v0.3)
- Duplicate detection (v0.5)
- `--json` for `clean` — no consumer yet; scan's JSON is unaffected
- Reclaimable-size link census (see Open Question 3)
- Walk parallelism work ([its own plan](../../plans/2026.07/2026.07.25-walk-parallelism.md), deliberately after v0.2)

### Protected Elements (DO NOT CHANGE)
- **`disk-tools <PATH>` must behave exactly as v0.1.** Its 16 `args.rs` tests and 16 `cli/tests/cli.rs` tests are the contract.
- **`disk-tools-core` never logs or prints.** Detectors and the cleanup engine are core code and stay silent; all prose is the CLI's.
- **`scan()` never fails.** The new `plan()` and `apply()` follow the same rule — outcomes as data.
- **`#![deny(unsafe_code)]`** with per-function exemptions only, all four currently `#[cfg(windows)]` and listed in `core/src/lib.rs`.
- **Never call `canonicalize()`** — including when walking up to find `.git`.
- Display filters (`-n`, `--depth`, `--min-size`) never affect totals.

### Constraints
- Dry-run is the default; nothing is removed without `--apply`
- Deletions go to the OS trash, never `rm`
- The denylist is absolute — no flag overrides it
- Safe-list categories work without any config file
- A partial failure is reported, never silent

### Conventions
- Unit tests in-module (`#[cfg(test)] mod tests`); `cli/tests/cli.rs` only for process-boundary behaviour
- Platform pairs: `#[cfg(unix)]` / `#[cfg(windows)]` bodies of the same function, with the non-implementing arm documented as an honest no-op
- Failures as data (`SkippedEntry`), not `Result`, from core
- Defensive fixtures: a permission test that cannot actually restrict must skip loudly rather than pass vacuously
- `#[ignore = "reason"]` for anything needing privileges, a real mount, or a desktop trash
- The justfile is the single entry point; new operations become recipes
- KB layout `kb/<folder>/<YYYY.MM>/<YYYY.MM.DD>-<slug>.md`

## 6. Testing Strategy

**TDD workflow:** each task is implemented test-first — write a failing test for an
acceptance criterion (red), make it pass simply (green), refactor. No production
code without a failing test driving it.

For this feature there is a second reason: **`plan()` is pure**, so every safety
rule can be driven by tests over hand-built `ScanTree` values with no filesystem
involved. A denylist bug should be caught by a unit test, not by a lost directory.

### 8.2 Algorithms

#### 8.2.1 Marker-aware junk detection

**Used by:** Task 3

1. Walk the `ScanTree` depth-first from the root.
2. For each node, test each enabled category rule against the node's file name,
   passing the parent's `children` slice so the rule can inspect siblings.
3. `rust-target` matches when the name is `target`, the node is a directory, **and**
   a sibling named `Cargo.toml` exists.
4. `node-modules` matches on the name alone. `pycache` matches `__pycache__`
   directories and `*.pyc` files. `user-caches` matches the three user-scoped cache
   roots only.
5. **On a match, record the node and do not descend into it** — the whole subtree is
   one candidate.
6. On no match, recurse into the node's children.

**Edge cases:**
- `target/` at the scan root with no visible parent: no sibling list, so no marker, so no match. Conservative and correct.
- Nested matches (`node_modules` inside `node_modules`): unreachable, since step 5 stops at the outer one.

#### 8.2.2 Old-file detection

**Used by:** Task 3

1. For each node not already claimed by a junk rule, compare `modified` against
   `now - older_than`.
2. Older or exactly equal ⇒ match `old`, confirm-tier.
3. `modified == None` ⇒ never matches. Absence of evidence is not evidence of age.
4. Directories are judged on their own `modified`, not their children's — a
   directory's mtime changes when its entries change, which is the intended signal.

#### 8.2.3 git-dirty guard

**Used by:** Task 5

1. Applies to build-output categories only — `rust-target` in v0.2. Caches and old
   files are unaffected: "mid-work" has no meaning for them.
2. Walk up from the candidate looking for a `.git` entry. No `.git` found ⇒ the
   guard does not apply.
3. `.git` found and no `git` binary on `PATH` ⇒ treat as dirty (conservative).
4. Otherwise run `git status --porcelain` in that repository. Non-empty output ⇒
   dirty ⇒ exclude with reason.
5. `--allow-dirty` skips steps 2–4 entirely.

**Edge cases:**
- `git` present but the repository is corrupt: non-zero exit ⇒ treat as dirty.
- Nested repositories: the nearest `.git` ancestor wins.

### 8.3 Validation Rules

| Rule | Condition | Behaviour | Task |
|------|-----------|-----------|------|
| Denylist | Path is or is under a never-touch root | Never a candidate; no flag overrides | 4 |
| Tilde distinction | `/Library/Caches` vs `~/Library/Caches` | System denied, user-scoped allowed | 3, 4 |
| Virtualenv tier | Name is `venv` or `.venv` | Confirm-tier, never auto | 4 |
| Safe filter | `--safe` set | Confirm-tier candidates excluded | 4 |
| Apply gate | `--apply` absent | Nothing is removed | 6, 7 |
| Missing timestamp | `modified == None` | Never matches the age rule | 3 |
| Purity | Any call to `plan()` | No filesystem write | 4 |

**Never-touch denylist:** `/System`, Windows system directories, `/Library/Caches`
(no tilde), `~/Library/Application Support`, `%APPDATA%`.

**Reclaimable-size caveat:** `dedup::attribute` assigns a hardlink group's bytes to
its lexicographically first path. If that path is inside the candidate set but
another link is outside it, deleting the candidate frees nothing, yet the total
counts it. The estimate can therefore over-report. Documented, not solved — see
Open Question 3 and concept §Open Questions.
