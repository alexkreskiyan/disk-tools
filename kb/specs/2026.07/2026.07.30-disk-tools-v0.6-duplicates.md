# Feature Spec: disk-tools v0.6 — duplicate detector

## 1. Overview

The last detector in the concept's §3, and the one it calls "most expensive,
deliberately last": files whose **contents** are identical, found by a staged
pipeline so that the expensive stage runs on almost nothing.

Everything before v0.6 answers *what is this and may it go* from a path. A
duplicate cannot be recognised that way — two files are duplicates only of each
other, the question is about a **set**, and the answer is never "remove them all"
but "keep exactly one". That single difference drives every decision below.

- **Concept:** [2026.07.14-disk-tools.md](../../concepts/2026.07/2026.07.14-disk-tools.md) — §3 (detectors), §4 (cleanup engine), Roadmap
- **Predecessor:** [v0.5 — preview + clean](2026.07.29-disk-tools-v0.5-preview-clean.md)

The concept's roadmap numbers this v0.5; the project renumbered when config and
the TUI landed ahead of it. Scope is unchanged.

## 2. Approach

### Architecture

```
        scan(root)                     ScanTree            (v0.1, unchanged)
             │
             ▼
  ┌──────────────────────────────────────────────────────┐
  │ core/src/duplicates.rs           NEW                  │
  │                                                       │
  │  detect(tree, rules) ──► claimed subtrees ──► pruned   │
  │  1  eligible files      apparent > 0, ≥ min_size       │
  │  2  group by apparent   singletons die here (free)     │
  │  3  re-stat survivors   regular file? size unchanged?  │
  │  4  xxh3-128 prefix     first 16 KiB, skipped if the   │
  │                         file is not bigger than that   │
  │  5  blake3 full         only for groups still ≥ 2      │
  │  6  keeper per group    Keep policy, keep_in wins      │
  └──────────────────────────────────────────────────────┘
             │  Duplicates { groups, skipped }
             ▼
  ┌──────────────────────────────────────────────────────┐
  │ core/src/clean.rs      plan_duplicates()      EXTENDED │
  │   denylist (absolute) · min_size · --safe · --purge    │
  │   every candidate: tier = Confirm, duplicate_of = Some │
  └──────────────────────────────────────────────────────┘
             │  CleanPlan  (the same type v0.5 removes from)
             ├──────────────► render::dup      (preview, --json)
             └──────────────► trash::apply     (clean)
```

One walk, one plan type, one removal path. `apply` is not touched at all: the
plan already says where each candidate goes, which is exactly the property v0.5
was built for.

### Design Decisions

| Decision | Chosen | Rationale | Alternatives |
|---|---|---|---|
| CLI shape | `--dup` on `preview` / `clean` | A third verb that also deletes would undo v0.5's consolidation — one function resolves both verbs so their flag sets cannot drift, and one `apply` removes. `--dup` inherits `--json`, `--yes`, `--purge` and the denylist for free | A `dup` verb with its own `--remove`; a report-only `dup` verb |
| What `--dup` does | **Replaces** the candidate source: content instead of rules | Two candidate models in one report have no common unit — rules yield tiered directories, duplicates yield groups of files with a keeper. Never mixed means the report is always coherent | Additive (`--dup` adds duplicate candidates to the rule plan) |
| Keeper | The earliest **creation** time (`--keep oldest-created`), degrading | The original is the file that existed first, and a copy is a new inode with a new creation time. Modification time cannot say that alone: `cp -p`, `rsync` and unpacking an archive all carry the original's mtime onto the copy. Byte-lexicographic order was tried first and rejected on live data — it keeps `IMG (1).jpg` over `IMG.jpg` | Byte-first path (deterministic but arbitrary); oldest mtime |
| When a date is missing | A member without it never wins; a group where **no** member has it falls back to the other date, then to the path, and **says so** per group | Linux without `statx` birth times has no creation time at all. "Kept the oldest" and "kept the first path" are different claims about the same run, and a report that conflates them is worse than one that admits the degradation — the same rule the TUI's `created` sort already follows | Treat unknown as the epoch (hands the keeper to whichever file the platform was quiet about); refuse to run |
| Keeper override | `--keep first\|oldest-created\|newest-created\|oldest-modified\|newest-modified`, plus `--keep-in <PATH>` (repeatable) | One flag, one flat list: no dependency between flags and nothing to ignore silently. `--keep-in` is the one users reach for — "keep whatever is under ~/Photos, remove the copies elsewhere" — and it beats `--keep`, which then only breaks ties inside the winning root | `--keep` + a second `--keep-by created\|modified`; three values with the direction fixed |
| Where the dates come from | The `symlink_metadata` the pass already makes | It re-stats every contested member anyway, to keep symlinks and changed files out of a removal. Both dates ride along on that call, so choosing by creation time costs nothing and **`ScanNode` never grows a field** the scan would otherwise carry for every node of every run | A `created` field on `ScanNode` (memory on every scan, a new `--json` key) |
| Rule-claimed subtrees | Pruned, always | `node_modules` and `target/` are duplicate farms, and removing one file out of one is how you break a tree that should have gone wholesale. Not a flag: there is no good reason to want it, and a flag that only ever causes harm is a trap | A `--include-claimed` escape hatch |
| Tier | Every duplicate is `Confirm` | The concept's own words: duplicates are manual, never auto-removed. `clean --dup` therefore refuses without `--yes`, and `--safe --dup` plans nothing — both fall out of v0.5's machinery with no new rule | A `duplicate` tier; honouring a rule's tier |
| Identity | blake3 over the whole file, no byte-for-byte pass | A 256-bit cryptographic digest; a collision is not a thing that happens. `fclones` relies on the same | A final `memcmp` pass (doubles the read for no reachable gain) |
| Grouping in the plan | `Candidate.duplicate_of: Option<PathBuf>` | The keeper travels **on the candidate**, so `merge()` stays a concatenation. A side table of groups with candidates indexing into it would need renumbering on merge — a bug waiting for the second root | `CleanPlan.groups` + an index on each candidate |
| Default `--min-size` under `--dup` | 1 MiB | Hashing megabytes of dotfiles to reclaim kilobytes is the wrong trade for a disk tool. Flag and `[duplicates] min-size` both override | 0 (fclones' default); 4 KiB |
| Default `--sort` under `--dup` | `size` | With rules a plan is dozens of directories and alphabetical is reviewable; with duplicates it is thousands of groups and only the top matters. Stated in `--help` where the exception lives | `name`, as without `--dup` |
| `--dup` in the config file | **Forbidden**, like `--yes` and `--purge` | A file that silently switched what `clean` removes would be the same defect those two are kept out for. `min-size`, `keep` and `keep-in` are settings and may live there | A `[duplicates] enabled` key |
| Feature gate | `duplicates`, default-on, mirroring `trash` | `just check-minimal` already proves a scan-only consumer compiles without the trash backend; the hashers get the same treatment | Unconditional dependencies |

## 3. Tasks

### Task 1: the pipeline

- **Goal:** `duplicates(&ScanTree, &DuplicateOptions) -> Duplicates` — content-identical groups with a keeper each, deterministic, reading nothing it does not have to.
- **Acceptance Criteria:**
  - [ ] Given two files with identical contents ≥ `min_size`, when the pass runs, then one group comes back holding both, `reclaimable` = the removed copy's `allocated`
  - [ ] Given two files of equal size but differing contents, when the pass runs, then no group comes back
  - [ ] Given two files differing only in the last byte, when the pass runs, then no group comes back — the prefix hash agreed and the full hash must not
  - [ ] Given a hardlinked pair, when the pass runs, then neither path appears: the zeroed twin is not eligible and removing one name frees nothing
  - [ ] Given a file whose content equals one member of a hardlink group, when the pass runs, then the group holds it and the group's live link, and that candidate is later marked `shared` (Task 2)
  - [ ] Given a symlink whose target is a duplicate, when the pass runs, then the symlink is not a member
  - [ ] Given a file that vanishes between the walk and the hash, when the pass runs, then it is absent from every group and present in `skipped`, and the run does not fail
  - [ ] Given a group whose only other member failed to hash, when the pass runs, then the group is dropped — a copy is never proposed for removal against content that could not be read
  - [ ] Given files below `min_size` or of zero length, when the pass runs, then they are never members
  - [ ] Given a subtree a rule claims, when the pass runs, then nothing inside it is a member
  - [ ] Given the same tree twice, when the pass runs, then the groups, their order and their keepers are byte-identical
  - [ ] Given `keep_in = [~/Photos]`, when a group has a member under it, then that member is the keeper whatever `keep` says; with several, the policy decides among those
  - [ ] Given the default rule and a file written first but sorting last, when the pass runs, then the earlier file is the keeper — the path is not what decides
  - [ ] Given a copy carrying the original's mtime, when the pass runs, then `oldest-created` keeps the original and `oldest-modified` keeps the copy — the two dates are different questions
  - [ ] Given one member with no creation time, when the pass runs, then it never wins and `keeper_fell_back` is false
  - [ ] Given a group where no member has a creation time, when `oldest-created` runs, then the earliest **mtime** wins and `keeper_fell_back` is true; with no date at all, the byte-first path wins and it is still true
- **Tests first (TDD):** one per criterion, over `tempfile` trees; determinism asserted by running twice; the "last byte differs" fixture must exceed the 16 KiB prefix or it proves nothing.
- **Key files:** `core/src/duplicates.rs`, `core/Cargo.toml`, `core/src/lib.rs`
- **Dependencies:** None
- **Status:** Done

#### Implementation Notes
- Data structures: §8.1. Algorithm: §8.2.1.
- `blake3` and `xxhash-rust` (feature `xxh3`) behind the crate's `duplicates` feature, default-on.
- Parallelism: `par_iter` over groups at stages 4 and 5, on the same global rayon pool as the walk. Sequential within a file — a 128 KiB buffer, not `read_to_end`: a 40 GiB disk image must not be a 40 GiB allocation.
- Progress: `&(dyn Fn(Hashed<'_>) + Sync)`, mirroring `measure::Finished`. The core still prints nothing.

### Task 2: the plan

- **Goal:** `plan_duplicates(&ScanTree, &Duplicates, &CleanOptions) -> CleanPlan` — the same plan type v0.5 removes from, so `preview` and `clean` keep speaking about one thing.
- **Acceptance Criteria:**
  - [ ] Given a group of three copies, when the plan is built, then two candidates come back and the keeper is in none of them
  - [ ] Given a copy on the denylist, when the plan is built, then it is `Excluded { Denylisted }`, not a candidate — no flag, `--purge` included, changes this
  - [ ] Given a group all of whose copies are denylisted, when the plan is built, then the group contributes no candidates and its keeper is not named as kept
  - [ ] Given any duplicate candidate, when the plan is built, then `tier == Confirm` and `duplicate_of == Some(keeper)`
  - [ ] Given `purge_all`, when the plan is built, then `purge` is true and `tier` is still `Confirm` — a flag about the destination must not cancel a confirmation
  - [ ] Given `safe_only`, when the plan is built, then there are no candidates and `filtered_out` equals the number of copies
  - [ ] Given a copy whose inode has another name in the scan, when the plan is built, then `shared` is true and the report may not promise its bytes
  - [ ] Given `min_size` above a group's size, when the plan is built, then its copies count in `too_small` and not in `candidates`
  - [ ] Given a plan of duplicates, when it is merged with another, then candidates keep their keepers and the totals add
- **Tests first (TDD):** hand-built `Duplicates` values — no filesystem needed for any of it except the hardlink fixture.
- **Key files:** `core/src/clean.rs`, `core/src/lib.rs`
- **Dependencies:** Requires Task 1
- **Status:** Done

#### Implementation Notes
- `Candidate.rule` carries the fixed string `"duplicate"`; §8.3 reserves that name in config so the report can never be ambiguous about where a candidate came from.
- The git guard does not run: it asks about build output regenerating from committed source, which says nothing about a photo. `below_rule_minimum` stays 0 — there is no rule to have a minimum.

### Task 4: the report

- **Goal:** A grouped report that says, per group, what is kept and what goes — and a `--json` shape that says the same.
- **Acceptance Criteria:**
  - [ ] Given a duplicate plan at `-d 0`, when it renders, then each group is one line: the size of a copy, the count, the reclaimable total and the keeper
  - [ ] Given `-d 1` or deeper, when it renders, then each group lists its keeper marked `keep` and every candidate marked `remove`
  - [ ] Given no `--sort`, when it renders, then groups are ordered by reclaimable, largest first; given `--sort name`, by keeper path
  - [ ] Given `Intent::Preview`, when it renders, then the closing line offers the `clean --dup` that would do it, with `--yes` in it

  - [ ] Given groups whose keeper rule degraded, when it renders, then it says how many and to what — never silently
  - [ ] Given a keeper, when it renders at `-d 1`, then the date the rule chose on is shown beside it, so the choice can be checked rather than trusted

  - [ ] Given a removal, when it renders its outcome, then the shape is v0.5's unchanged — trashed / purged / failed are already path-level
  - [ ] Given nothing found, when it renders, then it says so and names the two knobs that most often explain it (`--min-size`, the pruned subtrees)

## 4. Boundaries

### In Scope
- Content-identical **files**, found within one PATH
- Removal through the existing plan and the existing `apply`
- One keeper per group, by policy or by preferred root

### Out of Scope
- **Duplicate directories** — a tree whose every file is duplicated elsewhere. Real, and a different report
- **Several search roots in one run** (`--dup ~/Photos /Volumes/Backup`) — the arg is one optional path for both verbs, and widening it is a change to the whole surface
- **Replacing a duplicate with a hardlink or a clonefile** instead of removing it — the tool's one removal path goes to the trash, and reflinking is a different verb with different failure modes
- **The TUI** — the browser measures directories, and hashing on demand is a separate design
- **Similar-but-not-identical** files (images, audio) — nothing in this project is a perceptual hash
- **A byte-for-byte confirmation pass**

### Protected Elements (DO NOT CHANGE)
- The never-touch denylist and its absoluteness
- `apply` taking no removal mode — the plan says where each candidate goes
- `#![deny(unsafe_code)]` and its four `#[cfg(windows)]` exemptions; **no new one**
- The core reading no clock, no environment, no config, and printing nothing
- `std::path::absolute`, never `canonicalize`
- Identical flag sets on `preview` and `clean`

### Constraints
- MSRV 1.88, edition 2024, three platforms
- Hashing reads real bytes: it is the first thing in this project bounded by disk throughput rather than metadata calls
- Memory must not scale with a file's size

## 8. Implementation Reference

### 8.1 Data Structures

```rust
// core/src/duplicates.rs

/// Which copy survives when several are identical. `OldestCreated` is the
/// default; every date-based rule degrades rather than misleads.
pub enum Keep { First, OldestCreated, NewestCreated, OldestModified, NewestModified }

pub struct DuplicateOptions {
    /// Which rules claim subtrees the pass must not look inside, and the `now`
    /// they need. The rules never *make* a candidate here — they only prune.
    pub detect: DetectOptions,
    /// Apparent bytes. A file smaller than this is not a duplicate, whatever
    /// its content. Zero-length files are excluded at any setting.
    pub min_size: u64,
    pub keep: Keep,
    /// Preferred roots, in order. A group with a member under one keeps that
    /// member, whatever `keep` says; ties inside a root fall back to `keep`.
    pub keep_in: Vec<PathBuf>,
}

pub struct Copy { pub path: PathBuf, pub allocated: u64 }

pub struct DuplicateGroup {
    /// One copy's logical length — the identity the group was grouped on.
    pub apparent: u64,
    pub keeper: PathBuf,
    /// The rule asked for could not be applied here and a weaker one chose.
    pub keeper_fell_back: bool,
    /// The redundant copies, sorted by path bytes. Never empty.
    pub copies: Vec<Copy>,
    /// The sum of `copies`' allocated bytes. Not `apparent * copies.len()`:
    /// two identical files can occupy different amounts on different volumes.
    pub reclaimable: u64,
}

pub struct Duplicates {
    /// Sorted by `reclaimable` descending, then by keeper path bytes.
    pub groups: Vec<DuplicateGroup>,
    /// Anything unreadable, vanished or changed under us — as data.
    pub skipped: Vec<SkippedEntry>,
    pub files_hashed: usize,
    pub bytes_read: u64,
}

pub struct Hashed<'a> { pub path: &'a Path, pub bytes: u64, pub running_total: u64 }

pub fn duplicates(
    tree: &ScanTree,
    options: &DuplicateOptions,
    progress: &(dyn Fn(Hashed<'_>) + Sync),
) -> Duplicates;
```

### 8.2 Algorithms

#### 8.2.1 The staged pipeline

**Used by:** Task 1

1. **Prune.** Run `detect` and collect what it claims. Walk the tree, skipping
   any subtree at or under a claimed path.
2. **Eligible.** Keep files (not directories) with `apparent > 0` and
   `apparent >= min_size`. A hardlink twin was zeroed by `dedup::attribute` and
   fails the first test — which is the whole hardlink-collapse stage, already
   paid for.
3. **Bucket** by `apparent`. Drop buckets of one. Nothing has been read yet.
4. **Re-stat** each survivor with `symlink_metadata`. Drop anything that is not
   a regular file, whose length changed, or that is gone; each gone or unreadable
   path becomes a `SkippedEntry`. Drop buckets that fall below two. **Both dates
   are taken from this call**, which is why a keeper rule about creation time
   costs no extra syscall and no field on `ScanNode`.
5. **Prefix.** For files larger than 16 KiB, xxh3-128 of the first 16 KiB;
   sub-divide each bucket by that digest and drop the singletons. Files not
   larger than the prefix skip this stage — reading them twice to learn what
   stage 6 learns anyway is pure cost.
6. **Full.** blake3 over the whole file, in 128 KiB reads. Sub-divide again;
   drop singletons. A read error here drops that member and, if fewer than two
   remain, the group.
7. **Keeper.** For each surviving group: `keep_in` narrows to the members under
   the first of its roots that any member lies under; the `keep` policy then
   chooses among those. A member without the date asked for never wins; a group
   with none falls back to the other date, then to path bytes, and records
   `keeper_fell_back`. Every other member becomes a `Copy`.
8. **Order.** Groups by `reclaimable` descending, then keeper path bytes;
   copies within a group by path bytes.

**Edge cases:**
- Empty file: excluded at step 2. Removing one frees nothing, and every empty file is "identical" to every other — a group with no reclaim is noise.
- Sparse files: grouped by `apparent`, reclaimed by `allocated`. Two identical sparse files can free different amounts, which is why `reclaimable` sums rather than multiplies.
- A file changed between stage 5 and stage 6: the full hash simply disagrees and the group loses it.
- `keep_in` root that no member lies under: ignored, next root tried.
- A date the platform did not record: unknown never wins. Every member unknown → the other date → path bytes, with `keeper_fell_back` set.
- Two members with the same date: the earlier path wins, so a filesystem too coarse to tell two writes apart still decides the same way twice.

#### 8.2.2 From groups to a plan

**Used by:** Task 2

For each group, for each copy: denylist first (recorded as `Excluded`,
unconditional), then `min_size`, then `safe_only` (counted in `filtered_out`,
since every duplicate is confirm-tier), then a `Candidate` with
`tier = Confirm`, `purge = options.purge_all`,
`shared = the path has another name in the scan`, `duplicate_of = keeper`.

A group left with no candidates disappears — its keeper is not reported as kept,
because nothing is being removed in its name.

### 8.3 Validation Rules

| Rule | Condition | Behavior | Task |
|---|---|---|---|
| PATH required | `--dup` and no path | Error: the rule roots are not a search scope | 3 |
| Flags need the mode | `--keep` / `--keep-in` without `--dup` | Error, not a silent ignore | 3 |
| Reserved rule name | a config rule named `duplicate` | Rejected by name | 3 |
| Mode is not a setting | any `[duplicates]` key that would switch the mode on | Unknown key, warned | 3 |
| Denylist | a copy under a protected root | `Excluded { Denylisted }`; no flag overrides | 2 |
| Confirmation | a duplicate plan and no `--yes` | `clean` refuses, exit 2 — v0.5's rule, unchanged | 3 |
