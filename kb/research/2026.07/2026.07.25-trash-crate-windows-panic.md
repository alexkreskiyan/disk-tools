# Upstream: `trash` 5.2.6 panics on a Windows COM failure

## Why this is written down

`disk-tools` promises that a cleanup reports precisely what moved and what did
not, and that one bad path never aborts the rest. On Windows there is exactly one
failure mode where that promise does not hold, and it is not ours to fix: the
backend panics instead of returning.

This note holds the report, ready to send. **It has not been filed** — that is an
outward-facing action and the decision belongs to the repository owner's account.

- **Repository:** <https://github.com/ArturKovacs/trash>
- **Version examined:** 5.2.6, from
  `~/.cargo/registry/src/index.crates.io-*/trash-5.2.6`
- **Duplicate check:** `gh issue list --repo ArturKovacs/trash --state all` on
  2026-07-25 — nothing about `CoCreateInstance`, `unwrap` or a panic on Windows.

## The finding, verified in the sources

Three call sites, one of them different:

| Line | Function | Handling |
|------|----------|----------|
| `src/windows.rs:42` | `delete_specified_canonicalized` | **`.unwrap()`** |
| `src/windows.rs:186` | `purge_all` | `?` |
| `src/windows.rs:224` | `restore_all` | `?` |

```rust
// src/windows.rs:42
let pfo: IFileOperation = CoCreateInstance(&FileOperation as *const _, None, CLSCTX_ALL).unwrap();
```

So a COM initialisation failure is an `Error` from purge and restore, and a
**panic** from delete.

## Draft issue

> **Title:** Windows: delete path panics on COM failure where purge/restore return an error
>
> In `src/windows.rs`, `delete_specified_canonicalized` unwraps `CoCreateInstance`:
>
> ```rust
> // src/windows.rs:42
> let pfo: IFileOperation = CoCreateInstance(&FileOperation as *const _, None, CLSCTX_ALL).unwrap();
> ```
>
> The same call is fallible in the other two places it appears — `purge_all`
> (line 186) and `restore_all` (line 224) both use `?`. So a COM initialisation
> failure returns an `Error` from those paths and panics from the delete path.
>
> This matters for callers that collect per-item failures and continue: a panic
> aborts the whole run, and the caller cannot report which items were trashed and
> which were not. It is unlikely in a normal desktop session, and plausible in a
> service, a session-0 process, or a restrictive sandbox.
>
> `?` here would make the three consistent. Version: 5.2.6.

## What it costs this project, meanwhile

- `core/src/trash.rs` documents the gap at `move_to_trash`, and the README lists
  it under Limitations. `apply`'s guarantee is stated as holding for every
  failure the backend **reports** — which is honest, and narrower than we would
  like.
- `just smoke-trash` runs on all three platforms in CI, so an environment where
  COM cannot initialise surfaces as a red build rather than as a user's aborted
  cleanup. It has never fired on `windows-latest`, which is evidence the path is
  rare rather than evidence it is safe.
- No wrapper on our side can convert a panic into a `TrashFailure`. Catching it
  with `catch_unwind` was not attempted: the backend would be left in an unknown
  state mid-operation, and reporting "this item failed" after a panic inside a
  COM call is a guess, not a fact.

## If it is ever fixed upstream

Bumping past the fix lets `apply`'s doc comment drop the caveat, and the README's
first Limitations row goes with it. Watch the MSRV at the same time — the crate
currently requires exactly 1.85.0, the same as this project, so the `msrv` CI job
is the early warning for a bump.
