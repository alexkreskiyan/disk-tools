# disk-tools — Development Guide

Supersedes the [2026.07.14 snapshot](2026.07.14-development.md), written before
any code existed.

## Prerequisites

- Rust **1.85** or newer (edition 2024; the MSRV is pinned in the workspace
  manifest and enforced by CI)
- [`just`](https://github.com/casey/just)
- Optional, for benchmarks only: `hyperfine` and `diskus`
  (`cargo install hyperfine diskus` — Homebrew works too when `/opt/homebrew` is
  writable)

## The justfile is the entry point

Add new local operations as recipes rather than as ad-hoc commands. CI calls the
same recipes, so anything added to `verify` is automatically enforced on all three
platforms.

| Recipe | Runs | Notes |
|--------|------|-------|
| `just` | `just --list` | |
| `just build` | `cargo build --workspace` | |
| `just run <ARGS>` | `cargo run -p disk-tools -- <ARGS>` | e.g. `just run ~/Downloads --json` |
| `just release` | `cargo build --release` + prints the binary path | Host target only |
| `just test` | `cargo test --workspace` | |
| `just fmt` / `just fmt-check` | `cargo fmt --all` / `--check` | |
| `just lint` | `cargo clippy --workspace --all-targets -- -D warnings` | Warnings are errors |
| `just check` | `cargo check --workspace --all-targets` | What the MSRV job runs |
| **`just verify`** | `fmt-check` → `lint` → `test` | **The pre-commit gate** |
| `just bench-fixtures <dir>` | `scripts/bench-fixtures.sh <dir>` | ~28 GB, a few minutes |
| `just bench <dir>` | hyperfine over the three fixtures | Needs `hyperfine` + `diskus` |
| `just bench-memory <path> [ARGS]` | `/usr/bin/time -l` (or `-v`) around one scan | Peak RSS |
| `just bench-phases <path>` | An `#[ignore]` diagnostic in the core | Walk / dedup / aggregate split |

`release`, `bench` and `bench-memory` are shell-script recipes (`#!/usr/bin/env bash`
as the first body line). In those, `set shell` does not apply, and `{{DIR}}` is
interpolated textually before the shell parses the line — quote it.

## The loop

```bash
just verify          # before every commit
```

`verify` is `fmt-check` + `lint` + `test`. Formatting failures are the most common
first stumble: run `just fmt` and re-run.

To type-check the Windows code paths from macOS or Linux without running them:

```bash
cargo clippy --workspace --target x86_64-pc-windows-msvc --all-targets -- -D warnings
```

This catches compile errors in `#[cfg(windows)]` bodies the local build skips
entirely. It is not a substitute for CI — the NTFS sizing behaviour now documented
in the README was found by a red Windows job, not by this check.

To check the MSRV locally (the toolchain must be installed):

```bash
cargo +1.85 check --workspace --all-targets
```

## CI

`.github/workflows/ci.yml`, triggered on push to `main` and on every pull request,
with `concurrency` cancelling superseded runs.

| Job | Runner | Steps |
|-----|--------|-------|
| `verify (ubuntu / macos / windows-latest)` | matrix, `fail-fast: false` | checkout → `dtolnay/rust-toolchain@stable` (rustfmt, clippy) → `Swatinem/rust-cache@v2` → `extractions/setup-just@v4` → **`just verify`** → **`just build`** |
| `msrv (1.85)` | ubuntu-latest | same setup with `dtolnay/rust-toolchain@1.85` → **`just check`** |

Two design points:

- **CI calls justfile recipes, never raw cargo.** Local and CI checks cannot
  drift apart.
- **The Windows job needs no privilege setup.** Symlink, hardlink, sparse-file and
  permission fixtures are all `#[cfg(unix)]` and compile out; the one mount-point
  test is `#[ignore]`. Windows runs 83 tests against macOS's 102, with `0 ignored`
  — the difference is compile-time exclusion, not runtime skipping.
- `fail-fast: false` so a red Windows job still reports Linux and macOS.

`.gitattributes` pins `* text=auto eol=lf`: `cargo fmt --check` normalises to LF,
so a CRLF checkout under Git for Windows' default `core.autocrlf=true` would show
a diff on every file.

## Benchmarks

The numbers in the README and
[the benchmark note](../../benchmarks/2026.07/2026.07.25-v0.1-scan-performance.md)
are reproducible from a committed harness:

```bash
just bench-fixtures /tmp/dt-bench    # ~28 GB, a few minutes
just bench          /tmp/dt-bench
just bench-memory   ~/Projects --depth 0
rm -rf /tmp/dt-bench
```

`scripts/bench-fixtures.sh` generates three shapes with a fixed RNG seed, so two
runs produce identical trees:

| Fixture | Shape | Why |
|---------|-------|-----|
| `node_modules/` | 300 packages × 350 files of 1–8 KiB, nested 1–5 deep | Metadata-bound worst case |
| `cache/` | 200 dirs × 100 files of 4 KiB–2 MiB | The mixed middle |
| `media/` | 40 flat files of 200 MiB | Few entries, many bytes |

Files carry real bytes — never `truncate`d into sparse files, which would collapse
`allocated` to ~0 and make the reported sizes meaningless while leaving the walk
timings unchanged. The script refuses a non-empty target directory and never
deletes anything.

**Let the machine settle after generating fixtures.** Writing 28 GB wakes every
indexer and antivirus scanner on the system; timing through that measures them
rather than the scanner. `just bench` reports `min` alongside `mean ± σ` for
exactly this reason.

`just bench` is verbatim the invocation documented in the benchmark note — keep
the two in step or the recorded results stop being reproducible.

## Documentation workflow

`CLAUDE.md` requires that code changes be reflected in documentation. In practice:

- **User-facing behaviour** (flags, output, limitations) → `README.md`
- **Design and invariants** → a new dated snapshot under `kb/architecture/`
- **Workflow** → a new dated snapshot under `kb/guides/`
- **Structure and key concepts index** → `CLAUDE.md`

Run `/document-repository` after significant changes; it writes a fresh dated
snapshot rather than editing history. Feature work goes through `/write-spec` then
`/implement-task`, one task per session, each leaving a handoff under
`kb/handoffs/`.

## Conventions

- Standard Rust: `snake_case` modules, `cargo fmt` defaults, clippy clean with
  warnings as errors.
- Unit tests in-module (`#[cfg(test)] mod tests`), integration tests in
  `cli/tests/`.
- Comments explain **why**, not what — particularly for platform divergences and
  rejected alternatives, several of which look like oversights until the reason is
  written down.
- KB layout: `kb/<folder>/<YYYY.MM>/<YYYY.MM.DD>-<slug>.md`, always under a month
  folder, never with the folder name in the filename.
