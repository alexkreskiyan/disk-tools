# After v0.7: removing from the browser, and what a progress report may claim

The browser is where you *see* what is disposable: every row coloured by what the
rules say, every directory carrying how much of it is reclaimable. Acting on that
meant leaving the screen and retyping the path into `clean`. This is the account
of closing that gap without turning the browser into a file deleter.

## A keypress has no verb

On the command line the confirmation is the verb. You type `clean` yourself, and
that typing *is* the moment of intent — which is why there is no interactive
prompt and no config key for `--yes`.

A keypress has no such moment. `D` is one finger, and the finger does not say
what it meant. So the modal supplies the intent the verb was carrying, and the
question is asked every time.

**The key is not `Backspace`.** Backspace navigates, and a destructive action must
not share a finger with a habit.

### One question, two answers

The first build asked the user to type the word `purge` when the plan destroyed
rather than trashed. It was removed — 169 lines — and both cases collapsed to
`Y` / `N`.

The tier still decides, but it decides **what the modal says**: a plan that
destroys announces itself with a red heading and names every share as destroyed.
The information is the part that matters; the ceremony was not. Making the
agreement harder to type does not make it better informed.

## Only what the rules claim

`D` plans the subtree under the cursor exactly as `clean <that path>` would —
same denylist, same tiers, same git guard. On a row no rule claims it removes
nothing **and says so**, so a key that did nothing cannot be read as a key that
did not register.

The alternative — letting the browser remove whatever is under the cursor — would
make the tiers and the denylist decoration on a general-purpose deleter.

## What progress may honestly claim

Both halves of a removal run on a worker: planning walks a tree and runs a
`git status` per repository, and removing hands a batch to the OS trash, which on
macOS is a ~230 ms round-trip to Finder. Either on the UI thread freezes the one
screen whose point is that it stays responsive. That much was a straightforward
fix. What the progress may then *claim* was not.

`apply` reports each trashed candidate **before** submitting the batch, because
trashing is one backend call for the whole list. So those callbacks mean
*listed*, not *gone*. Purging is per item, and there the count is real.

| | the callback means | the count is |
|---|---|---|
| trash | listed for one batch call | a denominator being filled, then a wait |
| purge | this one is destroyed | the true figure |

A single bar over both would fill to the end and then sit there for exactly as
long as the real work took — lying in the one moment a progress report exists
for. So the modal counts the halves apart and says the waiting part out loud:

```
  Listing for the Trash: 12 of 40
  Handing 40 to the Trash — one call, and it takes as long as it takes
  Destroying: 2 of 3
```

**No key is offered while it runs.** Stopping half way through a batch the OS
already holds is not a promise this can keep, and a key on screen is that promise.

## Tidying belongs where the outcome arrives

Re-reading the listing used to happen where the key was pressed. Once removal
moved to a worker those stopped being the same moment: the disk changes when the
outcome comes back.

Two narrower decisions fell out of it:

- **`Sizer::forget` is called on the one path that was removed from**, and the
  listing is re-requested; `request` skips what it already holds, so exactly one
  walk runs. Forgetting the whole listing stays what the `r` key does — a removal
  is not a reason to re-measure the siblings, which had not changed.
- **The re-read goes through `refresh`, not `arrive`.** `arrive` clears the
  filter, which is right for a move and wrong for standing still.

## Sorting by what would be freed

`f` orders by reclaimable size, which reads a figure that may not be there yet
because the walk has not finished. That is the same failure shape as sorting by
creation time on a platform that never recorded it, and it degrades the same way:
fall back to name, **say so**, and sort an unknown last in either direction.

The difference is that this one corrects itself — `absorb_sizes` re-sorts when a
walk completes, for `Size` and `Cleanable` alike.

## Landed alongside

`*` stopped being a synonym for `**`. globset does not set `literal_separator`
by default, so until this `parent/*/` claimed grandchildren and "the direct
children of this directory" was inexpressible — load-bearing for the aged
package-store rules, whose unit is one crate version or one cache entry. Set once
in `rules::compile`, because both rule kinds compile through it.

## What did not change

The denylist, `apply` taking no removal mode, the plan deciding where each
candidate goes, and the browser's lazy model: it still lists one directory at a
time and still cancels only what the user asks it to and what exit requires.
