# After v0.7: parts, pools, and what a configuration cannot say for itself

v0.7 began as "let the user say where duplicates are looked for" and turned into
a change one level down, in what a rule *is*. This is the account of why, and of
the two things that fell out of it.

## The cross product could not say "or"

A rule used to be a root plus three independent lists, and its meaning was their
cross product. `requires` is matched **all**, so this was unsayable:

> claim `bin/` when a `*.csproj` sits beside it, **or** when a `*.fsproj` does

Listing both markers in one rule demanded both beside the node. Two rules said it
— at the cost of two names, two rows in every report, and two places to keep one
tier in step.

A **part** is the pairing that was missing: a root, its patterns, and the
predicates that qualify them, in one self-contained statement. A rule is then a
name, a consequence, and a list of parts, and a node is claimed when it satisfies
**any** of them.

The boundary between rule and part is not stylistic. Everything deciding
*whether an object qualifies* is in the part, because a part that needed the rule
to be read is not a statement. Everything about the *consequence* is on the rule,
because a tier on a part would make the part a rule and the rule would stop being
the unit the report groups by.

**There is no flat form.** Two spellings of one thing tax everything else: every
example, every error message and every future field would have to answer "and in
the flat form?". Two lines per rule is the cheaper side of that trade.

## The same word, two consequences

Duplicate rules reuse parts, and there they mean something else:

| | a part contributes |
|---|---|
| clean rule | **matchers** — anything satisfying any part is claimed, independently |
| duplicate rule | a **population** — everything satisfying any part is pooled, and duplicates are searched within that pool |

So adding a part to a clean rule adds candidates; adding one to a duplicate rule
can **create groups that did not exist**, because two populations can now pair. A
photo in `~/Photos` and its copy in `~/Downloads` are comparable only if one rule
covers both.

## Pools are exclusive, and that was not a preference

The first design let a file belong to every pool that matched it. That is not an
ambiguity to resolve later; it is a corrupt plan. One pool names a file its
keeper while another lists it for removal, both plans merge, and `apply` wins.

So membership is **exclusive**: the first rule, in list order, whose parts match
a file takes it. Pools are then disjoint by construction, the keeper policy and
the tier are unambiguous without a tie-break rule, and precedence stays the one
thing list order already meant.

**The cost is a silent miss.** Two natural rules — "photos", "downloads" — put a
photo and its copy in different pools, and they are never compared. That is
expressible (one rule, two parts) but the failure of *not* expressing it looks
exactly like a disk with no duplicates.

Which is why the report now states what it searched, always:

```
Searched 2 pools of 4120 files, and copies are only ever compared within one:
  photos  4000 files
  scans    120 files
```

In an empty run that line comes **first**, before the hints about `--min-size`.
It is the only thing that tells "there are none here" from "here was nowhere".

## `--explain`, and the general shape of the problem

Three of the decisions above share a property: the tool knows something the user
cannot see.

- A part whose `~` this machine cannot resolve is **dropped**, silently. That is
  right — refusing to run because a Linux box has no `%LOCALAPPDATA%` would be
  worse — but a rule that matches nothing looks exactly like a rule that is wrong
  about the disk.
- A pool that covers one directory and not its neighbour produces an empty
  report indistinguishable from a clean disk.
- A threshold arrives from a flag or from the file as the same value, and a
  message naming the wrong one sends the user to edit something they never wrote.

`--explain` is the answer to all three, and it exits without walking, reading or
removing anything. Explaining and then acting would make it a log line; the point
of a check is that it happens first. `Rules` now records what it dropped and why,
and `Args::resolve` records where each shown value came from — the same function
that *chooses* the value, so the answer and the explanation cannot disagree.

It also accounts for the flags that decide nothing. A flag passed and never
mentioned reads as a flag ignored, so `-d`, `--sort`, `--json` and `--verbose`
appear under a heading that keeps them in their place — *Shown, not decided* —
with the sentence that matters: a candidate a shallow report does not name is one
`clean` removes anyway.

## What it cost

`Rule` changed shape, and `detect`, `clean`, the config layer and every fixture
followed. `Detection` gained the index of the part that matched, because the tier
is the rule's but `min_size` and `requires-clean-repo` belong to the part, and a
rule with two parts holds two different answers.

Three drops are worth recording because each was caught by a test rather than by
reading:

1. A part that cannot be expressed is dropped and its siblings stand — but a rule
   left with **no** parts must be dropped whole, or its name appears in a list of
   rules that can never match.
2. The pool's keeper policy had been a parameter of the report, one per run.
   With per-rule policies that would label one pool's group with another's basis.
   It moved onto the candidate.
3. `just bench-dup` searched **nothing** for one commit, because the diagnostic
   built its options with `Default` and the new `rules` field defaults to empty.
   It reported success while measuring an empty set — the third time in this
   project that a check has been able to pass without checking. It now prints the
   pools it searched, so the same failure would be visible in its own output.

## What did not change

The denylist, `apply` taking no removal mode, `deny(unsafe_code)` and its four
exemptions, `std::path::absolute` over `canonicalize`, identical flag sets on
`preview` and `clean`, and clean rules pruning the duplicate search — a directory
that goes whole is not a place to remove single files from, whatever the
duplicate rules say.
