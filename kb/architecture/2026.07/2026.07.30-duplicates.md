# After v0.6: a second source of candidates

Every pass before this one answers a question about a **path**: is this a
`target/`, is it old, how big is it. A duplicate is not a property of a file at
all. It is a property of a *set*, the answer is never "remove these" but "keep
exactly one of these", and that single difference is behind most of what follows.

## `--dup` is a flag, and that was the first decision

The obvious shape was a third verb — `disk-tools dup`. It was rejected because
v0.5 had just spent a whole version consolidating the removal path: one function
resolves `preview` and `clean` so their flag sets cannot drift, and one `apply`
does the deleting. A third verb that also deletes reintroduces exactly what was
removed — a second set of flags to keep in step by hand, and a second place that
can be wrong about the trash.

So `--dup` is a **switch of source**, not an additional detector:

```
                     ┌── rules ──────► detect ──► plan ──────────┐
scan(root) ──► tree ─┤                                           ├──► CleanPlan ──► apply
                     └── contents ──► duplicates ──► plan_duplicates ┘
```

The two are **never mixed** in one plan. They have no common unit: rules yield
tiered directories, duplicates yield groups of files with a keeper, and a report
holding both would be about nothing in particular.

Everything downstream of `CleanPlan` — the refusal, the denylist, `--purge`,
`--yes`, the outcome, `apply` — is unaware that duplicates exist. That is the
whole return on v0.5's "the plan says what will happen".

## The funnel, and what it is really buying

| Stage | Reads | Why it is where it is |
|---|---|---|
| eligible files | nothing | the scan already measured them |
| bucket by apparent size | nothing | a unique size is proof of unique content |
| `symlink_metadata` per survivor | one stat | keeps symlinks, changed and vanished files out of a removal |
| xxh3-128 of the first 16 KiB | one block | skipped when the file is not larger than that |
| blake3 over the whole file | everything | the only thing here bounded by the disk |

On one real `~/Downloads`, 61% of eligible files have a unique size and are never
opened; 9% of the eligible bytes are read.
[Measured](../../benchmarks/2026.07/2026.07.30-duplicate-cost.md) — including the
adversarial case, a project tree, where 89% of files share a size with something
and the funnel narrows almost nothing.

**Hardlink collapse turned out to be free.** The concept lists it as a pipeline
stage. `dedup::attribute` has already zeroed every name of an inode but one, and
a zeroed entry fails the first filter — which is not a coincidence to exploit but
the correct answer: removing one name of a hardlinked file frees no bytes. The
stage was never written.

## The keeper rule, and why it changed once

The first implementation kept the byte-lexicographically first path — the rule
`dedup::attribute` already uses to pick which name of a hardlink owns its bytes,
chosen for the same reason: two runs must agree.

It survived exactly one look at real output. On a Telegram export it keeps
`IMG (1).jpg` over `IMG.jpg`, because that is where the alphabet falls. The rule
was defensible and the results were wrong.

What replaced it is **creation time**, because that is the one date copying does
not carry: a copy is a new inode with a new creation time, while `cp -p`, `rsync`
and unpacking an archive all move the *modification* time of the original onto
the copy. `--keep` takes five values in one flat list — no second flag, no
dependency between flags, nothing that can be silently ignored.

Three things came out of that episode and are worth keeping:

1. **A rule whose basis is invisible can only be trusted.** The report now prints
   `(created 4mo)` beside the keeper. The old rule was not wrong because
   lexicographic order is a bad idea; it was wrong because nothing said what it
   had gone on.
2. **The date rides on the re-stat the pass already makes.** `ScanNode` never
   grew a `created` field, so no scan pays memory for a question only this pass
   asks.
3. **Degrade, do not mislead.** `created()` is unrecorded on Linux without
   `statx`. A copy without the date never wins; a group where none has it falls
   back to the other date and then to the path, and every such group is marked.
   "Kept the oldest" and "kept whatever had a date" are different claims.

## Where the keeper lives, and why it is repeated

`Candidate.duplicate_of: Option<Kept>` — the kept path, its date, and whether the
rule held — is carried on **every candidate of a group**, rather than in a table
beside the plan with candidates indexing into it.

The reason is `CleanPlan::merge`. A multi-root run concatenates plans; group
indices would have to be renumbered per plan, and the second root is precisely
where that goes wrong. Repeating a `PathBuf` per candidate is a rounding error
next to a bug in a delete path.

The second return on it: the whole of what the report shows is **inside the
plan**, so `preview` prints exactly what `clean` acts on rather than a second
description kept in step by hand.

## What the report had to say out loud

The duplicate report is the first one in this tool that puts a size next to a
path which is **not** being removed. A reader who has to work that out from the
columns gets it wrong exactly once, and the cost of that once is a deleted
original. Hence a fixed first line — *Each group keeps one copy. The size is what
removing the others frees.* — and `keep` / `remove` spelled as words at `-d 1`.

Two smaller decisions:

- **`--sort` defaults to `size` under `--dup`.** The only default in the CLI that
  depends on another flag. A rule plan is dozens of directories and alphabetical
  order makes it reviewable; a duplicate search returns hundreds of groups and
  the only question asked of that list is which of them are worth acting on.
- **Which report is printed is settled by the mode**, not inferred from the
  plan's contents. An empty `--dup` run has to say *no duplicates found* and name
  the two things that explain it — the floor and the pruned subtrees — which a
  plan with no candidates cannot be told apart from.

## Safety, unchanged and deliberately so

Nothing here relaxes anything:

- Every duplicate is **confirm-tier**. `clean --dup` refuses without `--yes` and
  exits 2; `--safe --dup` plans nothing at all, which is correct, since `--safe`
  means *only what needs no confirmation*.
- The **denylist** applies unchanged, and a refused copy is reported.
- **Rule-claimed subtrees are pruned**, with no flag to turn it off. Removing one
  file out of a `node_modules` breaks a tree that should have gone wholesale, and
  a flag that only ever causes harm is a trap rather than a choice.
- **A file that could not be read is not evidence.** It drops out and is
  reported; if the group falls below two members it disappears.
- `--dup` cannot be set in the config file, and `duplicate` is a reserved rule
  name — one line of a plan must not be able to mean two things, especially when
  a user's rule may say `tier = "purge"` and a duplicate never can.

## One build-level consequence

`blake3` carries `features = ["pure"]`. Its default build assembles x86 sources
through `cc`, which on the Windows target needs `ml64.exe` — unavailable on a Unix
host, so `just lint-windows`, half of the local gate, simply stopped running.
The Rust SIMD paths remain; the disk gives about a fifth of what the hasher does,
so the assembly was never the bound. This is the second time in two versions that
a Windows-shaped fact was invisible until something failed loudly, and it is
recorded in `CLAUDE.md` beside the first.
