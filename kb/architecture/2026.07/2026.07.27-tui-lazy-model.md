# After v0.4: the browser, and why it does not scan

The previous snapshot,
[After v0.3: detection as data](2026.07.26-overview.md), describes the engine
this sits on: the three-phase scan, the rule set, the cleanup plan. Nothing
there changed. What follows is the layer above it.

## The model that was planned, and the one that shipped

The concept had the TUI open by running `scan()` and browsing the resulting
[`ScanTree`](../../../core/src/tree.rs). One walk, one tree, every number
already known. It is the obvious design, and the browser would have been a view
over a value.

It does not survive contact with a home directory.

`scan ~` on the machine this was built on takes minutes and 1.4 GB for a
2.2M-entry tree. A browser that opens by doing that is a browser that opens
after lunch, and it has to do it again the moment anything on disk changes.
Worse, the thing a user opens a disk browser *for* — "what is big in here" — is
answered one directory at a time, and the tree spends its cost on the 99% of
directories they will never look at.

So the browser lists one directory (`cli/src/ui/listing.rs`, one `read_dir` and
one `metadata` per entry) and measures subdirectory totals on demand, in the
background (`core/src/measure.rs` + `cli/src/ui/measure.rs`).

| | Scan-then-browse | Lazy |
|---|---|---|
| Time to first screen | The whole tree | One `read_dir` |
| Memory | ≈ 630 bytes × every entry | One listing, plus a `PathBuf` and a `u64` per directory measured |
| Staleness | The whole tree at once | Per directory, and `r` re-measures one |
| Cost of a directory never opened | Paid | Not paid |

`scan` keeps its tree. It needs one: hardlink attribution has to settle before
any total is summed, and the report is of the whole tree at once. The browser
asks a smaller question and would throw the rest away, which is why
`core::measure` exists beside `core::scan` rather than instead of it.

## `measure` is not a small `scan`

Three properties make it usable from a screen, and each was arrived at by
getting it wrong first.

**It can be stopped, promptly.** The cancel flag is read on entering every
directory *and* every 512 entries within one. Reading it only per directory
looks sufficient until a directory holds a hundred thousand files, which is a
hundred thousand `stat` calls with no check in between — and the keypress that
asked to stop waits for all of them.

**It reports every directory as that directory finishes**, not once at the end.
Walking a directory visits every directory beneath it, so its walk already
contains all of theirs. A caller that learns nothing until the whole thing
finishes will start those inner walks itself, and do the same work twice
concurrently through the same rayon pool. Reporting as it goes is what makes the
outer walk *subsume* the inner ones instead of racing them.

**A subtotal survives cancellation of the walk above it.** That subtree did
finish, whatever became of its neighbours. The first version discarded
everything on cancel, which is the same mistake at a different scale.

Everything runs through rayon's **global** pool, as `walk.rs` already does. A
pool per measurement would add N threads for every directory entered. The real
cost of sharing is not threads but queueing, which is why cancellation has to be
prompt rather than merely correct.

## The identity of a result is its absolute path

This is the invariant the browser is built around, and the one that took four
rounds of real use to find.

The first design cancelled the running walk whenever the user navigated, and
tagged results with a generation counter so late replies could be discarded. Both
halves were wrong:

- Cancelling on navigation **destroyed work that was about to be wanted**.
  Stepping into a directory and back out recomputed the parent from nothing.
- The generation counter existed to stop a stale answer landing on the wrong
  row. But an answer is not stale — it is about somewhere else. Key it on the
  absolute path and the problem does not arise.

So: nothing is cancelled except by `r` and by exit. A walk in flight runs to the
end and its answer goes into a session cache whether or not anyone is still
looking. The generation counter is gone. `Sizer` (`cli/src/ui/measure.rs`) holds

- `known: HashMap<PathBuf, u64>` — every total computed this session, never
  evicted,
- `running: HashMap<PathBuf, u64>` — figures still climbing, shown but never
  treated as totals,
- `pending: HashSet<PathBuf>` — queued or being walked,

and one worker thread over a queue, newest first, so the directory being looked
at is measured before whatever is left over from the last one. `is_measuring`
answers true for a path whose **ancestor** is being walked, because that walk
will report it on the way: the row shows a spinner rather than nothing, and
nothing is queued twice.

## Detection is shared, not reimplemented

`Rules::state` colours a row; `detect::claim` decides a candidate. They run the
same three tests in the same order — `matching`, `excluded`, `predicates_hold` —
so `included` means exactly *`clean` would claim this*.

The first version of `state` looked only at roots, includes and excludes, and
painted a `target/` with no `Cargo.toml` beside it as junk that `clean` would
never touch. Moving the predicates onto `Rules::predicates_hold` and calling it
from both fixed that. **None of it needs the filesystem**: `requires_sibling`
asks about the names beside a path, which is the listing the browser just read,
and `older_than` asks about the entry's own mtime, which is already in the row.
`Facts` carries those plus the caller's `now`, so the core still reads no clock
and stats nothing.

`requires_clean_repo` is deliberately not among them. It is not a question about
whether a rule *claims* a path — `detect` claims it either way — but about
whether `clean` will act, and it costs a `git status` per repository.

The four states are `Untracked`, `InScope`, `Included`, `Excluded`. `InScope` —
inside a rule's root, matched by none of its patterns — is a state of its own
because "my rule does not cover this" and "my rule is not running" are different
problems, and folding them together leaves the user unable to tell which they
have.

## The config file is edited, never regenerated

`cli/src/config/write.rs` is a function from TOML text to TOML text.
`toml_edit` keeps the whole document; the parsed form is never serialised back,
because a config worth writing by hand is one full of comments explaining why
each rule is there.

Two things this had to get right that are easy to miss:

- **A trailing comment belongs to the value, not the key.** `table["x"] = v`
  carries it off. The old value's decor is lifted onto the new one.
- **An absent `[[rules]]` means "leave the built-ins alone", not "there are no
  rules."** Appending one table to such a file turns five rules into one without
  a word, so the built-ins are written out first. `rules = []` is the opposite
  statement and is left alone.

Keys that fall back to a default are removed rather than left stale. `tier` is
the exception and is always written: it decides whether `--apply` takes
something without asking, and a file that leaves its most consequential setting
to a default has hidden it.

The write is a neighbouring file and a rename, and it happens **before** the
screen recolours — a rule that repainted the listing and then failed to save
would leave the user believing something that is not on disk.

## Where the layers sit

```
                        cli/src/ui/
  term.rs   ── the alternate screen, restored on every path incl. panic
  app.rs    ── cwd, cursor, order, filter, dialog; every key a function of state
  listing.rs── one directory: read_dir + one metadata per entry
  sort.rs   ── four orders; reports the one it could apply
  layout.rs ── the table: which columns fit, spinner, share-of-listing bar
  edit.rs   ── the rule form and its chooser, as values
  measure.rs── the sizing worker, its queue and its session cache
  mod.rs    ── drawing and key dispatch, and nothing else
                              │
              ┌───────────────┼────────────────┐
   core::measure        core::Rules::state   cli::config::write
   (bytes, cancellable) (four states)        (TOML in, TOML out)
```

Everything above `mod.rs` is a plain function over values, which is what lets it
be tested where there is no terminal. Layout is tested too, through
`ratatui::backend::TestBackend` — a fake terminal whose buffer reads back. A
real pseudo-terminal is not an option: `script` reports a size of 0×0 and
renders nothing.

## What four rounds against a real home directory found

None of these were visible to the test suite, and all were obvious within a
minute of use. They are the argument for exercising a TUI by hand, and for
writing the test afterwards.

1. **The screen froze.** `start` joined the worker from inside key handling.
2. **Entering a measured directory recomputed it.** `measure` kept one number
   and dropped everything it had walked through to get it.
3. **Navigating cancelled work and lost it.** See above.
4. **An outer walk raced the inner ones.** Same mistake as 2, one level up.

And two from CI and the config file:

5. **A clippy lint inside `#[cfg(windows)]` reached `main`**, because clippy only
   sees what the host compiles. `just lint-windows` cross-checks now, and
   `verify` runs it.
6. **`requires-clean-repo` was missing from the rule form**, so editing a rule
   that had it silently dropped its git guard.

## Invariants added in v0.4

- **A measured total is keyed on its absolute path**, never on the row it came
  from.
- **The browser cancels only what the user asks it to** (`r`) and what exit
  requires.
- **A walk of a directory subsumes the walks of everything inside it.**
- **`in scope` is a state of its own.**
- **A colour and a candidate are decided by the same code.**
- **The config file is edited, never regenerated**, and an absent `[[rules]]` is
  not an empty one.
- **The file is written before the screen recolours.**
