# disk-tools — Rust Crate Structure

## Workspace

`Cargo.toml` at the root:

```toml
[workspace]
members = ["core", "cli"]
resolver = "3"

[workspace.package]
version = "0.1.0"
edition = "2024"
rust-version = "1.85"
```

Edition 2024 stabilised in exactly 1.85, so the MSRV that `rayon` already forces
makes the newer edition free. Both member crates inherit `version`, `edition` and
`rust-version` from the workspace — there is no `rust-toolchain.toml`; the MSRV is
enforced by the manifest plus a CI job pinned to 1.85.

## The two crates

| Crate | Package | Kind | Role |
|-------|---------|------|------|
| `core/` | `disk-tools-core` | lib | The scanning engine. Silent: no printing, no logging |
| `cli/` | `disk-tools` | bin (`disk-tools`) | Argument parsing, rendering, process exit codes |

The arrow points one way — `cli → core` — so the engine can be depended on,
tested and (eventually) published without dragging in clap or a terminal.

### `disk-tools-core`

```
core/src/
├── lib.rs      deny(unsafe_code); pub fn scan(); re-exports
├── options.rs  ScanOptions
│
│   ── the scan ──
├── walk.rs     read_dir + rayon par_iter recursion, skip collection
├── size.rs     allocated + apparent, per platform (Windows: fallback only)
├── dedup.rs    hardlink identity → attribution, and the link groups it finds
├── tree.rs     ScanNode / ScanTree / SkippedEntry + aggregation
├── windows_dir.rs   #[cfg(windows)] — AllocationSize, file id, LastWriteTime
│
│   ── the cleanup ──
├── paths.rs    the comparisons that decide what is a candidate
├── detect.rs   the rules: four safe-list categories plus age
├── git.rs      one question — is there uncommitted work here?
├── clean.rs    denylist, tiers, totals → CleanPlan. Writes nothing
└── trash.rs    #[cfg(feature = "trash")] — the only code that removes anything
```

Every module except `lib.rs` is private; the public surface is the re-export
list in `core/src/lib.rs`. The split inside is by *effect*, not by topic:
`clean.rs` decides and `trash.rs` acts, which is why only the second needs the
backend and why every rule in the first is testable against a hand-built tree.

Dependencies:

| Dependency | Why |
|------------|-----|
| `rayon = "1.12"` | Directory-level parallelism in the walk |
| `serde = { version = "1", optional = true }` | Behind the `serde` feature — see below |
| `trash = { version = "5.2", optional = true }` | Behind the `trash` feature — the OS trash, never `rm` |
| `windows-sys = "0.61"` (Windows only) | `GetCompressedFileSizeW`; Unix builds never see it |
| `tempfile = "3"` (dev) | Filesystem fixtures |

The spec's original sketch also listed a `units.rs` and a `filesize` crate.
Neither exists: size formatting lives in the renderer (only the CLI needs it), and
`filesize` was rejected in Task 2 because its Windows path calls
`std::fs::canonicalize` on every file.

The git guard likewise takes no dependency: `gix` is large and `git2` needs
libgit2, which is a great deal of build for one boolean, so `git.rs` shells out
to `git status --porcelain` (D6). The cost of that choice is measured —
~23 ms per repository, [here](../../benchmarks/2026.07/2026.07.25-clean-latency.md).

### `disk-tools`

```
cli/src/
├── main.rs     args → scan → render → write; spinner and skips to stderr
├── args.rs     clap derive, parse_size, validate_root
└── render/
    ├── mod.rs
    ├── tree.rs     dust-style tree, parent-relative bars, unicode-aware fitting
    ├── json.rs     --json (full tree, raw byte counts)
    └── skipped.rs  skipped-entries summary, capped at ten
cli/tests/cli.rs    black-box tests against the built binary
```

| Dependency | Why |
|------------|-----|
| `disk-tools-core` (path, `features = ["serde"]`) | The engine |
| `clap = "4.5"` (derive) | Argument surface and `--help` |
| `terminal_size = "0.4"` | Bar layout; falls back to 80 columns when piped |
| `serde_json = "1"` | `--json` |
| `indicatif = "0.17"` | The scan spinner; tty-gates itself |
| `unicode-width = "0.2"` | Terminal column widths for CJK, emoji, combining marks |
| `tempfile = "3"` (dev) | Fixtures for the integration tests |

## Features

`core/Cargo.toml`:

```toml
[dependencies]
serde = { version = "1", features = ["derive"], optional = true }
trash = { version = "5.2", optional = true }

[features]
default = ["trash"]
trash = ["dep:trash"]
serde = ["dep:serde"]
```

**`serde`** — every model type carries
`#[cfg_attr(feature = "serde", derive(serde::Serialize, serde::Deserialize))]`.
A library consumer that does not need serialisation pays nothing; the CLI turns
it on explicitly (`cli/Cargo.toml`) because `--json` requires it.

**`trash`** — the ability to actually remove something, and **only** that.
`core/src/trash.rs` is the one module behind it; deciding *what* to remove
(`core/src/clean.rs`) needs nothing from the backend, so `--no-default-features`
leaves a consumer with `scan()` **and** `plan()` while dropping `objc2` on macOS
and `windows` on Windows. The feature is named for what it gates rather than for
the module it once lived in: a feature called `clean` that gated only removal
would misdescribe itself.

That promise is enforced rather than asserted — `just check-minimal` builds the
core without default features and runs as part of `just verify`. Nothing else
exercises that configuration, so without the recipe it would rot unnoticed.

The `dep:` syntax matters in both cases: it declares the optional dependency
without also creating an implicit feature of the same name that could be enabled
by accident.

## The unsafe policy

`core/src/lib.rs` declares `#![deny(unsafe_code)]` — crate-wide, **`deny` and not
`forbid`**, and that distinction is the whole point: `forbid` cannot be lifted by
a local `#[allow]`, and Windows offers no safe route to either a file's allocated
size or its identity.

Exemptions are granted **per function, never per module**, and all four are
`#[cfg(windows)]`:

| Function | Does |
|----------|------|
| `size::allocated` | `GetCompressedFileSizeW` — the per-file fallback |
| `windows_dir::read_facts` | `GetFileInformationByHandleEx` |
| `windows_dir::collect_batch` | Walks that call's output buffer |
| `windows_dir::volume_serial` | `GetFileInformationByHandle` |

Everywhere else, including all of Unix, `unsafe` still fails the build. The `cli`
crate contains none and needs no attribute.

`collect_batch` is the one doing pointer arithmetic rather than a single call, and
is the one to read carefully: it bounds-checks every read against the capacity it
passed the OS rather than trusting `NextEntryOffset`, and uses `read_unaligned`
because the API's 8-byte guarantee is weaker than the struct's own requirement.
The containing handle comes from `std::fs::OpenOptions` with
`FILE_FLAG_BACKUP_SEMANTICS`, so path length, error mapping and closing stay in
safe code.

Any further `allow` should get the same scrutiny these did.

## Platform-conditional compilation

Three patterns recur:

1. **Alternate function bodies** — `#[cfg(unix)]` / `#[cfg(windows)]` /
   `#[cfg(not(any(unix, windows)))]` implementations of `size::allocated`; a
   `#[cfg(unix)]` / `#[cfg(not(unix))]` pair for `walk::device_of` and
   `walk::file_id`, where the non-Unix arm returns `None` and turns a feature into
   a documented no-op.
2. **Platform-only helpers** — `size::verbatim_if_long` exists only on Windows.
3. **Platform-only dependencies** —
   `[target.'cfg(windows)'.dependencies] windows-sys`.

Cross-checking a Windows build from a Unix machine, without running it:

```bash
cargo clippy --workspace --target x86_64-pc-windows-msvc --all-targets -- -D warnings
```

This catches type errors in `#[cfg(windows)]` code that the local build never
compiles. It is not a substitute for CI, which actually *runs* the tests there —
the NTFS sizing behaviour documented in the overview was found by CI, not by this
check.
