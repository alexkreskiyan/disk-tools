# Architecture after v0.3: detection as data

The [2026.07.25 snapshot](2026.07.25-overview.md) still describes the pipeline
correctly — walk, dedup, aggregate, then detect, plan, apply. This note covers
only what v0.3 moved, and reads as a delta against it.

The change in one sentence: **what counts as junk stopped being code**.

## The rule engine

`core/src/rules.rs` is new. `Rule` is the shape a detection rule has; `Rules` is
that list compiled once for a scan.

```
config file ──parse──> Vec<Rule> ──Rules::new(dirs)──> Rules
                                                        │
                                   ┌────────────────────┤
                                   │ includes: GlobSet  │  one automaton,
                                   │ include_owner      │  all rules
                                   │ include_dir_only   │
                                   │ excludes + owner   │
                                   │ roots              │  for pruning
                                   └────────────────────┘
```

Three properties are load-bearing, and none is visible from the types:

**List order is precedence.** The first rule that claims a node wins. It falls
out of taking the *lowest* rule index among the patterns that matched, which is
also what reproduces v0.2's "a junk match beats the age rule" without a special
case — the junk rules simply come first, and `--older-than` appends its rule
last.

**A rule that cannot be expressed matches nothing.** Disabled, an unresolvable
`~`, a root that is not UTF-8: each drops that rule and leaves the others alone.
Every one is a case where the honest answer is "unknown", and for input to a
delete operation the only safe reading of unknown is *no*.

**One `GlobSet` across all rules, not one per rule.** Detection visits every node
of the tree — 2.3 million on a 171 GB `~/Projects` — so matching each rule
separately would multiply the per-node cost by the rule count. A single
`globset::Candidate` is built per node and reused across every pattern; it
precomputes the basename and, on Windows, the lowercased form.

### It came out faster

| | v0.2 hardcoded | v0.3 rules |
|---|---|---|
| `detect` | 347 ms | **196 ms** |
| full traversal, nothing claimed | 667 ms | **472 ms** |
| per node | 285 ns | **201 ns** |
| candidates on `~/Projects` | 104 | **104** |

The budget was "no worse than 2×". Two reasons it improved instead: `claim()`
used to call `cache_roots()` on every node, building a `Vec` and two `PathBuf`s
each time — roots now resolve once, at compile time — and one automaton beats a
chain of string comparisons. Identical candidate counts on a real 171 GB tree is
the evidence that nothing else changed.
[Measured.](../../benchmarks/2026.07/2026.07.26-detect-budget.md)

## The config path

```
  args --config  ─┐
  $XDG_CONFIG_HOME├─> config::locate ──> config::load ──> Config
  UserDirs        ┘                          │             { rules, scan,
                                             │               report, clean,
                                             │               warnings }
                                             ▼
                                    Args::resolve(Environment)
                                    flag > file > default
                                             │
                                             ▼
                              ScanOptions / CleanOptions / Rules
```

`cli/src/config.rs` finds, reads, validates and converts. The core still reads no
config file, no clock and no environment — `core/src/options.rs` states that, and
it is what keeps every rule testable with a temp directory standing in for a home.

**The file's rule schema is not the core's `Rule`.** A rule in the file must name
a `root`; the core type allows `None`, because the built-ins genuinely apply
wherever the scan goes. `RuleEntry` is the bridge and `root = "*"` is how the file
spells the permissive case — without it, `config init` would have written
`root = "~"` for those three and silently narrowed what `clean /var/tmp` finds.

**A malformed file stops the program; an unfamiliar key does not.** A syntax
error or a rule missing its `includes` means the user's intent is unknown. An
unknown key is far more likely a typo or a newer version's setting, so it is a
warning naming the key. (`deny_unknown_fields` and `serde_ignored` are also
mechanically incompatible — the first fails before the second can observe
anything.)

### Precedence lives in one place

`Args::resolve` is the only expression of flag > file > default. No overridable
flag carries a clap `default_value`: with one, `--min-size 0` and an absent
`--min-size` arrive identical, and the first has to beat the file while the
second defers to it.

One limitation: a boolean turned **on** in the file cannot be turned off from the
command line, since a flag can only be passed or not passed. Undoing that needs a
`--no-…` per flag, and no requirement asked for it.

## `clean` over several roots

With no path, `Rules::scan_roots()` supplies what to walk: the resolved roots of
the enabled rules, sorted, with any root inside another dropped. That
deduplication is not tidiness — a rule at `~` and one at `~/Projects` would
otherwise walk the latter twice, and `reclaimable` would report double what
removing it frees.

Each root is scanned and planned separately, then `CleanPlan::merge` combines
them. Merging plans rather than trees avoids inventing a node above them that
would need a path and a size it does not have. Every field is additive, and
safely so **only because** the roots are disjoint by then; the doc on `merge`
says so, since handing it overlapping roots would double both.

A missing root is fatal only when the **user** named it. A path typed on the
command line that is not there is a typo, and an empty report would hide it. A
root that came from a rule is a description that may have gone stale, and one of
those is no reason to leave the others uncleaned.

## Which invariants moved

| Invariant | Then | Now |
|---|---|---|
| The safe list | Four hardcoded categories | Five built-in rules, all editable |
| Tiers | The tool's claim, always | The **rule's** claim. A user rule may say `auto`, and nothing verifies it |
| `venv`/`.venv` | Forced to `confirm` whatever matched | Gone. The rule sets the tier, full stop |
| `--apply` | Removes everything in the plan | **Refuses** while anything `confirm` remains, unless `--safe` or `--yes` |
| `clean` | Required a path | Optional; the rules say where |
| The clock | `Age` paired threshold with `now` | `DetectOptions.now` is mandatory, which restores "cannot be half-armed" |

## What did not move

**The denylist.** `DENIED_ROOTS` and the absolute roots derived from `UserDirs`
are byte-identical to v0.2, still checked in both raw and lexically-normalised
form, and still reachable from no rule, flag or config file — `--purge` included.
It is the one thing in the tool that a user cannot configure, and that is the
point.

Dry-run by default; the trash as the destination; failures as data; the core
never printing; `#![deny(unsafe_code)]` with four per-function exemptions;
anything that really deletes `#[ignore]`d behind `just smoke-trash`.

## Two things the tests taught

Both were found by the suite failing, not by review, and both are worth knowing
before writing another integration test:

- **The tests were reading the developer's config.** Three failed the moment the
  config reached behaviour, because this machine had `depth = 0` in
  `~/.config/disk-tools/config.toml`.
- **And then walking the developer's home.** Once `clean` with no path began
  following rule roots, the built-in `user-caches` sent the suite through all of
  `/Users/alex` — 93 seconds. `run()` in `cli/tests/cli.rs` now isolates `HOME`,
  `USERPROFILE` and `XDG_CONFIG_HOME` into a temp directory.
