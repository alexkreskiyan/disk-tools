# After v0.5: two verbs, three tiers, and a plan that says what it will do

The previous snapshot,
[After v0.4: the browser](2026.07.27-tui-lazy-model.md), describes the layer
above the engine. This is about the engine's front door.

## One word for two things

`clean` without `--apply` showed; with it, removed. One word for both is why the
flag existed, and the flag is why the word was ambiguous — a flag that decides
whether a command is destructive is a flag that gets forgotten in **both**
directions.

So: `preview` shows, `clean` removes. What matters is not the split but that the
two take an **identical** flag set, resolved by one function
(`Args::cleanup`). The way a preview is acted on is to retype the line with the
other verb, so a flag either verb refused would break the copy at exactly the
moment the user had decided to act. `preview` therefore accepts `--purge` and
`--yes` and does nothing with them.

### What was ceremony and what was a guard

`--apply` carried two checks and only one of them was about anything:

| Check | Reads | Kept? |
|---|---|---|
| "did you pass `--apply`" | the arguments | no — that is the verb now |
| "does the plan hold a confirm-tier candidate" | **the plan** | yes |

The second could never have been clap's: it is a property of the data, not of the
argument list. It exits **2**, not 1, because 1 already means *the removal partly
failed* — and a script that cannot tell that from *nothing happened, add a flag*
has lost the distinction it most needs.

The cost is real and is written down rather than argued away: a bare
`disk-tools clean` now walks the configured rule roots and removes what they
claim. With the shipped config that is the whole home directory. It goes to the
trash, and `preview` is one word away, but it is a sharper default than v0.2's.

## Three tiers, because two named different axes

v0.2 had `auto` and `confirm`; v0.5's `--purge` would have been a third
destination beside them. Naming it that way does not read:

- `purge` names a **destination**
- `auto` names a **ceremony**

The contrast between them resolves on nothing, which is why the set became
`purge` / `trash` / `confirm` — three answers to **one** question, *what does
`clean` do with this*. "Nothing, until `--yes`" is an answer of the same kind as
the other two.

One field, not a `purge = true` key beside a tier. As two fields, `purge` with
`confirm` is writable and has to be rejected at load; as one value it cannot be
written. And `--safe` **admits purge**: it drops what needs confirming, and purge
is a stronger claim of regenerability than trash, not a weaker one.

`purge` earns its place on a fact about trashes rather than on taste: **the trash
frees no space until it is emptied.** A `clean` that moves 20 GB of `node_modules`
into it has relocated the problem and added a manual step.

## The trap: `--purge` must not rewrite the tier

The obvious implementation of the flag is "set every candidate's tier to
`Purge`". It is wrong, and dangerously so: `--safe` and the refusal both read the
tier, so one flag would silently cancel a confirmation it has nothing to do with.
`clean --purge` would have destroyed confirm-tier candidates without `--yes`.

So a candidate carries **both**:

| Field | Is | Read by |
|---|---|---|
| `tier` | what the **rule** says | `--safe`, the refusal |
| `purge` | where it actually goes | `apply`, the report |

`purge` is the resolution of `tier` and the flag together — genuinely new
information, not a second name for the first. The spec's "one field" rule holds
where it was made: on the *rule*.

## The plan is the whole decision

`apply` stopped taking a `Removal`. Where a candidate goes is on the candidate,
decided by `plan()`, so:

```
plan(&tree, &options)  →  every candidate knows its fate
        │
        ├── preview: print it
        └── clean:   apply(&plan, progress)
```

That is what lets `preview` print **exactly** what `clean` does, rather than a
description of it maintained in step by hand. `Removal` itself is gone — it had
become a second name for `Tier`, and keeping a derived name beside its source is
what "a colour and a candidate are decided by the same code" exists to prevent.

`CleanOutcome` split into `trashed` and `purged`, and **the core never adds them
up**. One "freed" figure over a mixed run does not say what can be brought back,
which is the only thing a reader wants from it; summing is a decision, so it
belongs to whoever is printing. The recoverability sentence is likewise read off
the outcome rather than off a flag — after v0.5 one run can send some candidates
to the trash and destroy the rest, and a sentence derived from `--purge` would
describe the invocation instead of the paths it stands under.

## Display and plan, kept apart

Two flag groups, and which one a flag belongs to is the whole of its contract:

| Changes the plan | Changes the display |
|---|---|
| `--safe`, `--min-size`, `--older-than`, `--purge`, `--yes` | `-d`, `--sort`, `--json` |

`Report { depth, sort, json }` carries the second group and nothing in it can
keep a candidate out of the removal — only out of the printout. `CleanPlan`
carries the first.

`-d` numbering starts at the **rule**, not at the candidate:

| `-d` | Prints |
|---|---|
| 0 (default) | one line per rule: count, total, fate |
| 1 | one line per candidate |
| 2+ | inside a candidate, from `ScanNode::children` |

Level 0 had to *be* something or the default would do nothing, and grouping is
also what `-n` was providing by truncating — without hiding a tail. `--sort size`
breaks ties by path, because a rule over a large tree yields hundreds of
candidates of one size and an unchanged disk must print identically twice.

**The plan keeps its own order.** `CleanPlan.candidates` stays sorted by path so
two runs are comparable; `--sort` reorders the *report*.

`--json` ignores both display flags. A machine-readable output quietly shortened
by one of them is the worst kind of shortened, because nothing in the document
says it happened. `preview --json` is a plan and `clean --json` is an outcome —
two documents, not one shape with half its fields null, which would make every
consumer branch on emptiness to discover which it had.

## The deeper levels cost memory, so they are opt-in twice

`-d 2` needs a candidate's children, which live in the `ScanTree` the plan was
made from. Two decisions there:

**The trees are handed to the renderer beside the plan**, never folded into it. A
`CleanPlan` that owned subtrees would be a plan carrying the whole scan result,
and `--json` would then have to decide whether to serialise it.

**They are only kept at `-d 2` or deeper.** A tree costs ~630 bytes per entry —
1.4 GB for a home directory — and holding every root's alive through the removal
to satisfy a display flag nobody passed is exactly the cost the lazy browser was
built to avoid. Below that they are dropped as they are planned. With none kept,
the candidate line stands alone, which the renderer accepts rather than treats as
a failure.

## Two flags that left, and where they went

| Gone | Replaced by |
|---|---|
| `--apply` | the verb |
| `--allow-dirty` | `requires-clean-repo` on the rule that wants the guard |

`--allow-dirty` was already duplicated by a finer, better-placed setting, which is
the argument for removing it — stronger than the one that was first offered
("configure it instead"), and it also avoided reversing an old decision: a guard
that a *file* can disable is a guard disabled invisibly.

`tier = "auto"` is an **error** naming `trash`, not an alias. An alias lives for
ever; an error costs one edit and stops a verb that now removes from starting on a
file nobody has read through.

## A path bug the split uncovered

`preview .` inside a project reported "Nothing to clean" while `preview /full/path`
to the same directory reported four gigabytes. A rooted rule compiles to an
absolute glob (`~` resolves to one), so a relative path produces nodes like
`./target` that nothing matches — and the run claims nothing, silently and in the
safe direction. The browser had it too, colouring a home full of junk as
untracked.

Every path the tool acts on now goes through `args::absolute` —
`std::path::absolute`, **never** `canonicalize`, because the path shown has to be
the path removed. The core cannot do this itself: it reads no environment, so it
has no working directory to join.

Known limitation, recorded rather than chased: the working directory the kernel
returns is already symlink-resolved, so a home behind a symlink (`/var` →
`/private/var` on macOS) still defeats a `~`-rooted rule on a relative path.

## Invariants added in v0.5

- **`preview` changes nothing, whatever the flags.** Asserted against the seven
  combinations most able to break it.
- **The two verbs resolve through one function**, so their flag sets cannot drift.
- **`clean` refuses on the plan, not on the arguments**, and exits 2.
- **`Candidate.tier` is the rule's word; `Candidate.purge` is where it goes.**
- **The plan says what will happen, so `apply` takes no removal mode.**
- **The core never adds `trashed` and `purged` together.**
- **`--sort` orders the report; the plan keeps its path order.**
- **No display flag can change a byte of `--json`.**
- **Trees are kept only when the report will unfold inside a candidate.**
- **Every path the tool acts on is absolute before anything else happens.**
