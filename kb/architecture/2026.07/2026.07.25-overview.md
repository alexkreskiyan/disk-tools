# disk-tools — Architecture Overview

Cross-platform disk-utilities CLI in Rust. v0.1 answers one question — *what is
eating my disk* — by walking a tree in parallel, measuring **real on-disk
(allocated) size**, and printing a size-sorted, dust-style tree or JSON.

Supersedes the [2026.07.14 snapshot](2026.07.14-overview.md), which described an
empty repository and guessed the project was Discord tooling. All eleven tasks of
the [v0.1 spec](../../specs/2026.07/2026.07.14-disk-tools-v0.1-scan-report.md) are
now implemented.

## System shape

```
                 disk-tools (cli)                    disk-tools-core
                 ────────────────                    ───────────────
  argv ─► args.rs ──ScanOptions──────────────────► lib.rs::scan()
           │                                             │
           │                                    ┌────────┴────────┐
           │                                    │ 1. walk         │  parallel, per-directory
           │                                    │ 2. dedup        │  hardlink attribution
           │                                    │ 3. aggregate    │  bottom-up sums
           │                                    └────────┬────────┘
           │                                             │
           │                                          ScanTree
           │                                       { root, skipped }
           ▼                                             │
   RenderOptions ──────────────────────────────────────► │
           │                                             │
           ├─ render/tree.rs    ─┐                        │
           ├─ render/json.rs    ─┼── String ──► stdout ◄──┘
           └─ render/skipped.rs ─┴────────────► stderr
```

The split is strict and load-bearing:

- **`disk-tools-core`** never logs, never prints, and knows nothing about
  terminals or config files. Everything that goes wrong comes back as data in
  `ScanTree::skipped`. It is driven entirely by an explicit `ScanOptions`.
- **`disk-tools`** owns every presentation decision: terminal width, bars,
  truncation, colour-free formatting, the progress spinner, and which stream each
  piece of output belongs on.

Dependency direction is one-way (`cli → core`); the core is usable and testable
standalone.

## The three phases, and why the order is fixed

`scan()` (`core/src/lib.rs:35`) runs exactly three phases:

### 1. Walk — `core/src/walk.rs:71`

`fs::read_dir` plus recursion, parallelised at the **directory** level:
`subdirs.into_par_iter().map(walk_dir).collect()` (`core/src/walk.rs:167`). Each
worker returns its own `Walked { entries, skipped }`, merged by `absorb` — no
shared lock on the hot path.

The output is a **flat** `Vec<WalkEntry>`, not a tree. That is deliberate: phase 2
must group entries by identity across the *whole* scan before anything is summed.

Cost discipline shows up here:

- `DirEntry::file_type()` (free, from `readdir`'s `d_type`) decides dir/file/link.
- `DirEntry::metadata()` is called **once per entry**, where size is needed anyway
  — never speculatively.
- Symlinks are never followed; their own metadata is what gets recorded.
- `--one-file-system` compares `st_dev` against the root's (`crosses_filesystem`,
  `core/src/walk.rs:200`) — only for directories, since a file cannot start a new
  mount.

Errors never abort a scan. `skip_reason` (`core/src/walk.rs:192`) maps
`io::ErrorKind` onto `SkipReason`, and the entry lands in `skipped`.

### 2. Dedup — `core/src/dedup.rs:17`

Entries sharing a `FileId { device, inode }` are one file on disk reached by
several names. `attribute` groups by that key and keeps the **lexicographically
first path**, zeroing `allocated` and `apparent` on every other member.

Lex-first, not first-walked: under a parallel walk "first" is nondeterministic, so
directory totals would drift between runs and tests would flake. Comparison is on
raw `OsStr` bytes rather than `Path::cmp`, which orders component-wise and
disagrees at `/` boundaries.

### 3. Aggregate — `core/src/tree.rs:62`

Builds the `ScanNode` tree from the flat list via a `by_path` index, then folds
bottom-up: a directory's size is **its own bytes plus the sum of its children**,
matching `du`. Children are sorted by path (`core/src/tree.rs:112`) so output is
reproducible despite the parallel walk.

An unreadable or missing root yields a zeroed placeholder node, never a panic.

**Why this order cannot change:** attribution must settle before any sum is
computed. Deduplicating during the walk would reintroduce the nondeterminism that
lex-first attribution exists to remove.

## Data model

`core/src/tree.rs`, re-exported from `core/src/lib.rs:24-25`.

| Type | Fields | Notes |
|------|--------|-------|
| `ScanOptions` | `root`, `min_size`, `depth`, `apparent`, `one_file_system` | The core's entire input. `min_size`/`depth`/`apparent` are read by the *renderer*, not the walk |
| `ScanNode` | `path`, `allocated`, `apparent`, `is_dir`, `children` | Both sizes always measured, regardless of `--apparent` |
| `ScanTree` | `root`, `skipped` | What `scan()` returns |
| `SkippedEntry` | `path`, `reason` | Failure as data |
| `SkipReason` | `PermissionDenied` / `NotFound` / `Other(String)` | |

All five carry `#[cfg_attr(feature = "serde", derive(Serialize, Deserialize))]`.

## Invariants

These hold across the codebase and are what the tests defend:

1. **Display filters never touch totals.** `-n`, `--depth` and `--min-size` prune
   *output only* (`cli/src/render/tree.rs:50`); a directory's number is always its
   full subtree, like `du`. Filtering during aggregation would corrupt parents.
2. **Phase order is fixed** — walk → dedup → aggregate.
3. **The core is silent.** No `println!`, no `log`, no `tracing`.
4. **stdout carries the report; stderr carries everything else** — that is what
   keeps `--json` pipe-clean (`cli/src/main.rs:71-77`).
5. **`canonicalize()` is never called.** It rewrites paths into `\\?\` form on
   Windows and fails on RAM disks, network drives and container mounts.
6. **`#![deny(unsafe_code)]`** in the core, with exactly one scoped `allow`.

## Platform splits

The same function has different bodies per platform, and each divergence is a
documented capability gap rather than an implementation detail:

| Concern | Unix | Windows | Consequence |
|---------|------|---------|-------------|
| Allocated size | `metadata.blocks() * 512` (`core/src/size.rs:47`) | `AllocationSize` from the directory listing (`core/src/windows_dir.rs`) | Equivalent on both |
| File identity | `(st_dev, st_ino)` (`core/src/walk.rs`) | `(volume serial, file id)` from the same listing | Hardlinks dedup on both |
| `walk::device_of` | `metadata.dev()` | always `None` | `--one-file-system` is silently a no-op off Unix |
| `size::verbatim_if_long` (`core/src/size.rs:69`) | n/a | prefixes `\\?\` past 248 chars | Long **UNC** paths may skip — fallback path only |

A third `allocated` variant covers neither-unix-nor-windows targets by falling
back to `metadata.len()`.

**Windows takes its facts from the directory, not from each file.** `Metadata`
there exposes neither the allocated size nor an identity, and the path-based
alternatives are poor — `GetCompressedFileSize` returns the logical length for
anything not compressed or sparse, and a file id means opening every file.
`GetFileInformationByHandleEx(FileIdBothDirectoryInfo)` answers both for a whole
directory from one handle, and should be cheaper than the per-file call it
replaced, since that one resolves and opens a path each time.

`walk_dir` therefore runs a uniform `dir_facts` step that returns an **empty map
on Unix**, where `Metadata` already carries everything. One traversal path, not
two; Unix behaviour is bit-for-bit unchanged, and an entry the listing missed
falls back to `size::measure`.

## Rendering

`render_tree` (`cli/src/render/tree.rs:39`) emits `size · indented name · bar ·
percent`, where the bar and percentage are **parent-relative** — each entry shows
its share of its container, and every directory is 100% of itself.

Layout is column arithmetic against the terminal width (`terminal_size`, falling
back to 80 when piped). Names are fitted with `fit` (`cli/src/render/tree.rs:141`),
which measures **display width** via `unicode-width`: CJK and emoji occupy two
columns and combining marks none, so a character count would push the bar block
off the right edge. Below 38 columns the bar is dropped rather than mangled.

`render_json` (`cli/src/render/json.rs:13`) serialises the **full** tree with raw
byte counts — display filters do not apply. `render_skipped`
(`cli/src/render/skipped.rs:14`) caps the preview at ten paths unless `--verbose`.

`main` writes the finished report through a `BufWriter` and treats
`ErrorKind::BrokenPipe` as a normal end of output (`cli/src/main.rs:60-69`), so
`disk-tools ~ | head` exits `0` instead of panicking.

## Performance

Measured on 2026-07-25 (see
[the benchmark note](../../benchmarks/2026.07/2026.07.25-v0.1-scan-performance.md)):
**1.8–2.1× faster than `du -sh`** on matched output across three fixture shapes,
**≈630 bytes of peak RSS per entry** (1.42 GB for a 2.2M-entry tree).

The memory figure is the accepted cost of keeping the whole tree: directory totals
need it, and the planned v0.4 TUI will need it again. `diskus`, which keeps only a
running total, stays 1.3–1.7× ahead on metadata-heavy trees — that gap is the
standing headroom for any future optimisation, and closing it means attacking
per-entry allocation rather than the walk strategy.
