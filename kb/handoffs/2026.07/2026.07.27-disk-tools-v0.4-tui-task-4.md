## Decisions Made During Implementation

- **`state` is a display function, not a decision function.** `detect` answers
  "may this be removed" and stops descending at the first match; this answers
  "why is that", which needs an answer for *every* row including ones `detect`
  would never look at. They share `matching` and `excluded` so the precedence
  cannot drift, but neither is written in terms of the other.
- **An `excludes` that matches with no `includes` reaching the path still reads
  as `excluded`.** The user named that path to be left alone; saying `in scope`
  would drop the only thing they said about it. `detect` never meets this case,
  because it stops at the include.
- **Classification runs once per listing, not once per frame.** The rules do not
  change while a directory is open, and a glob match per row twelve times a
  second is work for an answer that never moves. It runs again on arrival — the
  state follows the path, and a row keeping the colour of a same-named row in
  the previous directory would be worse than no colour at all.
- **`Untracked` keeps the terminal's own foreground.** Most rows are untracked;
  colouring those too would leave the few that matter nothing to stand out
  against.
- **The legend is a conditional band.** A row spent explaining colours that are
  not on screen is a row taken from the listing, so it appears only when
  something in the current directory is under a rule.
- **`ui` builds its rules without the age rule.** `--older-than` is a `clean`
  flag; a browser that coloured every old file as junk would be saying nothing.

## Deviations from Spec

The spec named `cli/src/ui/paint.rs` for the colours; they live in
`cli/src/ui/mod.rs` beside the rest of the drawing, which is four functions
long. A file for `colour` and `legend` alone would be a file for two matches.

## For Next Task

**Task 5 is the rule editor** — a form over one `Rule`, reached from a row. The
state machinery is all in place: `Rules::state` says what a rule currently makes
of a path, so an edit can be shown taking effect. What is missing is the form
itself and, from Task 6, writing it back with `toml_edit`.

**Gotchas discovered:**

- `Rules::new` **returns `Ok` for an unresolvable root** — the rule is dropped,
  not rejected. Tests that expect an error there are testing the wrong thing;
  the observable consequence is that the territory reads as `untracked`.
- `Rules::default()` is the empty rule set, which is what every existing UI test
  wants — colour is not what they are about.
