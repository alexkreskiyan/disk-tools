# Handoff: Task 5 — `require-confirmation`

## Feature Spec

[v0.3 — configuration and declarative rules](../../specs/2026.07/2026.07.26-disk-tools-v0.3-config-rules.md)

## Completed

- `--yes` on `clean`, with `requires = "apply"` like `--purge`.
- `Mode::Clean` carries `confirm_tier_allowed`, resolved once from
  `--yes || !require-confirmation`.
- `remove()` decides the refusal **before** printing anything, prints the plan as
  a dry run, names the count and both remedies, and exits 2.
- The three booleans that only mean something together — `apply`, `removal`,
  `confirm_tier_allowed` — are bundled into a `Removing` struct so no caller can
  supply two of the three.

This closes the disagreement recorded as open in the v0.2 spec: the concept asked
for per-target confirmation and v0.2 accepted `--apply` as the confirmation. v0.3
answers with a refusal, which gives the same guarantee without the stdin and TTY
machinery a real prompt needs.

## Decisions Made During Implementation

- **The default is `true`.** Without a config file, `--apply` now refuses. The
  user chose this, on the asymmetry the denylist already states: over-refusing
  costs one extra flag, under-refusing costs data. Task 3 decided the opposite
  for `-n`, and that is not a contradiction — one is about output, this is about
  deletion.
- **The refusal is decided before anything is printed.** The plan goes out with
  an `Intent`, and `AboutToApply`'s closing line promises a removal. Printing
  that and then declining would make the last sentence a user reads before the
  outcome the one that is false — precisely the defect `Intent` was introduced
  for in v0.2. On refusal the plan prints as `DryRun`, so "nothing was removed"
  is true.
- **Exit 2, not 1.** The flags were well formed; the invitation was incomplete.
  That is a usage answer, not an operation that failed.
- **`--safe` needs no special case** — it keeps confirm-tier candidates out of
  the plan, so the count is zero and there is nothing to refuse. Pinned by a test
  rather than left as a coincidence.
- **`--yes` is not a config key**, for the reason `--purge` and `--allow-dirty`
  are not: a file that answers yes in advance cancels the confirmation, and
  cancels it invisibly.

**Gotchas discovered:**

- **Three of the new tests were putting temp fixtures in the real Trash.** The
  suite went from 1.3 s to **121 s**, and the project's own convention is that
  anything which really deletes is `#[ignore]`d. They pass `--purge` now: the
  refusal is decided before the removal method matters, so the same branch is
  exercised, and the deletion stays inside the temp directory.
- An earlier run of that version did leave a few temp fixtures in this machine's
  Trash. Harmless, but they are there.
- `Mode::Clean` now has five fields. `Removing` bundles the three that only mean
  something together; a new one should join it rather than become a sixth
  parameter.
