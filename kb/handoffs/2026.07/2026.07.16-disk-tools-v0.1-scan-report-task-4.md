## Completed

- `core/src/dedup.rs`: `pub(crate) fn attribute(entries: &mut [WalkEntry])` — a pure, in-place pass over the walk's flat entry list. Groups entries by `id: Option<FileId>`, and for each identity group of >1 path charges the full bytes to the **byte-lexicographically-first** path, zeroing `allocated` **and** `apparent` on the rest.
- Entries with `id == None` (directories, and every file on Windows) are never touched — each is treated as unique.
- Wired into `lib.rs` as `#[allow(dead_code)] mod dedup;` (dead until Task 5's `scan()`).
- 10 tests (7 `#[cfg(unix)]` hardlink fixtures + 3 portable), plus the mutation/AC/review passes.

## Decisions Made During Implementation

- **Byte order, not `Path::cmp`, for the keeper.** `Path::cmp` orders *component-wise*, which disagrees with raw-byte order whenever a component holds a byte below `/` (0x2F) — e.g. `a-b.bin` vs `a/c.bin`, where `Path::cmp` picks the deeper `a/c.bin` but `sort(1)` and the spec's "lexicographically first" pick `a-b.bin`. Switched to `path.as_os_str().cmp(...)`, which is a byte compare on Unix (the only platform where dedup ever fires — `id` is `None` elsewhere). Locked in by `keeper_uses_byte_order_not_component_order`. *(Surfaced by the bugs reviewer, confidence 82.)*
- **Both `allocated` and `apparent` are zeroed on non-keepers**, so `--apparent` ranking dedups too, not just the default allocated ranking. Group members share one inode, so they already share both numbers — the keeper keeps its own, nothing is recomputed.
- **Index-based two-pass** (group into `HashMap<FileId, Vec<usize>>`, then mutate) rather than sorting the slice — keeps the keeper choice independent of input order and satisfies the borrow checker without cloning entries.

## Deviations from Spec

None. §8.2.3's algorithm is implemented as written; the "sort paths lexicographically" step is realised as a byte-lexicographic `min_by` (see the keeper decision above), which is what "lexicographically first" means to `sort(1)` and to a reader.

## For Next Task

Task 5 is **Bottom-up aggregation → `ScanTree`** (`core/src/tree.rs`), depends on Tasks 3 and 4.

- **Pipeline is `walk()` → `attribute(&mut walked.entries)` → aggregate.** The flat `Vec<WalkEntry>` after `attribute` already has hardlink bytes charged to one path each, so a plain post-order sum of `allocated` (and `apparent`) over children gives correct, non-double-counting directory totals — that's the whole point of doing dedup before aggregation.
- **Build the tree from the flat list by path.** Entries include every directory (with its own size) and every file; the root entry is the one whose path equals `options.root`. A dir node's total = its own size + Σ children (§8.2.4). Don't re-measure — the numbers are final after `attribute`.
- **This is where `scan()` lands** and makes the whole `walk`/`size`/`dedup` chain reachable — **drop the three `#[allow(dead_code)]`s in `lib.rs` then** (`dedup`, `size`, `walk`), not before. Confirmed again this task: nothing public reaches them yet.
- **AC "root total matches `du -sh`" is Unix integration** (`root_total_matches_du`, §8.2.4 / Task 5). The Task 3 sanity check already matched a 7-file/4-dir fixture to `du -sk` exactly (147456 bytes) — reuse that fixture shape. Recall directories are recorded with their own block, so on ext4 they contribute; on APFS they're 0.
- **Determinism carries forward:** because `attribute` is order-independent, the aggregation must not reintroduce order sensitivity (e.g. sort children by size *and* break ties by path if you sort for display — but that's Task 7's rendering concern, not Task 5's totals).
