## Decisions Made During Implementation

- **The denylist is root-relative**, not absolute: component sequences anchored
  at the filesystem root, so `Windows` protects a system on `D:` exactly as on
  `C:`. A hardcoded `C:\Windows` would have covered only the common case.
- **It is not `#[cfg]`-gated per platform.** Over-denying costs a user one
  directory they could have cleaned; under-denying costs them a system
  directory. With that asymmetry the cross-platform list is both the safer choice
  and the one every CI runner exercises.
- **`is_denied` checks the raw *and* the lexically-normalised path.** See the
  finding below; the union is the only direction a denylist may move.
- **`--safe` is a silent filter, by design.** `excluded` answers "the tool
  refused something you might have expected"; `--safe` is the user's own
  narrowing. One list holding both would show a protected system directory beside
  something they asked to hide. Pinned by `the_safe_filter_records_nothing`.
- **`clean.rs` was split and the feature renamed.** Task 1 deferred this decision
  to here. Planning needs nothing from `trash`, so `clean.rs` is now always
  compiled and `trash.rs` alone sits behind the feature — renamed from `clean` to
  **`trash`**, since a feature called `clean` gating only removal misdescribes
  itself. `--no-default-features` now means "scan and plan, cannot remove".
- **`CleanOptions` embeds `DetectOptions`** rather than restating three of its
  fields, which would have to be kept in step by hand.

### The two findings worth remembering

**A parent traversal walked through the denylist.** `Path` never resolves `..`
and cannot — whether `a/b/..` is `a` depends on whether `b` is a symlink — so
`disk-tools clean /home/me/../../System` would carry the traversal into every
node path and a literal component comparison would never fire. Fixed by checking
both forms: normalising *instead* would have weakened the check, since
`/System/../Users/x` matches `System` literally and stops once resolved.

**An invariant no test covered.** A hand-applied mutation moving the `--safe`
filter ahead of the denylist left all 89 tests passing. The only combination that
distinguishes the two orders is a confirm-tier match inside a protected root —
with `--safe` off the filter is a no-op, and an auto-tier match passes it anyway.
Wrong order, and the path disappears from `excluded` too: the tool silently
declining to say it protected something. Both fixes were verified by reverting
them and watching the new tests fail.

## For Next Task

Task 5 — **the git-dirty guard**. It plugs into the pipeline `plan()` already
has.

1. **Add a variant to `ExcludeReason`**, not a second mechanism. `Excluded`
   already carries a reason and the plan already reports it; the guard is a
   `DirtyRepo` arm and an extra filter step after the denylist.
2. **`CleanOptions.allow_dirty` is carried but inert**, and documented as such at
   the field. Task 5 makes it mean something. Nothing today reads it, so its
   presence is not evidence a guard exists.
3. **The guard runs after the denylist, before `--safe`** if it is to behave like
   the denylist does — and `the_denylist_beats_the_safe_filter` is the shape of
   the test that proves an ordering invariant, since ordering bugs are invisible
   in every combination but one.
4. **§8.2.3 says the guard gates build-output categories only** (`rust-target` in
   v0.2). `Candidate.category` carries what is needed to tell.

For Task 6 (the CLI):

- **It must resolve `UserDirs`** — `home`, `local_app_data`, `app_data` — or the
  `user-caches` category matches nothing and two denylist entries go unenforced.
  `std::env::home_dir` is deprecated at our MSRV and wrong on Windows; read the
  environment variables directly.
- **`--safe` hides candidates without recording them.** Worth telling the user
  how many, which the CLI can get by planning once without the flag.
- **The `shared` marker must read as "this total may be smaller in practice"**,
  never "this will not be freed" — and its absence on Windows is not evidence of
  anything.
