## Decisions Made During Implementation

- **Directories recorded, not just recursed** — on ext4 a directory occupies a block and `du` counts it; on APFS it's 0 blocks, so omitting it is invisible on macOS but would fail Task 5's "root total == `du`" AC on Linux CI only. Verified: fixture of 7 files / 4 dirs → 11 entries, 147456 bytes; `du -sk` → 144 KiB = 147456. Exact.
- **`into_par_iter()` over subdirectories, not `rayon::scope`** (spec said scope) — same crate, same directory-level parallelism, but each subtree returns its own `Walked` and the parent concatenates, so no lock is shared.
- **Windows identity is `None`** — the decisive finding of this task. `volume_serial_number()`/`file_index()` are (a) `#[unstable(feature = "windows_by_handle")]`, nightly-only, and (b) even on nightly return `None` from directory-listing metadata: std hardcodes them in `From<WIN32_FIND_DATAW>`; they're `Some` only from an open handle. `number_of_links()` is `None` too, so we can't even cheaply find which files have links. The spec claimed "both available on std MetadataExt" — wrong twice, and it only surfaced because the Windows branch was actually compiled.
- **`--one-file-system` is Unix-only** — same root cause (no device id from a walk). A documented no-op on Windows beats a wrong guess at drive letters (which misses volume mount points anyway).
- **Long-path `\\?\` conversion lives in `size`, not the walk** — `std::fs::read_dir`/`symlink_metadata` already prefix internally (`maybe_verbatim`); the only place std doesn't cover is the raw `GetCompressedFileSizeW` FFI. An earlier draft prefixed the directory path before `read_dir`, which was redundant *and* unsound (left the per-file path that reaches the FFI unconverted — a long child name would wrongly skip).

## Deviations from Spec

1. **`rayon::scope` → `into_par_iter()`** — spec §8.2.2 amended.
2. **Directories recorded** — spec §8.2.2 recorded only files; amended.
3. **Windows identity + `--one-file-system` Unix-only** — spec §8.2.3 claimed Windows keys were available; corrected. Hardlinks double-count on Windows in v0.1 (documented; Task 4 can close it with the fclones size-collision trick — open a handle only for files whose sizes match).
4. **UNC long paths not converted** — `verbatim_if_long` handles drive-letter paths only; long UNC paths may skip. Documented v0.1 limitation in §8.2.1. **You approved skipping full UNC support.**

## For Next Task

Task 4 is **Hardlink dedup with deterministic attribution** (`core/src/dedup.rs`), depends on Task 3.

- **Input is `Walked.entries`** — each file carries `id: Option<FileId>`. Group by `id`, and within a group of >1 path attribute full `allocated` to the **lexicographically first** path, zero to the rest (§8.2.3). Sort paths before attributing — the walk order is nondeterministic under rayon, so relying on it would make dir totals flake.
- **`id` is `None` on Windows and for directories** — treat `None` as "unique, never a hardlink". So on Windows dedup is a no-op and hardlinks double-count; that's the documented v0.1 behaviour. If you want to close it, the cheap route is the fclones trick: after grouping by size, open a handle (`GetFileInformationByHandle`) only for the files whose sizes collide — a small fraction — which would add a *second* `#[allow(unsafe_code)]` and should get the same scrutiny the first did.
- **Drop the `#[allow(dead_code)]`s on `mod size`/`mod walk` when Task 5's `scan()` makes them reachable** — not before. Confirmed empirically this task: removing them now warns on the whole chain, because nothing public reaches `walk` yet.
- **Determinism has a test waiting** — Task 4's spec test `dir_totals_deterministic_across_runs` should scan twice and assert byte-identical totals; that's the guard against the parallel-order trap.
- **Verify with `just verify`**; type-check Windows with `cargo clippy -p disk-tools-core --target x86_64-pc-windows-msvc --all-targets -- -D warnings`.
