## Decisions Made During Implementation

- **`--apply` removes every candidate, tier and all**, per this spec's AC 2. The
  concept asks for per-target confirmation on the confirm tier; that tension is
  now written into the spec rather than left implicit. The mitigations are real:
  the plan is printed immediately before acting, the confirm-tier count is said
  out loud ("N of these are not regenerable — removing anyway, as asked"), and
  `--safe` excludes the tier entirely.
- **`CleanOutcome` is not a `Result`** (D5). A run that removed four of five
  succeeded four times; one verdict would lose the only detail that matters.
- **`apply_with` is a seam, not indirection.** The success arm — what lands in
  `removed`, what is added to `reclaimed` — was otherwise reachable only by
  really trashing something, leaving "how much did I free" verified solely by a
  test nobody runs by default. Same move as `git::interpret` and `env::as_path`.
- **The partial-failure integration test is Linux-only, and that was measured.**
  The fixture makes the parent `chmod 555` so the removal must fail. On macOS it
  *succeeded*, in 42 seconds: the Finder backend goes through `osascript` and is
  not bound by the parent's permissions. Linux's freedesktop backend is a rename,
  which a read-only parent really does refuse.

### What running it by hand found that the tests did not

The first `--apply` printed, immediately before deleting:

```
Dry run — nothing was removed. Re-run with --apply.
Removed 1 of 1. Freed 64.0K.
```

One report served two moments and its closing line did not. Every test called
`render_clean` directly and none knew about the `--apply` path, so nothing caught
it. Hence `Intent` — and a test that now builds `Intent::AboutToApply` and
asserts the sentence is absent.

### The four ways the report could lie, and the review that found three of them

1. **"Everything above is in the trash and can be put back"** was printed
   whenever anything failed, with **no check on `removed`**. A run that trashed
   nothing said everything was recoverable. And even in the mixed case, "above"
   sat directly under the failure list — promising exactly the items that are
   *not* in the trash. It now names what it covers and appears only when
   something moved.
2. **The freed total contradicted the dry run's.** `reclaimed` sums `allocated`,
   which a `shared` candidate overstates; the preview said "at most X, may free
   less" and the outcome said "Freed X" flatly. The outcome now carries the same
   hedge.
3. **`apply` trusted that no candidate contains another.** True of `plan()`, but
   `apply` is public over a struct with public fields. Without the guard a child
   would be attempted after its parent took it, fail, and be reported as **still
   on disk** — the report telling a user their data survived when it is in the
   trash.
4. The `Intent` bug above, found by hand rather than by review.

My first test for (3) was itself wrong: it really trashed a directory on every
`just test`, which is what every other real-trash test here is `#[ignore]`d to
avoid. Extracted `already_gone` and tested it without a filesystem.

## For Next Task

Task 8 — **documentation of the safety model**. The last task of v0.2, and the
one v0.1's equivalent proved is not a formality: it caught three factual errors
in already-written documentation. Budget for the same.

What must be documented, and what must not be overstated:

1. **Dry run is the default; `--apply` is required.** Unambiguously.
2. **Four safety mechanisms**, and they are not equal: the denylist cannot be
   overridden by any flag; the git guard is exactly what `--allow-dirty` relaxes;
   `--safe` is the user's own narrowing; the tiers decide which of those applies.
3. **The reclaimable figure is an upper bound** when anything is `shared` — and
   on **Windows the absence of that marker is not evidence of unshared content**,
   because `links` is `None` there (D10). A user comparing two machines will
   otherwise draw the wrong conclusion.
4. **Two limits that cannot be tested away**, both from Task 1: on Windows a COM
   failure inside the backend panics rather than returning, so "the summary names
   the survivors" holds only for failures the backend *reports*; and on macOS no
   automated test can prove a deletion was recoverable.
5. **The tier tension** — `--apply` removes confirm-tier candidates without a
   per-target prompt. If the README describes the tiers, it must say what
   `--apply` actually does with them.

Also worth a line: a dry run over many repositories is no longer instant (one
`git status` per repository, twice under `--safe`), and nobody has measured it on
a large tree.
