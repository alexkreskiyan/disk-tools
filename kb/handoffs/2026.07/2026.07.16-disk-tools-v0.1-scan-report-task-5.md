# Handoff: Task 5 — Bottom-up aggregation → ScanTree

## Feature Spec

[2026.07.14-disk-tools-v0.1-scan-report.md](../../specs/2026.07/2026.07.14-disk-tools-v0.1-scan-report.md)

## Completed

- `core/src/tree.rs`: `pub(crate) fn aggregate(entries: Vec<WalkEntry>, root: &Path) -> ScanNode` + private `build_node`. Folds the flat, dedup-attributed entry list into a nested `ScanNode`: a path→index map attaches each non-root entry to its `path.parent()`, the root is found by `path == root`, and `build_node` recurses bottom-up summing **own + Σ children** for both `allocated` and `apparent` (du semantics — directories carry their own block). Children are sorted by path (byte order) for a deterministic tree.
- `core/src/lib.rs`: `pub fn scan(&ScanOptions) -> ScanTree` — the crate's **sole public function** — wires `walk::walk` → `dedup::attribute` → `tree::aggregate`. The three `#[allow(dead_code)]` on `mod dedup`/`mod size`/`mod walk` are removed: `scan()` makes the whole chain live.
- `core/src/walk.rs`: fixed an orphan-drop found in review (see Decisions) — the walk now descends only into a directory it managed to record.
- 7 aggregation tests (5 planned + 2 from test-writer).

## Decisions Made During Implementation

- **Node size = own + Σ children, not Σ children alone.** §8.2.4 step 2 literally reads `dir.allocated = Σ children.allocated`, but §8.2.2's Task 3 revision and the `du -sk` parity AC require the directory's own block too. `build_node` sums own + children; on APFS the own block is 0, on ext4 it's a real block — matching `du` on both. (This is a documented spec self-correction, not a deviation.)
- **Children sorted by path (byte order) in aggregation.** The walk's order is nondeterministic under rayon; sorting here gives a reproducible tree (good for JSON/tests). The renderer re-sorts by size at display time (Task 7), so this doesn't conflict.
- **Orphan-drop fixed at the root, in `walk.rs`.** A bugs reviewer found that `walk_dir` pushed a directory to the recursion list *before* measuring it; if the directory's own measurement failed (a Windows FFI possibility), its children were still measured but its own entry was missing, so `aggregate` silently dropped the whole measured subtree (only the top dir showed in `skipped`). Fix: `subdirs.push(path)` moved inside the `Ok(entry)` arm of `match entry_for(...)`, so a directory is descended into only if its own entry was recorded. This makes `aggregate`'s orphan branch unreachable in normal operation (kept as a defensive, non-panicking fallback). Unix behaviour is unchanged (measurement is infallible there).
- **`build_node` left as plain recursion.** A reviewer flagged unbounded recursion → stack overflow on a pathologically deep tree, contradicting "never fails". Declined: `walk_dir` is itself recursive with the same depth bound and would overflow first, and real filesystem `PATH_MAX` limits prevent creating a deep-enough tree. Converting only `build_node` to an explicit stack would be inconsistent and buy nothing.

## Deviations from Spec

None. §8.2.4 implemented as clarified (own + Σ children — see Decisions). The walk.rs orphan fix tightens Task 3 behaviour (a directory whose own size can't be measured is no longer descended into) but doesn't change any Task 3 AC — on unix, directory measurement is infallible, so every directory is still recorded and descended.

## For Next Task

The core is now feature-complete for v0.1 scanning: `disk_tools_core::scan(&ScanOptions) -> ScanTree` produces the full size-annotated tree. The remaining tasks are all in the **CLI crate** (`cli/`), which is still the Task-1 placeholder.

- **Task 6 — CLI args → ScanOptions** (`cli/src/args.rs`, `cli/src/main.rs`), depends only on Task 1. clap derive; `<PATH>` required (never scan CWD); `--min-size` suffix parsing (1M → 1048576); nonexistent path errors *before* scanning; `--help` lists all six flags. It maps args → `ScanOptions` but has nothing to render yet — the human report is Task 7.
- **Task 7 — Tree renderer** (`cli/src/render/tree.rs`), depends on Task 5 **and** Task 6 — the first point the tool actually prints something. It consumes `ScanTree`: choose ranking unit (`apparent` ? apparent : allocated), sort each node's children by that unit descending, emit until `-n` exhausted, prune deeper than `--depth` and below `--min-size` — **totals shown stay full-subtree totals** (§8.2.5). The tree is already deterministic (children path-sorted here), so the renderer only needs to re-sort by size for display.
- `ScanNode`/`ScanTree`/`SkippedEntry`/`SkipReason`/`ScanOptions` are all `pub` from the crate root; `scan` is the only function to call. Directory nodes carry their own block in `allocated` (0 on APFS) — don't double-count it when rendering.
