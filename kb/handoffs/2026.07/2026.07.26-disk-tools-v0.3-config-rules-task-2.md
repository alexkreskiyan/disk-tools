# Handoff: Task 2 — The config file

## Feature Spec

[v0.3 — configuration and declarative rules](../../specs/2026.07/2026.07.26-disk-tools-v0.3-config-rules.md)

## Completed

- `cli/src/config.rs` — `locate`, `load`, `parse`, `init`, `DEFAULT_CONFIG`, the
  file's own schema (`FileConfig`, `RuleEntry`) and its conversion to
  `core::Rule`.
- `--config <PATH>` as a global flag, and a `config init [--force]` verb.
- `Args::resolve` takes an `Environment` (clock, user dirs, config, config path)
  and is fallible again: the globs being compiled are now partly the user's.
- The config is loaded **before** anything is scanned, and a config that cannot
  be understood stops the program — the rules decide what may be deleted.

## Decisions Made During Implementation

- **`root = "*"` means "wherever the scan goes".** AC 11 wants the written file
  to parse back to `builtin_rules()`, and AC 9 wants a missing `root` to be an
  error — but three built-ins are deliberately unrooted. Writing `root = "~"` for
  them would have made `config init` silently narrow what `clean /var/tmp` finds.
  A required field with a value meaning "anywhere" satisfies both.
- **`$XDG_CONFIG_HOME` wins on every platform.** Exporting it is a user saying
  where their configuration lives; overruling that on Windows because the
  platform has a different habit would be worse than the inconsistency.
- **An absent default file is fine; an absent `--config` file is not.** The tool
  ships working defaults, so no config is ordinary. A path the user *named* and
  that is not there is a typo, and substituting defaults would leave them
  cleaning under rules they never wrote.
- **The `config` verb does not read the config.** Loading first made
  `--config <new path> config init` fail on the absence of exactly the file it
  was asked to create. Found by the integration test, not by reasoning.
- **`deny_unknown_fields` had to go.** It makes serde fail before
  `serde_ignored` has anything to observe; the two cannot both be used, and AC 8
  wants a warning.
- **`serde_ignored`'s paths are cleaned before display.** It emits a `?` segment
  per `Option` layer, so a misspelt key in `[[rules]]` came back as
  `rules.?.0.tyer` — a path the user cannot find in their file.
- **`#[cfg_attr(not(test), expect(dead_code, …))]`** on the three settings
  sections. `expect` rather than `allow` so Task 3 wiring them makes the
  attribute itself a warning; scoped to `not(test)` because the tests already
  read them, which would make the expectation unfulfilled — and so an error — in
  the test build.

## Deviations from Spec

- **`root = "*"`** — the AC 9 / AC 11 reconciliation above. The spec's §8.4
  template is updated to match.
- **The `[scan]` / `[report]` / `[clean]` sections are parsed and validated but
  not yet wired**, which is what Task 3 is for. Their Task 2 consumers are the
  schema tests; a bad `[report] min-size` is nonetheless rejected at read time
  rather than carried as an unparsed string.
- **One incidental fix outside the task.** The dry-run report said "N more
  candidates are below `--min-size`" even when the threshold came from a rule's
  own `min-size` — a flag the user never passed. It now names both. Found by
  running the binary against an edited config. The finer fix — counting the two
  separately, as `filtered_out` and `too_small` already are, because the remedy
  differs (lower the flag vs edit the file) — is left for Task 3 or 6.

## For Next Task

**Task 3 (precedence) has its inputs ready.** `Config.scan` / `.report` /
`.clean` are parsed, validated and all-`Option`. Wiring each one removes its
`cfg_attr(not(test), expect(dead_code))`, and the build will insist on it — an
unfulfilled expectation is an error under `-D warnings`.

`ReportSettings.min_size` is already a `u64`, parsed at read time by the same
`parse_size` the flag uses. `[report] depth = 0` means unlimited in the file but
`ScanOptions.depth` is `Option<usize>`; the merge has to translate, not copy.

**Gotchas discovered:**

- `toml::Deserializer::new` is deprecated in toml 1.x — `Deserializer::parse`,
  and it returns a `Result`.
- `#[expect(...)]` is evaluated per build configuration. An attribute that is
  correct for the binary can be an error for the test build of the same file.
- `Args::resolve` is fallible again, and `Mode` now has a third variant. Any new
  `match` on it needs the `ConfigInit` arm.
- Integration tests must pass `--config` at a temp path. Without it they would
  read — and `config init` would write — the real config of whoever runs them.
