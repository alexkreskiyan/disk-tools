## Decisions Made During Implementation

- **`plan()` now reads the filesystem, and the docs say so.** The module doc
  claimed "Nothing here touches the filesystem"; the guard makes that false.
  Injecting an oracle to preserve purity was rejected — an abstraction for one
  boolean, and it would move the guard's real behaviour out of the tests that
  matter. The claim was narrowed to the one that is still true and still
  load-bearing: `plan()` **writes** nothing, proved by Task 4's
  `plan_writes_nothing`. Both the module doc and `plan()`'s own doc were
  corrected; the second was caught by review after the first was fixed.
- **`RepoState` has no `NoRepo` variant.** `enclosing_repo` returns `Option`, so
  a variant would be a second way to say the same thing — and two ways to say it
  is how they come to disagree.
- **Everything unknown is `Dirty`, in one fall-through arm** rather than a list
  of cases. A missing binary, a corrupt repository, a failure nobody has thought
  of: the safety argument is "the tool does not delete what it cannot vouch for",
  and a list is something a future change can forget to extend.
- **The guard is scoped to build output** (`rust-target`). `node_modules` is
  restored by a lockfile install rather than rebuilt from the working tree, so a
  dirty repository says nothing about it; guarding it would refuse cleanups for
  an unrelated reason.
- **One `git status` per repository, not per candidate.** Sibling projects would
  otherwise each spawn a process.

### The five ways a dirty repository could have read as clean

Every one of these fails in the same direction — the guard stays silent and the
build output gets removed:

1. **A relative candidate path.** `Path::ancestors` stops at `""`, so
   `disk-tools clean target` from inside a repository never reaches the `.git`
   above the working directory. `validate_root` does not make the root absolute.
   Fixed with `std::path::absolute`, which anchors lexically and resolves no
   symlink — unlike the banned `canonicalize()`.
2. **An inherited `GIT_DIR` / `GIT_WORK_TREE`.** These override `-C` entirely, so
   under a git hook or an IDE integration git would answer about a different
   repository. Now removed from the child's environment.
3. **`status.showUntrackedFiles = no`.** With that in the user's config,
   brand-new files produce no porcelain output at all — genuine uncommitted work
   reading as clean. `--untracked-files=normal` is now explicit. `normal` rather
   than `all`: enough to override the config, without enumerating every file
   inside an untracked directory.
4. **A broken `.git` symlink.** `exists()` follows links and returns `false`, so
   the directory looked repository-less and the walk continued past it. Now
   `symlink_metadata`.
5. **A test that passed because its fixture failed.** The fixtures skipped on
   *any* `git init` failure — an unwritable `$HOME`, a sandbox refusing to spawn.
   Seven tests would have counted as passes while asserting nothing. Only
   `ErrorKind::NotFound` now skips; anything else panics.

## For Next Task

Task 6 — **the `clean` subcommand and dry-run report**. The engine is complete;
this is the first task that makes any of it reachable.

What it owes the core:

1. **Resolve `UserDirs`** — `home`, `local_app_data`, `app_data`. Without it
   `user-caches` matches nothing and two denylist entries go unenforced.
   `std::env::home_dir` is deprecated at our MSRV and documented as wrong on
   Windows; read `$HOME` / `%USERPROFILE%` / `%LOCALAPPDATA%` / `%APPDATA%`.
2. **Supply `now`**, paired with the parsed `--older-than` in an `Age`. The core
   reads no clock.
3. **Build `CleanOptions { detect, safe_only, allow_dirty }`** — nested, not flat.

What the report must convey:

- **Two exclusion reasons, and they are not equivalent.** `Denylisted` cannot be
  overridden by anything; `DirtyRepo` is exactly what `--allow-dirty` is for. A
  report that shows them identically invites the user to reach for a flag that
  will not help.
- **`--safe` hides confirm-tier candidates without recording them** — a
  deliberate choice, since it is the user's own narrowing rather than a refusal.
  Worth telling them how many, which the CLI can get by planning once without it.
- **The `shared` marker means "this total may be smaller in practice"**, never
  "this will not be freed" — and its absence on Windows is not evidence of
  anything.
- **The guard costs a `git status` per repository.** On a tree of many Rust
  projects a dry run is no longer instant; the spinner already exists.

Still open:

- **The `clean.rs` split may need revisiting at Task 7**, as flagged in Task 4.
  `apply()`, `CleanOutcome` and progress reporting all land in `trash.rs`.
- **Three invariants have no mutation coverage** (above). If those tests are ever
  touched, they are the only thing standing behind the behaviour.
