## Decisions Made During Implementation

- **The global rayon pool, not one per measurement.** A pool per walk would add
  N threads for every directory entered. The real cost of sharing is not threads
  but queueing: a cancelled walk that keeps running occupies the cores its
  replacement is waiting for, which is why the flag is read as often as it is.
- **The cancel flag is read every 512 directory entries**, not only on entering a
  directory. A directory of a hundred thousand files is a hundred thousand
  `stat` calls, and stopping only at the end of that is not stopping.
- **Percentages are against the sum of what is known**, not a parent total. That
  total would cost a second walk of the level above, and nobody asked for it. A
  directory still being measured is excluded from both sides of the fraction: a
  denominator moving under the settled rows would have every percentage on
  screen drifting for a reason none of them show.
- **The spinner frame comes from the clock.** `event::poll` wakes on a keypress
  as well as on its timeout, so a per-frame counter would race ahead while the
  user typed and stall while they did not.
- **Re-sorting only on completion, and only when size is the order in force.**
  Sorting on every climbing figure would have rows swapping places continuously.

## Deviations from Spec

**One, and it is the task's central design decision reversed.**

The spec said a size in progress must *stop* when restarted, "rather than
surviving in the background". Implemented that way, then tested on a real home
directory, it is wrong twice over:

- Stepping into a directory cancelled the walk of its neighbours, so stepping
  back out started from nothing. The same number was computed twice and never
  finished.
- The walk of `~` and the separate walks of `~/Projects`'s children were the
  same tree measured twice, concurrently, through one rayon pool.

Cancellation is now only what the user asks for (`r`) and what exit requires.
What made cancel-on-navigate look necessary — a stale answer landing on the
wrong row — is solved instead by **keying every result on its absolute path**,
which removed the generation counter entirely.

Also: the spec named `cli/src/ui/paint.rs`; the file is `cli/src/ui/layout.rs`,
which Task 2 had already created for the same purpose. Task 4's key-files entry
was corrected to match.

## What the four rounds found

Every one of these was invisible to the test suite and obvious within a minute
of real use.

1. **The UI froze.** `start` joined the worker from inside key handling.
2. **Entering a measured directory recomputed it.** `measure` kept one number and
   dropped everything it had walked through to get it.
3. **Navigating cancelled work and lost it.** See Deviations.
4. **An outer walk raced the inner ones.** Fixed by reporting each directory as
   it finishes, and by not queueing a path whose ancestor is already being
   walked.

Rounds 2 and 4 are the same mistake at different scales: the walk had the answer
and threw it away.

**Gotchas discovered:**

- `Path::ends_with("")` is true for every path, so it is useless as a test
  filter. Two assertions were written with it in this task, both passing without
  checking anything.
- **"The inner answer arrives before the outer walk ends" is not a CLI test.**
  Written there it means racing an 800-directory walk to observe it mid-flight —
  it failed roughly one run in four. It belongs in the core, where report *order*
  is guaranteed by construction (a directory reports after its children) and can
  be asserted without a clock: `a_directory_is_reported_before_the_one_above_it`.
- A 200-level nested directory is a path the filesystem refuses (`File name too
  long`). Test fixtures that need a big tree should be wide.
- A test helper that drains a channel cannot be called twice — the first call
  discards the second's answer.
- `rtk` filters test stdout; `rtk proxy cargo test … --nocapture` is how to see
  the `show` diagnostic's screen.
