## Decisions Made During Implementation

- **The crate is fine.** `trash` 5.2.6 builds on macOS in 3.4 s on the `objc2`
  stack; the reported issue came from the old `cocoa`/`objc` one. Files land in the
  Trash with "Put Back", confirmed visually.
- **Feature-gated the dependency** (`default = ["clean"]`) rather than making it
  unconditional, which the plan had proposed. A code reviewer pointed out the
  manifest already promises `serde` consumers "pay nothing", and a scan-only
  consumer should not compile `objc2` for a capability it never calls. Default-on
  keeps `cargo test` honest; `--no-default-features` leaves only `rayon`.
- **Renamed `to_trash` → `move_to_trash`.** `to_*` denotes a cheap conversion in
  Rust, not a side-effecting operation. Cheap to change now, expensive after Task 7
  depends on it. The spec's wrapper-shape note was updated to match.
- **`mod clean` is private**, like `options` and `tree`, with a re-export — `pub mod`
  would have given the type two public paths where every other type has one.
- **The skip branch became a named helper.** Both smoke tests are `#[ignore]`, so
  their "no backend" arm was never executed anywhere. `trashed_or_skipped` gives it
  one implementation and one always-running test.
- **`just smoke-trash` runs in CI.** It moves real files into an ephemeral runner's
  trash, which is how the three-platform timings were obtained at all — and it is
  the guard against the Windows panic below.

## For Next Task

Task 2 — **age and sharing signals through the model**. No dependency on this task.

Three findings here change later tasks, and the spec has been updated with each:

1. **Windows trashing is 7,000× slower than Linux** — 3.1 s vs 443 µs for 10,000
   files; macOS ~170 ms. Task 7's progress reporting is therefore **required**, and
   its granularity is fixed at **per candidate**: the backend reports no per-file
   completion, so a percentage within one tree is not obtainable.
2. **One failure mode is not catchable.** `trash` 5.2.6 `unwrap()`s
   `CoCreateInstance` on its Windows delete path (`src/windows.rs:42`) where the
   same call in `purge_all`/`restore_all` uses `?`. A COM failure panics and no
   wrapper can convert it — exactly the "one bad entry aborts the run" mode this
   module's contract rules out. It did **not** fire on `windows-latest`, so it is
   rare rather than safe. Worth reporting upstream. Task 7's "names the survivors"
   criterion holds for every failure the backend *reports*, and not for this one.
3. **On macOS the safety promise is unprovable by test.** `~/.Trash` needs Full Disk
   Access; `trash::os_limited::list()` does not exist for macOS. A test can assert
   only that the original path is gone — true of an unrecoverable delete too. Linux
   and Windows could assert more if Task 7 wants a stronger check.

Smaller, but worth knowing:

- **Headless Linux needs nothing** — no desktop, no dbus, no portal. Task 7's
  integration tests can exercise the real apply path on Linux CI rather than being
  `#[ignore]`d.
- **`plan()` will land inside the `clean` feature** (Task 4), since it lives in
  `clean.rs`. Planning needs nothing from `trash`, so a consumer wanting to plan but
  not apply would need the module split. Named in Task 4's notes; not worth doing
  pre-emptively.
- **MSRV is now coupled.** `trash` requires exactly 1.85.0, as we do. A bump in the
  crate breaks the `msrv` CI job immediately — that job is the early warning and
  should not be relaxed.
