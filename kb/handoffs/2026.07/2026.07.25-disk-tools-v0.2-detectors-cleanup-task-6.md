## Decisions Made During Implementation

- **`--apply` refuses rather than no-ops.** Removal is Task 7. A flag whose
  entire purpose is deletion, silently accepted and then ignored, would leave a
  user believing their disk had been cleaned — the one behaviour that cannot
  ship even for one task. Non-zero exit, and an integration test asserts the
  fixture is untouched.
- **`Args.root` became `Option`,** because clap cannot require a positional a
  subcommand replaces. The guarantee it protected moved into `Args::resolve`,
  which raises clap's own `MissingRequiredArgument` — same message shape, same
  exit code.
- **The `--safe` hidden count comes from a second `plan()`.** The core does not
  record `--safe`-filtered candidates in `excluded`, deliberately: that list is
  for the tool's refusals, and `--safe` is the user's own narrowing. Planning
  twice keeps that boundary intact at the cost of a second git-guard pass.
- **`m` is 30 days and `y` is 365** in `--older-than`, documented at the parser
  because `m` could be read as minutes. A bare number is rejected: `90` could
  mean seconds as easily as days, and a deletion rule is no place to guess.

## Deviations from Spec

- The three above.
- `parse_duration` offers no unit below a day — the rule exists to find things

- 17 tests beyond the spec's list, four of them written in response to review.

### The finding worth remembering

Two reviewers reached the same line from opposite directions. The bug reviewer
found that `unfiltered.candidates.len() - planned.candidates.len()` can go
negative — each `plan()` re-runs the git guard against the world as it is *then*,
so a repository whose state changes between the two calls can leave the
unfiltered plan shorter. On `usize` that wraps silently in a release build, and
the report would have announced **eighteen quintillion hidden candidates**. The
test verifier independently found the same line had **0% coverage**: no
integration test ever ran `clean --safe`.

A real bug and its invisibility, found separately and pointing at the same
place. Fixed with `saturating_sub` — a count low by one in a rare race is the
cheaper wrong answer — plus an integration test, verified by swapping the
operands and watching it fail.

Two smaller ones worth noting:

- **`HOME` was preferred over `%USERPROFILE%`.** Under Git Bash or MSYS2 `HOME`
  holds `/c/Users/alex`, which Windows does not consider absolute and which
  nothing the scan walked will equal. Now a `#[cfg]` pair. (The reviewer read
  this as disabling a never-touch rule; it does not — the affected denylist
  entry is macOS-shaped and `%APPDATA%` is read separately. What broke was
  `user-caches` detection.)
- **A test that checked a copy of itself.** `an_empty_environment_variable_is_not_a_home`
  called a local helper duplicating `read`'s logic, which is why three of four
  surviving mutants sat in that function. The production code now splits lookup
  from decision, and the test drives the real one.

## For Next Task

Task 7 — **apply**. The only task in the project that removes anything.

1. **`--apply` currently refuses in `run_clean` (`main.rs`).** That branch is
   where the real implementation goes; `apply_is_refused_until_it_exists` will
   need replacing, not deleting — its fixture check is the shape the new test
   wants.
2. **Progress is required, per candidate.** Task 1 measured 10,000 files at
   443 µs on Linux, ~170 ms on macOS and **3.1 s on Windows**, and the backend
   reports no per-file completion. The spinner in `scan_or_report` is the
   existing pattern; a per-candidate bar is the shape needed.
3. **`CleanPlan.candidates` is already sorted and non-overlapping,** so applying
   in order removes no path twice and no parent before a child it contains.
4. **The exit code must be non-zero on partial failure**, and the summary must
   name the survivors — with the caveat Task 1 recorded: one Windows failure
   mode panics inside the backend and cannot be caught.

Still open:

- **`clean.rs` versus `trash.rs`** — Task 4 split them on the pure/effectful
  line and flagged Task 7 as the moment to re-check. `apply()`, `CleanOutcome`
  and progress all land in `trash.rs`.
- **A dry run over many repositories is no longer instant** — one `git status`
  per repository, twice when `--safe` is used. Nobody has measured it on a large
  tree; worth a number if it becomes noticeable.
