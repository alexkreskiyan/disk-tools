# disk-tools

## Overview

`disk-tools` is a cross-platform (macOS/Linux/Windows) console disk-utilities suite in Rust. Its first and anchoring capability is finding what's eating disk space — largest files and directories — and, subsequently, safely reclaiming it. It aims to be as fast as the best-in-class Rust scanners (diskus/dust) and, longer-term, as ergonomic as an interactive browser (dua-cli), behind one binary named `disk-tools`. **v0.1 ships the scan + report; the interactive browser and cleanup are later phases.**

## Core Idea

Scan a directory tree in parallel, computing **real on-disk (allocated) size** per file, aggregate bottom-up per directory, and surface the biggest consumers as a **dust-style size-sorted tree** (largest dirs and files, indented with proportional bars), limited by `-n` and `--depth`. A hybrid UX prints this fast report by default; an optional interactive mode to review and clean comes later. Cleanup is safety-first: only an explicit safe-list is auto-cleaned, everything else is manual, and deletions go to the OS trash, never `rm`. Everything is built on a reusable `disk-tools-core` library so later detectors (junk, old, duplicates) and a TUI are additive. **v0.1 scope = scan + tree report only.**

## Key Components

### 1. `disk-tools-core` (library crate)

The engine. Responsibilities:
- **Walker** — parallel recursive traversal via `std::fs::read_dir` + `rayon::scope` (true diskus-style), living in a `core::walk` module. No-follow-symlinks by default; optional `same_file_system` boundary stop (own `st_dev` check). `walkdir` is **not** used: it is a *sequential recursive* iterator and cannot sit inside a parallel recursion (only `max_depth(1)`, i.e. `read_dir` with overhead) — diskus doesn't use it either. Since symlinks aren't followed, loop detection is a non-issue. (`ignore::WalkParallel` also deliberately *not* used for the size scan — its gitignore filtering would skip exactly the `target/`/`node_modules` we want to find; reserved for the future junk detector with gitignore off.)
- **Sizing** — per-file allocated size (Unix `blocks()*512`; Windows `GetCompressedFileSizeW` via `windows-sys`), plus apparent size. Implemented in-crate: the `filesize` crate was rejected because its Windows path calls `canonicalize()` on every file, which this project forbids. Uses `DirEntry::file_type()` to avoid speculative `stat`; one metadata call per real file.
- **Dedup accounting** — track `(dev, inode)` / `(volume, file_index)` so hardlinks count once. A cross-directory hardlink is attributed to the **lexicographically first** of its paths, resolved in a post-collection pass, so directory totals sum to the root total *and stay identical across runs*. ("First occurrence in the walk" — the diskus/ncdu framing — is nondeterministic under a parallel walk and would make dir totals drift run-to-run.) (nlink-aware "reclaimable size" is out of MVP scope — see §4.)
- **Aggregation** — bottom-up subtree totals, producing a size-annotated tree. `-n`, `--depth` and `--min-size` are **display-time** filters applied at render, never during aggregation — otherwise the totals would lie.
- **Error policy** — permission-denied / vanished-file (TOCTOU) entries are **collected as data** into the result (path + reason), never fatal. The core does not log or print — presenting skipped entries is the frontend's job (keeps the lib free of logging-framework decisions).
- **Model types** — a `ScanNode`/`ScanTree` model (`path`, allocated + apparent size, `is_dir`, `children`) plus a skipped list and size-unit formatting. This size-annotated tree drives the dust-style report and JSON output now, and the future TUI reuses the same tree (navigable/expandable) rather than needing a separate model.

### 2. `disk-tools` (binary crate — CLI frontend)

Thin `clap` v4 derive frontend over the core. v0.1 surface:

```
disk-tools <PATH> [-n 20] [--min-size 0] [--depth N] [--apparent] [--one-file-system] [--json] [--verbose]
```

- `<PATH>` — **required** (no implicit CWD scan — avoids accidental huge scans).
- `-n` — max entries shown (default 20).
- `--min-size` — hide entries below this size (default 0). **Display filter** — parent totals unaffected.
- `--depth` — limit **display** depth, exactly like `du --max-depth`: traversal is always full, so shown directory totals still reflect their whole subtree. Default unlimited.
- `--apparent` — rank by apparent size instead of allocated.
- `--one-file-system` — don't cross filesystem boundaries.
- `--json` — machine output instead of the human tree.
- `--verbose` — list every skipped path (default: count + first 10).

Default output is the dust-style size-sorted tree with proportional bars, sized to the terminal (`terminal_size`, fixed fallback when piped). `indicatif` spinner during scan. **Stream discipline:** JSON goes to stdout; the spinner and skipped summary go to stderr, so `--json` output stays parseable when piped. `ArgGroup` reserves report-vs-interactive exclusivity for later.

*Forward-compat note:* the post-MVP `disk-tools clean` subcommand (§4) introduces a subcommand-style CLI. When that lands, v0.1's bare `disk-tools <PATH>` either becomes the default subcommand or migrates to `disk-tools scan <PATH>` — decided then; it does not affect the v0.1 surface above.

### 3. Detectors (post-MVP modules in core)

**Not in v0.1** — MVP does large-files inline over the walk; do not introduce the abstraction early. Later: a pluggable `Detector` trait over the walk covering junk-patterns (marker-aware: `node_modules`, `target/`+`Cargo.toml`, `__pycache__`, caches), old/forgotten (atime/mtime threshold), duplicates (staged size → hardlink-collapse → xxh3-128 partial → blake3 full, per fclones).

### 4. Cleanup engine (post-MVP)

Invoked as a dedicated subcommand: `disk-tools clean <PATH> [--safe] [--apply] [--allow-dirty]`.

**Candidate sources** — what can be cleaned comes from: (a) the detectors in §3 (junk / old / duplicates), (b) entries a user selects in the report/TUI, or (c) the safe-list categories below.

**Safe-list = named built-in categories**, each backed by a marker-aware detection rule (§3):

| Category | Matches | Marker required |
|----------|---------|-----------------|
| `rust-target` | `target/` | sibling `Cargo.toml` |
| `node-modules` | `node_modules/` | none (unambiguous) |
| `pycache` | `__pycache__/`, `*.pyc` | none |
| `user-caches` | `~/Library/Caches`, `~/.cache`, `%LOCALAPPDATA%\Temp` | none (user-scoped only) |

Categories ship with **built-in defaults** in v0.2 — config is not required to clean. Once config lands (v0.3, §5) it toggles categories on/off; it never invents new deletion rules.

**Two tiers:**
- **Auto** (`clean --safe`) — only safe-list categories are eligible; these are regenerable, so they can be removed without per-item confirmation.
- **Manual** — everything else (large files, old files, duplicates) requires explicit per-target confirmation; never auto-removed.

**Dry-run / apply:** dry-run is the default — it prints what *would* be removed and the reclaimable size. Nothing is touched without `--apply`. On apply, entries always move to the **OS trash** (`trash` crate), never `rm`.

**git-dirty guard:** refuse by default to clean a build directory whose owning project has uncommitted VCS changes (you may be mid-work); override with `--allow-dirty`.

**Never-touch denylist:** system caches (`/Library/Caches`, no tilde), `~/Library/Application Support` / `%APPDATA%`, `/System` and Windows system dirs. Virtualenvs (`venv/`, `.venv/`) are **confirm-tier**, never auto (recreation is less deterministic than a lockfile install).

**Trash caveats:** trashing a huge tree (e.g. `node_modules` with 100k+ files) can be slow or fail on some volumes; surface progress and fall back to reporting the failure rather than a partial silent delete. Smoke-test the `trash` crate on macOS before relying on it (see Constraints).

### 5. Configuration (post-MVP, optional)

**Location — XDG everywhere:** `$XDG_CONFIG_HOME/disk-tools/config.toml`, falling back to `~/.config/disk-tools/config.toml` on **both** macOS and Linux; `%APPDATA%\disk-tools\config.toml` on Windows. `directories::ProjectDirs` is deliberately **not** used — it resolves macOS to `~/Library/Application Support/…`, which is not where CLI users look.

**Discovery:** one global config only, plus an explicit `--config <path>` override (that flag ships with config support, not in v0.1). No project-local config file — no merge rules, no surprises.

**Precedence:** CLI flags > config file > built-in defaults.

**Schema sketch:**

```toml
[scan]
excludes = ["**/Trash/**"]      # paths/globs never walked
min-size = 0
one-file-system = false

[report]
n = 20
apparent = false

[clean]
# safe-list category toggles (§4) — enable/disable only, no new deletion rules
rust-target = true
node-modules = true
pycache = true
user-caches = false
```

There are **no scan roots** — `<PATH>` is always an explicit argument (§2).

**Where it lives:** config loading/parsing sits in the **CLI crate**; `disk-tools-core` takes an explicit options struct and knows nothing about TOML or config paths (keeps the lib/bin boundary from §1).

**Validation:** `serde` with `#[serde(default)]` (works with zero config) and `#[serde(deny_unknown_fields)]` (typos surface as errors rather than being silently ignored).

### 6. Interactive TUI (post-MVP)

`ratatui` + `crossterm` frontend over the same core: navigable tree, mark-to-delete, confirm. Background scan thread + channel keeps the render loop responsive. Reference UX: dua-cli / ncdu.

## Roadmap

Sequencing follows the original goal — *find the junk **so you can clean it*** — so the cleanup path comes before ergonomics.

| Version | Scope | Blocked by |
|---------|-------|------------|
| **v0.1** | Scan + dust-style tree report (§1, §2) | — |
| **v0.2** | junk-pattern + old-file detectors (§3) + cleanup engine (§4) on built-in safe-list defaults | junk detection (safe-list categories *are* marker-aware junk rules) |
| **v0.3** | Config (§5) — category toggles, excludes | cleanup (nothing worth configuring before it) |
| **v0.4** | Interactive TUI (§6) | cleanup (mark-to-delete needs it; without it the TUI is just a browser) |
| **v0.5** | Duplicate detector (§3) | cleanup (deleting duplicates needs the engine) |

**Hard dependencies:** `clean --safe` ← junk detection · TUI mark-to-delete ← cleanup engine · duplicate removal ← cleanup engine. Config is *not* a blocker — v0.2 ships built-in category defaults.

**Relative cost:**
- *old-files* — nearly free: v0.1 already fetches metadata per file, so this only adds an mtime threshold. Cheap enough to ride along with v0.2.
- *junk-patterns* — moderate: marker-aware rules per category.
- *duplicates* — most expensive: the staged size → hardlink-collapse → xxh3-128 → blake3 pipeline plus device tuning. Deliberately last.

The tree model already exists in v0.1 (§1), so the TUI is cheaper than it would have been over a flat model.

### Distribution — deferred

Orthogonal to the feature roadmap, and **deliberately postponed** (decided
2026-07-25): while the tool is used by its author, `just release` plus
`cargo install --path cli` is enough. Publishing only becomes worth its cost when
someone else has to install it.

What it will take, when that day comes:

| Blocker | Detail |
|---|---|
| No licence | No `LICENSE` file and no `license` field. Rust convention is `MIT OR Apache-2.0` |
| Manifest metadata | `description`, `license`, `repository`, `readme`, `keywords` are absent from all three `Cargo.toml`s; crates.io rejects a publish without `description` + `license` |
| `disk-tools-core` is a path dependency | Needs `version` alongside `path`, and core must be published **before** the CLI |
| No release automation | CI only verifies; there is no tag-triggered workflow, no cross-built binaries, no `git tag` at all |

Routes, cheapest first: **GitHub Releases** with cross-built binaries (no Rust
toolchain needed by the user) → **crates.io** (`cargo install disk-tools`) →
**Homebrew tap** with a formula pulling from Releases. `cargo-dist` generates the
release workflow, the cross-builds, a `curl | sh` installer, the Homebrew formula
and a `cargo-binstall` manifest from one config, covering the first and third in
one step.

Both crate names — `disk-tools` and `disk-tools-core` — were free on crates.io as
of 2026-07-25.

## Considerations

**Trade-offs**
- core-lib + CLI upfront costs a bit more structure now; pays off for TUI/dedup and testability.
- Allocated vs apparent size: report allocated by default (matches `du`), expose apparent as an option.
- Walker chosen: `read_dir`+`rayon::scope` (diskus-proven), as a plain `core::walk` module — not a trait abstraction (no second walker to swap in). `walkdir` rejected: sequential recursive iterator, incompatible with per-directory parallel recursion. `ignore` rejected: respecting `.gitignore` would hide the build artifacts we specifically want to surface.

**Constraints / risks**
- **APFS COW clones** can't be cheaply detected → sizes may overcount shared blocks; document as known limitation.
- `trash` crate: one downstream report of a macOS build issue → smoke-test on macOS before committing to it. Cleanup is **v0.2** (the next version after MVP), so this check is near-term, not deferred.
- Windows long paths (`MAX_PATH`): avoid `canonicalize()`; walk raw paths, add `\\?\` defensively on error.
- Cross-platform CI needed (macOS/Linux/Windows) to catch per-platform metadata differences early.
- **Memory scaling**: the dust-style tree report requires retaining the size-annotated directory tree in memory (also needed for dir subtree totals and the future TUI). A files-only flat report could stream through a bounded heap (near-constant memory), but that's not the chosen v0.1 output — accepted trade-off; watch memory on whole-volume (`/`) scans of millions of files.

**Dependencies (MVP):** `rayon`, `clap` (derive), `indicatif`, `terminal_size`; `windows-sys` (Windows-only, for `GetCompressedFileSizeW`); `tempfile` (dev). **Not `walkdir`** — the parallel walk is built on `std::fs::read_dir` + `rayon::scope` directly (see §1). **Not `filesize`** — its Windows implementation canonicalizes every path, which §1 forbids; on Unix it wraps a single `blocks()*512`. Later: `blake3`, `xxhash-rust`, `ratatui`, `crossterm`, `trash`, `serde`, `toml`, and `etcetera` (XDG strategy) — or a minimal manual `$XDG_CONFIG_HOME`/`%APPDATA%` resolution — for config paths. **Not** `directories`/`dirs`: both follow the macOS platform convention (`~/Library/Application Support`), which conflicts with the XDG-everywhere decision in §5.

## Resolved Decisions (2026-07-14 review; revised during spec-writing)

- **Walker**: `std::fs::read_dir` + `rayon::scope` (not `walkdir`, not `ignore`).
- **Ranking unit**: allocated by default; apparent via `--apparent`.
- **Report**: dust-style size-sorted tree of the largest entries (dirs + files), limited by `-n` and `--depth`.
- **Reclaimable size**: deferred to the cleanup engine (§4); MVP ranks by size only.
- **CLI**: `<PATH>` required (no implicit CWD); `-n 20` caps shown entries; `--min-size 0`; `--depth` limits **display** depth (traversal always full, `du --max-depth` semantics); `--verbose` lists all skipped paths.
- **Display vs aggregation**: `-n`, `--depth`, `--min-size` are all render-time filters — never applied during aggregation, so totals stay truthful.
- **Cross-dir hardlink**: attributed to the **lexicographically first** path (deterministic under parallelism; dir totals sum to root total).
- **Streams**: JSON → stdout; spinner + skipped summary → stderr.

## Open Questions

- None blocking MVP. Revisit when specifying the cleanup engine: reclaimable-size computation (full-fs link census vs `nlink`-vs-seen heuristic) and its performance cost.

*Raised and resolved while specifying v0.2 (2026-07-25). Full reasoning in that spec's §2 and §7:*

- **atime or mtime** for the old-file rule? §3 says "atime/mtime". → **mtime.** `relatime`/`noatime` are widespread mount defaults, which makes atime least reliable on exactly the caches the rule exists to find.
- **What default age, under what flag?** §3 names no threshold. → **`--older-than <DURATION>`, opt-in with no default.** An always-on age rule would bury the safe-list candidates under confirm-tier noise on the first run.
- **Reclaimable size and hardlinks.** → **Mark, don't solve.** `nlink` rides free on metadata already fetched, so candidates containing multi-link files are flagged and the total is reported as an upper bound. Only one of three hardlink cases actually over-reports; distinguishing it exactly still needs the deferred link census. Two signals do it: the link groups `dedup` already builds (which paths in this scan share an inode — available on both platforms) and `nlink` (how many names exist in total — Unix only, since `FILE_ID_BOTH_DIR_INFO` carries no link count). Their difference is the number of links outside the scan, so on Unix the answer is exact; on Windows only in-scan sharing is visible.
