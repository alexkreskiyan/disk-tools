# Plan: parallelise the per-directory walk behind an entry-count threshold

Not scheduled. Recorded so the measurements behind it are not repeated, and so
the obvious-but-wrong version of this change is not attempted.

Full numbers and method: [the benchmark note](../../benchmarks/2026.07/2026.07.25-v0.1-scan-performance.md).

## The defect

`walk_dir` (`core/src/walk.rs`) parallelises **recursion into subdirectories** and
nothing else. The per-entry loop inside one directory — where the `metadata()`
syscall lives, the walk's dominant cost — is sequential.

A tree with many directories therefore parallelises; **a single wide directory does
not**. Measured on 50,000 files in one directory: 118.8 ms at one thread, 110.5 ms
on all sixteen — **1.08×**, with identical system time.

"A flat media library" is one of the three shapes this tool claims to handle. The
`media` fixture hides the problem by holding only 40 files.

## What the measurements say

Stat-ing one directory's entries, sequential vs `par_iter`, best of five
alternating passes (`just bench-stat <dir>`):

| Entries in one directory | Speed-up on 16 threads |
|--------------------------|------------------------|
| 50 | **0.33×** |
| 350 | **0.71×** |
| 2,000 | 1.02× |
| 10,000 | 1.89× |
| 50,000 | 1.98× |

Two facts follow, and the second is the one that shapes the design:

1. **The kernel permits it.** Metadata lookups in one directory scale to ~2× —
   the same ceiling directory-level parallelism reaches. Contention is real but
   symmetric; it is not a reason to skip this.
2. **Below ~2,000 entries `par_iter` costs more than it saves.** Rayon's per-task
   overhead exceeds the work: 0.33× at 50 entries, 0.71× at 350.

**Parallelising the loop unconditionally would regress the common case by ~30%.**
The `node_modules` fixture's leaf directories hold 350 files each — squarely in the
losing range — and that fixture has no wide directory to gain from the change. Any
implementation that skips the threshold is worse than doing nothing.

## Design

In `walk_dir`:

1. Drain `read_dir` into a `Vec<DirEntry>` instead of iterating it lazily.
2. If `len() >= PARALLEL_THRESHOLD` (start at 2,000; it is a tuning constant, not a
   law of the filesystem) process entries with `par_iter`, otherwise keep the
   existing sequential loop.
3. Both branches must produce **identical** `Walked` output — same entries, same
   skips. Skip collection currently pushes into a `&mut Walked`; the parallel
   branch needs a fold-and-merge instead, reusing the existing `absorb`.

Ordering is already irrelevant: `tree::aggregate` sorts children by path precisely
because the parallel walk's order is nondeterministic.

## Open questions — answer before implementing

- **What does buffering cost?** `read_dir` is currently lazy; collecting every
  directory into a `Vec` adds an allocation per directory, and most directories are
  small. If that cost is material it eats the win on exactly the trees that do not
  benefit. Measure before committing to step 1.
- **Is 2,000 the right threshold on Linux and Windows?** Every number here is APFS
  on one machine. The break-even depends on syscall cost and thread-pool overhead,
  both of which differ. Consider measuring in CI, or picking a deliberately
  conservative value.
- **Does nesting the pools hurt?** The parallel branch would run inside a
  `par_iter` over subdirectories. Rayon handles nested parallelism by work
  stealing, but the interaction with the ~2× ceiling is unmeasured.

## Expected payoff

- Wide flat directories: 1.0× → ~1.9×.
- Everything else: unchanged, by construction.
- Whole-scan effect on the current fixtures: **none** — none of them has a
  directory past the threshold. A fixture with one would have to be added to
  demonstrate the improvement, which is itself a signal about how common the shape
  is.

## Related work, ranked

The phase split (`just bench-phases`) puts the walk at 78–89% of a scan, so
everything else is a smaller prize:

| Target | Ceiling | Notes |
|--------|---------|-------|
| Per-directory parallelism (this plan) | ~1.9× on wide dirs only | Well understood; needs the threshold |
| `dedup` + `aggregate` | ~20% of total | Fully serial today, but only 13–22% of the time |
| Per-entry allocation | Unknown | A `PathBuf` per entry drives both the 630 B/entry memory and allocator pressure in the hot loop; needs a profiler, not a stopwatch |

## When

After v0.2. The detectors add per-entry work and touch this exact loop, so
optimising it first means doing it twice.
